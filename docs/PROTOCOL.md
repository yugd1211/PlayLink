# PlayLink 연결 프로토콜 (버전 1)

앱(폰)이 기다리고 Unity(PC)가 접속합니다. 기준 구현은 `tools/playlink-proto.js`, 고정 시험 벡터는 `tools/proto-vectors.json` 입니다.
이 문서와 기준 구현이 다르면 기준 구현이 맞습니다.

## 용어와 값

| 이름 | 내용 |
|---|---|
| PC(I) | Unity 에디터. 탐색을 묻고 TCP 를 겁니다(거는 쪽) |
| 폰(R) | 앱. UDP 질문에 답하고 TCP 를 받습니다(받는 쪽) |
| `pcId`, `phoneId` | 무작위 16자, `[A-Z2-7]`. PC 는 Windows 사용자마다 하나, 폰은 설치마다 하나 |
| 이름 | 사람에게 보이는 라벨. 글자·숫자·공백·`_-.()` 만, 32자까지 |
| 포트 | 폰의 TCP 7300 과 UDP 7300 (TCP 를 못 열면 7301~7309 중 하나. 실제 포트는 탐색 응답의 `port`) |
| base64url | 패딩 없는 base64url |
| 페어링 키 | 32바이트. 페어링이 끝날 때 양쪽이 저장 |

## 1. 탐색 (UDP)

PC 는 Start 중에 1초마다 `255.255.255.255:7300` 과 각 네트워크의 브로드캐스트 주소로 질문을 보냅니다. 내용은 UTF-8 JSON 한 개(512바이트 이하)입니다.

```json
{"t":"q","v":1,"pc":"<pcId>","name":"<PC 이름>","n":"<임의 8바이트 base64url>"}
```

폰은 질문을 보낸 주소와 포트로 **즉시** 답합니다(Windows 방화벽은 방금 보낸 것의 답만 몇 초 동안 통과시킵니다).

```json
{"t":"r","v":1,"ph":"<phoneId>","name":"<폰 이름>","port":7300,"busy":"<지금 보고 있는 pcId 또는 빈 문자열>","want":false,"n":"<질문의 n>","mac":"…","qr":true}
```

- `want`: 폰에서 이 PC 를 골랐거나 방금 이 PC 의 QR 을 찍음 → PC 가 접속해 주기를 바람.
- `mac`: 이 PC 와 페어링돼 있으면 페어링 키로, 이 PC 의 QR 을 찍은 상태면 `SHA256(QR 비밀)` 을 키로 만들고 `"qr":true` 를 붙입니다. 둘 다 아니면 `mac` 이 없습니다.
  `mac = base64url( HMAC-SHA256(키, "PLK1-DISC|" + pcId + "|" + phoneId + "|" + name + "|" + port + "|" + (want?1:0) + "|" + n)[0..16] )`
- PC 는 `n` 이 자기 질문의 것이고 `mac` 이 맞는 응답만 "페어링된 폰"으로 믿습니다. `mac` 이 없는 응답은 "새 폰"으로만 보여 주고 `want` 를 무시합니다. `mac` 이 틀린 응답은 버립니다.

**TCP 로 묻기(who)**: 탐색이 안 되는 망이나 USB(adb forward)에서는 PC 가 폰의 TCP 포트로 접속해 아래를 보내고(2장의 평문 틀), 폰은 UDP 응답과 같은 JSON 을 돌려준 뒤 닫습니다.

```json
{"t":"who","v":1,"pc":"<pcId>","name":"<PC 이름>","n":"<임의 값>"}
```

## 2. 접속과 키 교환 (TCP)

PC 는 채널마다 TCP 연결을 하나씩 겁니다. 채널(`ch`)은 `video`, `input`, `pair` 입니다.
키 교환 전의 메시지는 **평문 틀**: 길이 2바이트(빅엔디언) + UTF-8 JSON(2048바이트 이하).

| 순서 | 방향 | 내용 |
|---|---|---|
| m1 | PC → 폰 | `{"t":"hello","v":1,"pc":pcId,"name":…,"ch":…,"mode":…,"take":bool,"ni":<16B>,"commit":<SHA256(epkI ‖ ni)>}` |
| m2 | 폰 → PC | `{"t":"hello","v":1,"ph":phoneId,"name":…,"app":<versionCode>,"epk":<65B>,"nr":<16B>}` 또는 `{"t":"err","code":…,"msg":…}` |
| m3 | PC → 폰 | `{"t":"key","epk":<65B>}` (폰은 `SHA256(epk ‖ ni) == commit` 을 확인, 틀리면 끊음) |

- `epk`: 연결마다 새로 만든 P-256 공개키(압축 안 한 65바이트, `04‖X‖Y`).
- `mode`: `paired`(페어링 키가 있음, `ch` 는 `video`/`input`), `qr`(QR 비밀, `ch` 는 `pair`), `sas`(6자리 숫자 확인, `ch` 는 `pair`).
- `take`: 사람이 방금 시작한 연결이면 true(자동 재접속이면 false).
- m2 자리의 오류 코드: `version`, `bad_message`, `unknown_pc`(페어링돼 있지 않음 / 찍은 QR 의 PC 가 아님), `busy`(다른 PC 화면을 보는 중이고 사람이 바꾸기를 거절했거나 답이 없음).
  폰은 "바꿀까요?"를 묻는 동안 m2 를 최대 30초 미룰 수 있습니다. PC 는 m2 를 40초까지 기다립니다.

**키 계산**

```
Z    = ECDH(P-256) 의 공유 X 좌표 32바이트
th   = SHA256( "PLK1" ‖ u16(len m1) ‖ m1 ‖ u16(len m2) ‖ m2 ‖ u16(len m3) ‖ m3 )     (m1~m3 은 보낸 JSON 바이트 그대로)
psk  = paired: 페어링 키 32B / qr: SHA256(QR 비밀 16B) / sas: 0x00 32개
PRK  = HMAC-SHA256(key = th, data = Z ‖ psk)
K(l) = HMAC-SHA256(PRK, ascii(l) ‖ 0x01)
키   = K("enc i2r"), K("mac i2r"), K("enc r2i"), K("mac r2i"), K("pair"), K("sas")
숫자 = uint32_be(K("sas")[0..4]) mod 1000000 을 6자리로(앞을 0 으로 채움)
```

i2r 은 PC → 폰, r2i 는 폰 → PC 방향입니다.

**m3 뒤는 전부 레코드(3장)로 암호화**합니다. 마무리 메시지는 레코드 하나에 JSON 하나입니다.

1. `sas` 일 때만: 양쪽이 같은 6자리 숫자를 보여 줍니다. 폰에서 [허용]을 누르면 폰이 `{"t":"ok"}`, PC 에서 [확인]을 누르면 PC 가 `{"t":"ok"}` 를 보냅니다(순서 무관, 70초 기한). 거절하면 `{"t":"err","code":"rejected"}`.
2. PC → 폰 `{"t":"fin","proto":2,"caps":"h264,seat,take"}`
3. 폰 → PC `{"t":"fin","proto":2,"app":<versionCode>,"caps":"h264,seat"}` 또는 `{"t":"err","code":"proto",…}`

- 폰이 PC 의 fin 레코드를 확인하지 못하면(키가 다름 = 페어링 키나 QR 비밀이 다름) 그냥 끊습니다. PC 는 이것을 `auth_failed` 로 봅니다.
- `ch` 가 `pair` 이면 fin 을 주고받은 뒤 양쪽이 `K("pair")` 를 상대의 id·이름과 함께 저장하고 연결을 닫습니다. 그다음 PC 가 `paired` 로 `video`, `input` 을 겁니다.
- `proto` 는 영상/입력 메시지 형식 번호(지금 2)입니다.

**QR 내용**: `playlink://pair?v=1&pc=<pcId>&n=<URL 인코딩한 PC 이름>&s=<QR 비밀 16B base64url>`
폰은 찍은 뒤 2분 동안 그 PC 의 탐색 질문에 `want:true`, `qr:true` 로 답하고, PC 는 증명이 맞으면 `mode:"qr"` 로 접속합니다. QR 비밀은 한 번 쓰면 PC 가 새로 만듭니다.

## 3. 레코드

```
레코드 = len(2B 빅엔디언, 1..65535) ‖ 암호문(len 바이트) ‖ 태그(16B)
암호문 = AES-256-CTR(키 = 그 방향의 enc 키, 처음 카운터 블록 = seq(8B 빅엔디언) ‖ 0x00 8개)   (자바의 "AES/CTR/NoPadding" 과 같음)
태그   = HMAC-SHA256(그 방향의 mac 키, seq(8B) ‖ len(2B) ‖ 암호문)[0..16]
```

`seq` 는 방향마다 0 에서 시작해 레코드마다 1 씩 늡니다. 태그가 틀리면 연결을 끊습니다. 쓰는 쪽은 16384바이트 이하로 잘라 보냅니다.
fin 뒤로는 레코드의 평문을 이어 붙인 것이 하나의 바이트 흐름입니다(레코드 경계에 뜻이 없음).

## 4. 레코드 안의 내용

fin 뒤의 바이트 흐름에는 예전과 같은 **WebSocket 프레임(RFC 6455)** 이 HTTP 업그레이드 없이 바로 흐릅니다.
PC 가 예전의 서버 역할(마스크 없이 보내고, 마스크된 프레임을 받음), 폰이 클라이언트 역할입니다.
`video` 채널과 `input` 채널의 메시지(프레임 헤더, hello, caps, key, take, seat, 터치, 닫기 코드)는 예전 그대로입니다.

## 5. 폰이 연결을 받는 규칙

- 페어링되지 않은 PC 의 `paired` 접속은 `unknown_pc`.
- 비어 있을 때 페어링된 PC 가 걸면 묻지 않고 받습니다.
- 다른 PC 화면을 보는 중에 페어링된 PC 가 걸면 폰에서 바꿀지 묻습니다. 바꾸면 이전 PC 의 연결을 닫습니다.
- 같은 PC 가 같은 채널을 다시 걸면 이전 연결을 닫고 새 연결을 씁니다.
- `sas` 접속은 앱이 대기 화면일 때만 받고, 사람이 [허용]을 눌러야 끝납니다.

## 6. 알려진 한계

- 탐색 질문과 페어링 전의 응답은 증명이 없습니다. 같은 망의 다른 기기가 "새 폰"으로 보일 수 있고, 그래서 숫자 확인은 PC 와 폰 양쪽에서 합니다.
- P-256 계산을 Unity 쪽은 직접 구현했습니다(Mono 에 없음). 실행 시간이 일정하지 않습니다. 연결마다 새 임시 키를 한 번만 씁니다.
