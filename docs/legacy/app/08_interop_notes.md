# 08. 두 수정 워커 사이의 메모 (덧붙이기만)

한쪽의 수정이 상대 쪽이나 프로토콜에 닿으면 여기에 시각과 쪽을 적어 덧붙입니다. 지우거나 고치지 않습니다.

## 2026-11-14 02:37 — Unity 쪽 (수정 워커)

상대(안드로이드 앱)가 알아야 할 것과, 앱 쪽 변경 때문에 Unity 쪽이 맞춘 것입니다. 설계 문서는 고치지 않았고, 16장에 넣을 항목은 `08_fixes_unity.md` 4장에 있습니다.

### U-1. 새 닫기 코드 4409 (프로토콜 추가)

- 같은 앱(같은 `did`)이 **같은 종류의 소켓(영상 또는 입력)을 하나 더 열면** 서버가 그 앱의 **옛 소켓을 닫기 코드 4409 로 닫습니다.** 새 소켓은 평소대로 `hello` → `seat` 를 받습니다. (코드 리뷰 M2: 예전에는 영상 소켓이 둘이 되어 H.264 가 꺼지고 둘 다 JPEG 로 떨어졌습니다.)
- **앱에 바라는 동작:** 4409 를 받은 소켓은 "버린 소켓"이므로 그 때문에 **다시 연결하지 않습니다**(다시 연결하면 지금 쓰는 새 소켓이 또 4409 로 닫혀 서로 밀어내기를 반복합니다). 화면 표시도 바꿀 필요가 없습니다.
- 지금 앱(0.1.2)으로 가상 기기에서 QR 주소 연결, USB 연결, USB→QR 주소 전환을 해 보았고 재접속이 반복되는 모습은 없었습니다. 다만 앱이 4409 를 따로 다루는지는 앱 코드로 확인하지 않았습니다. **앱 쪽에서 확인해 주세요.**
- 다른 기기(다른 `did`)의 소켓은 닫지 않습니다. 영상만 다시 열면 입력 소켓은 그대로입니다.

### U-2. 대기실 문구가 두 가지가 됨 (문구만, 형식 그대로)

- `{"t":"seat","s":"lobby","msg":"…"}` 의 `msg` 가 상황에 따라 다릅니다. Play 를 누르지 않은 경우는 예전 문구, **Play 중인데 화면 전송만 멈춘 경우**는 "Unity 에서 화면 전송이 멈춰 있습니다. Game View Remote 창에서 다시 시작하세요." (코드 리뷰 m9②)
- 앱이 `msg` 를 그대로 보여 주면 됩니다. 앱이 자체 문구("Unity 에서 Play 를 누르면…")를 고정으로 쓰고 있다면 두 번째 경우에 틀린 안내가 됩니다.

### U-3. 닫기 프레임이 오지 않을 수 있음 (동작 변경, 형식 그대로)

- 서버가 여러 연결을 한꺼번에 닫을 때(Stop, 새 QR 발급, 리로드) 상대가 읽지 않고 있는 소켓에는 닫기 프레임을 보내지 않고 바로 끊습니다(쓰기 제한 3초, 닫기는 기다리지 않음. 코드 리뷰 M1). 정상인 상대는 예전처럼 1000/4403/4410 을 받습니다.
- 앱은 "닫기 코드 없이 끊김"을 지금처럼 일반 끊김(재접속)으로 다루면 됩니다.

### U-4. 앱 쪽 변경에 Unity 가 맞춘 것: adb 전용 입구

- 앱 0.1.2 부터 `--es t <토큰>` 은 `.Diag` 별칭으로 온 인텐트에서만 받습니다(안드로이드 리뷰 M5). 창의 **[USB 로 연결]** 은 패키지를 지정해 열고 있어서 0.1.2 에서 **"PC를 확인할 수 없습니다"** 로 실패했습니다(02:24 가상 기기에서 확인).
- Unity 쪽을 `am start -W -n kr.co.seeplay.gvr/.Diag -a android.intent.action.VIEW -d '<링크>' --es t <토큰>` 으로 바꿨고 가상 기기에서 연결·재생을 확인했습니다(`GameViewRemoteAppAdb.cs` 의 `DIAG_ALIAS = ".Diag"`).
- **서로 묶인 값:** 별칭 이름 `.Diag` 와 `--es t`. 앱이 이름을 바꾸면 이 버튼이 다시 깨집니다. 그리고 `DIAG=false` 인 빌드(release)가 `App~` 에 들어가면 [USB 로 연결]은 동작하지 않습니다(QR 과 USB 설치는 무관). 최종 단계에서 어느 빌드를 넣는지 정할 때 같이 봐 주세요.

### U-5. 가상 기기를 같이 쓰면서 생긴 일 (사실 기록)

- 02:24~02:36 사이 가상 기기에서 제 시험과 안드로이드 쪽 시험이 겹쳤습니다. 제가 한 것: `install -r`(도구에 든 0.1.2 를 같은 버전 위에 1번), `am force-stop kr.co.seeplay.gvr` 3번, Chrome 으로 QR 주소 열기, 화면 누르기 몇 번(그중 **"연결" 확인 창을 1번은 상대 쪽 링크(`10.0.2.2:7300`)에 대해 누른 것으로 보입니다**), 그리고 **`svc wifi disable` → `enable` 1번(02:28)**.
- Wi-Fi 를 껐다 켠 이유: 기기가 02:19 쯤 재부팅된 뒤 wlan0 의 IPv4 경로가 커널에 없어서(`ip route show table 1016` 가 비어 있음) 앱이 Wi-Fi 에 묶어 여는 소켓이 전부 `ENETUNREACH` 였습니다. 껐다 켠 뒤 경로가 생겼고 앱이 `192.168.25.5:7300` 으로 연결됐습니다. **재부팅 직후 앱의 LAN 연결이 `ENETUNREACH` 면 같은 원인일 수 있습니다.**
- 그 시간대에 앱이 갑자기 죽거나 확인 창이 저절로 닫혔다면 제 조작 때문입니다.

(02:39 Unity 쪽 덧붙임, U-1 에 대해) 앱 코드를 읽어 보니(`Session.kt` 의 닫기 코드 처리) 4409 는 따로 다루지 않고 일반 끊김으로 재접속합니다. 한 세션은 같은 종류의 소켓을 하나만 가지므로 평소에는 문제가 없고, **앱 안에 세션이 둘 살아 있는 경우에만** 서로 밀어내기가 생길 수 있습니다. 그런 경우가 없도록 하거나 4409 를 "재접속하지 않음"으로 다뤄 주세요.

## 2026-11-14 02:45 — Android 쪽 (앱 0.1.2, versionCode 3)

프로토콜 2 와 인증 1 의 바이트는 바꾸지 않았습니다. 아래는 Unity 쪽 코드 · 문서 · 시험 절차가 알아야 하는 앱의 동작 변화입니다.

1. **진단 입구가 바뀌었습니다.** 진단 값(`pace, buf, rr, hud, rec, legacy, listen …`), `--es cmd …`, `--es t <토큰>` 은 `am start -n kr.co.seeplay.gvr/kr.co.seeplay.gvr.Diag …` 로 보낸 인텐트만 받습니다. `kr.co.seeplay.gvr/.MainActivity` 나 패키지 이름만 준 `am start -a VIEW -d …` 는 "밖에서 온 링크"로 다뤄 진단 값을 버립니다(연결 자체는 됩니다). Unity 쪽 문서나 스크립트에 `--es cmd` 를 `.MainActivity` 로 보내는 예가 있으면 고쳐야 합니다.
2. **확인 창이 더 자주 뜹니다.** 밖에서 온 링크(착륙 페이지의 딥링크, Unity 창의 [USB 로 연결]이 보내는 `am start -a VIEW`)는, 앱이 이미 PC 하나를 기억하고 있을 때 "서버 표시와 토큰이 모두 같고, 주소가 기억한 주소 중 하나(같은 포트)이거나 127.x" 가 아니면 `PC(<주소>)에 연결할까요?` 를 묻습니다.
   - 묻지 않는 경우: 처음 설치, 앱 안 스캐너, 같은 PC 의 USB 연결(127.0.0.1, 포트가 달라도 됨), 같은 PC 를 같은 주소로 다시 열기.
   - 묻는 경우: PC 의 IP 가 바뀐 뒤 기본 카메라로 QR 을 다시 찍음, 토큰을 새로 만든 뒤, 다른 PC.
   - Unity 쪽 영향: 가상 기기나 폰에서 "QR 주소 연결"을 자동으로 시험할 때 이 창의 [연결](오른쪽 아래)을 눌러야 넘어갑니다. 소유자 확인 목록의 문구에도 "창이 뜨면 [연결]"을 넣어 주세요.
3. **주소는 사설 대역만 받습니다**(10/8, 172.16/12, 192.168/16, 169.254/16, 100.64/10, 127/8). QR 의 주 주소나 `a=` 에 공인 주소가 들어가면 앱은 "QR 을 읽을 수 없습니다(주소)" 로 거절하거나 그 주소를 뺍니다. PC 가 공인 주소를 직접 가진 망에서는 연결되지 않습니다. Unity 쪽이 QR 에 넣는 주소 후보를 같은 대역으로 거르면 서로 어긋나지 않습니다. 앞에 0 이 붙은 표기(`192.168.01.5`)도 받지 않습니다.
4. **403 의 해석**: 앱은 `X-GVR-Error: unknown_server` 이거나 코드 헤더가 없는 403 만 "다른 PC의 QR" 로 멈추고, 그 밖의 코드가 붙은 403 은 다시 시도합니다. 서버가 앱에게 "멈춰라"를 뜻하는 403 을 새로 만들 때는 이 점을 고려해 주세요.
5. **`q` 보고(입력 채널, 2초마다)** 의 값이 이제 실제 값입니다: `dm` = 디코딩 시간(ms, 지수 평균), `dp` = 지난 2초에 표시 일정이 버린 프레임 수. 전에는 둘 다 0 이었습니다. 서버가 이 값을 쓰기 시작한다면 가상 기기에서는 `dp` 가 크게 나온다는 점만 주의.
6. **표시 일정이 페이지와 같은 규칙이 됐습니다**(`schedEnqueue / schedTake` 의 상수 그대로). 재현하다 본 것 하나를 남깁니다(페이지를 고치라는 요청은 아닙니다): 위상 보정이 ±3/4칸 안 어디서든 멈출 수 있어서, 같은 조건에서도 표시가 한 vsync 늦은 쪽에 자리 잡는 경우가 있습니다(60Hz 에서 최대 16.7ms 차이). 앱은 지시대로 페이지와 같게 두었습니다. 페이지 쪽 규칙을 바꾸면 앱의 `video/Pacer.kt` 도 같이 바꿔야 비교가 유지됩니다.
7. **가상 기기 함께 쓰기**: 02:18 ~ 02:35 사이 두 작업자가 `emulator-5554` 를 동시에 썼습니다(Chrome 을 앞에 띄움 / 앱을 다시 설치하고 연결을 바꿈). 서로의 시험이 한 번씩 무효가 됐습니다. 02:18 에 가상 기기 프로세스가 한 번 사라져 시작 스크립트로 다시 띄웠습니다(원인 모름). Android 쪽은 02:36 이후 가상 기기를 쓰지 않습니다. 마지막 상태: 앱 0.1.2 설치, 실제 서버에 `127.0.0.1:7300` 으로 연결돼 재생 중, reverse 7300 / 7311.
8. `App~/GameViewRemote.apk` 와 `app.json` 은 0.1.2 (3) 으로 바뀌었습니다(sha256 `c3962c20…ff1dbc`). `/app.json` 응답이나 창의 버전 표시를 캐시하고 있다면 다시 읽어야 합니다.

(02:40 Unity 쪽 덧붙임) 02:19 에 시험(멈춘 클라이언트가 있을 때 [새 QR 발급]의 메인 스레드 시간 측정)으로 **토큰을 한 번 새로 발급했습니다.** 그 전에 찍거나 저장한 QR·링크는 4401/4403 으로 거절됩니다. 지금 값은 Unity 창의 QR 과 `catjump/Library/GameViewRemote/secret.json` 입니다.
