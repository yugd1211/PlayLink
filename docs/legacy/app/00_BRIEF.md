# Game View Remote App — 프로젝트 브리프 (모든 워커 공통)

이 문서는 조정자(coordinator)가 쓴 요구사항과 규칙입니다. 모든 단계의 워커는 작업 전에 이 문서를 끝까지 읽습니다.
이 문서의 "소유자 요구사항"은 소유자가 직접 말한 내용이고, 나머지 판단은 각 단계 문서에서 근거와 함께 정합니다.

## 2. 소유자 요구사항 (그대로 지킬 것)

1. APK 시제품을 만든다. 폰에 설치해서 Unity 에디터에 연결한다.
2. **구조부터 잘 잡는다.** 기획 → PRD → 설계 → 구현 → 리뷰 → 피드백 반영 순서로 진행한다.
3. Unity 쪽 도구를 설치하고, **그 도구에서 QR 을 만들어 앱 설치도 QR 로, 연결도 QR 로** 한다.
4. **주소나 포트를 직접 입력하지 않는다.** 잘 모르는 사람도 QR 한 번 찍으면 바로 연결돼야 한다.
5. 서버는 Unity 도구에서 **Start 같은 버튼을 누르면 열리고, 그러면 QR 이 생성되며, 그 QR 로 진입**한다.
6. QR 생성 등 필요한 것은 조사해서 정한다.
7. 작업은 Claude 워커만 쓴다(Codex 금지).
8. **시작 전에 문서를 하나 남긴다**: 지금 구조가 어떻게 돼 있는지, 왜 앱을 만들기 시작했는지, 지금까지 무엇을 시도했고 무엇이 틀렸는지. 나중에 앱에서 문제가 생겼을 때 이 문서를 보고 시행착오를 줄일 수 있어야 한다(`docs/00_current_system_and_history.md`).
9. 폰은 PC 에 연결돼 있다. **워커가 APK 를 직접 설치하고 시험까지 알아서 한다**(adb 설치와 실행 허용). 소유자에게 확인을 구하느라 멈추지 않는다.
10. **QR 은 만들어 두기만 하면 된다.** QR 을 폰 카메라로 찍는 시험은 소유자가 나중에 한다. 워커는 QR 이 올바른 내용으로 생성되는지(생성한 이미지를 프로그램으로 다시 읽어 확인), QR 이 가리키는 주소/딥링크가 실제로 동작하는지(adb 로 같은 URL/인텐트를 열어 확인)까지 검증한다.

11. **최종 목표는 무선(Wi-Fi) 연결이다.** 지금까지 USB 로 진행한 것은 USB 가 더 빨라서 먼저 맞춰 본 것일 뿐이다. 앱의 기본 경로와 합격 기준은 무선이어야 하고, USB 는 개발 중 기준선과 대체 수단이다. 조사·PRD·설계·시험 계획 모두 무선에서의 부드러움과 지연을 1순위로 다룬다(무선 adb 터널이 아닌 LAN 직접 연결, TCP 대 UDP, 지터 버퍼, 프레임 버림과 키프레임 복구, 비트레이트 적응, 2.4GHz/5GHz 차이 포함). 측정도 무선에서 한 수치를 반드시 포함한다.

12. (Chrome 쪽이 잘 동작하는 것을 확인한 뒤의 결정) **앱은 그대로 진행한다.** 이유는 "다른 곳에서 쓰기 좋게, 그리고 기능을 더 붙일 수 있을 것 같아서"다. 따라서 설계는 (a) **다른 Unity 프로젝트에서도 쓸 수 있는 형태**(catjump 에 묶이지 않는 구조: 게임 코드 의존 없음, 프로젝트별 설정 분리, Unity 쪽을 패키지로 떼어낼 수 있는 경계)와 (b) **기능을 붙이기 쉬운 구조**(프로토콜 버전·기능 협상, 메시지 종류를 늘릴 수 있는 틀, 앱의 모듈 경계)를 갖춰야 한다. 어떤 기능을 붙일지는 정해지지 않았으니 구체 기능을 미리 만들지는 말고, 붙일 자리만 만든다. 설계 문서에 확장 지점과 재사용 시 바꿔야 하는 것을 따로 적는다.

## 3. 조사와 설계에서 반드시 답해야 하는 질문

- QR 설치: 폰 기본 카메라로 QR 을 찍어 APK 를 받게 하려면 무엇이 필요한가(Unity 서버가 APK 를 HTTP 로 제공, 출처를 알 수 없는 앱 설치 허용 흐름, Play Protect 경고, 서명, 버전 갱신 시 재설치). 설치 QR 과 연결 QR 을 하나로 합칠 수 있는가(예: 서버가 주는 착륙 페이지가 앱이 있으면 앱을 열고 없으면 APK 를 받게 함, 커스텀 스킴/intent URL/App Links 중 무엇이 서명되지 않은 사내 앱에서 실제로 동작하는가).
- QR 연결: QR 에 무엇을 담는가(주소 후보 여러 개, 포트, 일회용 토큰, 프로토콜 버전). 앱 안 스캐너(CameraX + ML Kit 또는 ZXing)와 기본 카메라 딥링크 중 무엇을 쓰는가. PC 에 네트워크 어댑터가 여러 개일 때(VPN, 가상 어댑터) 어느 주소를 넣는가.
- 네트워크: QR 연결은 같은 Wi-Fi 직접 접속을 뜻한다. **Windows 방화벽**이 Unity.exe 의 들어오는 연결을 막는 문제를 관리자 권한 없이, 사용자가 명령을 치지 않고 어떻게 넘는가(가능한 방법과 한계를 실제로 이 PC 에서 확인). USB/adb reverse 경로는 앱에서도 대체 수단으로 남길 것인가. 재접속(자동 발견: mDNS/NSD, 마지막 서버 기억)은 어떻게 하는가.
- 보안: 지금 서버는 인증이 없다. LAN 에 여는 순간 누구나 화면을 보고 조작할 수 있다. QR 의 토큰으로 무엇을 어떻게 막는가.
- 0단계에서 확인된 사실(자세한 내용은 `docs/00_current_system_and_history.md`): 서버가 보내는 H.264 는 Annex B 가 아니라 **AVCC + avcC** 다. 영상 클라이언트가 2개면 둘 다 MJPEG 로 떨어진다. caps/key/ack 판정이 문자열 검사라 형식에 민감하다. 지금 있는 무선 수치는 전부 무선 adb 터널 것이고 LAN 직접 수치는 없다. 탭 끊김 원인은 아직 확정되지 않았다. 따라서 설계에서 정할 것: H.264 형식 변환을 앱과 서버 중 어디서 할지, Chrome 페이지 세션과의 공존 방식과 시험 포트, 무선 합격 기준(LAN 직접 수치를 재기 전까지는 잠정값으로 두고 구현 단계에서 실측으로 확정).
- 전송: 지금의 WebSocket(TCP) + H.264(AVCC) 를 그대로 쓰는가, 앱 전용 경로를 두는가. Wi-Fi 에서의 지연/정체를 어떻게 다루는가(지터, 프레임 버림, 키프레임 요청, 비트레이트).
- 앱: MediaCodec 저지연 설정, SurfaceView/TextureView, 주사율 지정(Surface.setFrameRate), 터치 전달(멀티터치, 좌표계), 전체 화면/화면 켜짐 유지, 화면 방향, 수명 주기(백그라운드, 재접속), 진단 HUD.
- QR 생성: Unity 에디터에서 외부 서비스 없이 QR 을 그리는 방법(순수 C# 구현, 라이선스가 맞는 라이브러리, 직접 구현). 인터넷이 필요하면 안 된다.
- 빌드: 이 PC 에 있는 도구로 APK 를 빌드할 수 있는가(Unity 내장 Android SDK/NDK/JDK/Gradle 경로와 버전, 별도 Android Studio 유무). 최소 SDK 버전. 서명(디버그 키).
- 배포 형태: 도구를 다른 Unity 프로젝트에도 "설치"할 수 있게 하려면 지금의 `Assets/04_Scripts/Editor/GameViewRemote/` 를 어떻게 묶는가(UPM 패키지 등). 이번 시제품 범위에 넣을지 다음 단계로 둘지.

## 3.1 조정자 결정과 새 사실 (PRD 리뷰 뒤 추가, 3단계부터 적용)

새 사실(진단 워커, 실제 손가락 탭 87회 기록):
- **탭 끊김의 원인이 확인됐다.** 손가락이 화면에 닿아 있는 동안(60~150ms) Chrome 페이지의 메인 스레드가 영상 프레임을 받지 못하고, 손을 떼는 순간 몰아서 받는다(탭의 약 60%). adb 로 주입한 탭은 누르는 시간이 없어서 재현되지 않았다. 60/120Hz 전환은 주원인이 아니었다.
- 웹 페이지는 영상 수신·디코딩·표시 일정·그리기를 Web Worker + OffscreenCanvas 로 옮겼고(기본 켬, `?worker=0` 이 예전 방식), 소유자가 "웹으로 잘 되는 것 같다"고 확인했다. 전후 수치 보고는 아직 오지 않았다. 무선 adb 터널에서는 ack 최대 약 130ms 의 정체가 여전히 보인다.
- 따라서 앱의 존재 이유는 "탭 끊김 제거"에서 **(1) QR 로 쉬운 설치와 연결, (2) 무선(LAN 직접)에서의 품질** 쪽으로 무게가 옮겨졌다. 앱이 탭 중에도 영상을 계속 받는지는 여전히 합격 조건으로 재되(실제 누르는 시간이 있는 탭으로: `adb shell input swipe x y x y 100` 처럼 제자리 100ms 누름), 비교 대상은 워커 경로가 적용된 새 웹 페이지다. 시험에서 주입 탭은 반드시 누르는 시간을 가진 것을 쓴다.

조정자 결정(리뷰 C1~C5):
- C1 방화벽 UAC: 지금 소유자에게 요청하지 않는다. 도구에 버튼을 만들어 두고 소유자가 나중에 누른다. 그 전까지 LAN 직접 측정은 이미 허용된 `node.exe` 중계로 한다. 리뷰 M11(방향 뒤집기: 앱이 듣고 PC 가 거는 방식) 실험은 필수로 한다. 관리자 동의 없이 무선 직접 연결이 되는 유일한 후보이기 때문이다.
- C2 폰 화면 조작: QR 설치/연결 흐름을 확인하려고 워커가 adb 로 폰 브라우저와 이 앱 화면을 누르는 것은 허용한다. 단 **폰의 보안 설정을 바꾸는 화면(출처를 알 수 없는 앱 설치 허용, 자동 차단 해제 등)은 누르지 않는다.** 그 화면이 나오는 데까지 확인하고 화면 내용을 기록한다. 앱 설치는 adb 로 한다.
- C3 6단계(Unity 쪽 구현) 시작 시점: 진단 워커가 끝난 뒤 조정자가 시작한다. 공존 규칙과 Play 밖 서버처럼 기존 파일을 바꾸는 것은 6단계에서 한다.
- C4 연속 시험: 폰에서 30분 연속 시험은 허용한다. 소유자가 폰을 쓰고 있는 것으로 보이면(통화, 다른 앱 사용) 미루고 보고에 적는다.
- C5 실제 Unity 서버로 재는 시간: 5단계에서는 짧게(한 번에 몇 분) 쓴다. 그동안 Chrome 세션이 밀려나므로, 끝나면 Chrome 페이지가 다시 붙었는지 확인한다. 진단 워커가 아직 측정 중이면 재생 서버를 먼저 쓰고 실제 서버 측정은 뒤로 미룬다.
- 리뷰의 차단 B1(합격 조건이 실제 서버·무선·실제 게임 탭 없이도 채워짐)과 B2(Chrome 페이지 재접속과 서로 뺏는 공존 규칙)는 반드시 PRD 에서 고친다.

## 3.2 조정자 결정 (설계 14장 질문에 대한 답, 4단계부터 적용)

진단 워커는 끝났다. Unity GameViewRemote 폴더는 이제 이 프로젝트 워커만 고친다(6단계부터). 폰은 지금 가변 120Hz 모드다.
1. 실제 서버(7300)에 앱이 붙는 시험: 허용. 한 번에 몇 분으로 짧게 하고, 필요하면 폰 Chrome 탭을 잠시 떼었다가 끝나면 기본 주소·전체 화면으로 되돌려 다시 붙었는지 확인한다.
2. 측정을 위해 도구 창 설정(무선 우선, 비트레이트, 테스트 패턴)을 바꾸는 것: 허용. 끝나면 원래 값으로 되돌리고 보고에 적는다.
3. `GameViewRemotePage.html` 에 [여기서 보기] 버튼 같은 작은 수정: 6단계에서 허용.
4. 식별자 `kr.co.seeplay.gvr`, 스킴 `seeplay-gvr`: 확정(시제품). 다른 프로젝트·회사에서 재사용할 때 바꿔야 하는 값으로 설계 15장에 남긴다.
5. 6단계는 5단계가 끝난 뒤 시작한다.
6. 5GHz 측정과 방화벽 UAC 는 최종 보고(8단계)에서 소유자에게 요청한다. 그 전에는 요청하지 않는다.
7. 잠정 수치 기준은 5단계 실측을 근거로 8단계가 확정안을 내고, 최종 보고에서 소유자가 받아들인다.

## 3.3 조정자 결정 (설계 리뷰 5장에 대한 답, 5단계부터 적용)

## 3.4 소유자 지시: 실제 폰 사용 금지 (2026-11-14 00:55 부터, 이전의 폰 관련 허용을 모두 대체)

- **실제 폰(SM-F731N, R3CW70LJ2VP, 192.168.25.60:5555)으로 시험하지 않는다.** adb 명령, 설치, 실행, 입력, 화면 캡처, logcat, adb connect, adb reverse 모두 금지. 폰은 USB 와 무선 adb 모두 끊겨 있고 다시 연결하지 않는다.
- 시험 순서(소유자 지시): (1) PC 의 안드로이드 가상 기기(AVD `Medium_Phone_API_35`, 시리얼 `emulator-5554`)가 뜨면 그것으로 계속 시험한다. (2) 가상 기기가 안 되면 비슷하게 띄울 수 있는 오픈소스 대안을 설치해 진행한다. (3) 그것도 안 돼 시험할 수 없으면 문서와 코드로 미리 파악해서 처리하고, 기기에서 확인하지 못했다고 명시한다.
- 가상 기기의 한계를 문서에 적는다: x86_64 이미지, 소프트웨어/호스트 GPU 디코더라 실제 폰의 디코딩 시간·주사율·터치 표본화·Wi-Fi 특성과 다르다. 가상 기기에서 잰 부드러움과 지연 수치는 기능 확인용이고 실제 폰 합격 기준의 근거가 아니다. 무선 수치는 가상 기기로 잴 수 없다. 이미 실제 폰에서 잰 수치는 측정 시각과 함께 문서에 남긴다.
- 가상 기기에서 PC 의 서버에 닿는 방법: `adb -s emulator-5554 reverse tcp:포트 tcp:포트` 또는 호스트 주소 `10.0.2.2`. adb 는 항상 `-s emulator-5554` 를 붙인다.
- 실제 폰에서만 확인할 수 있는 항목(카메라로 QR 찍기, 삼성 인터넷 동작, 실제 Wi-Fi, 손가락 탭, 60/120Hz)은 최종 보고의 소유자 확인 목록으로 모은다.
