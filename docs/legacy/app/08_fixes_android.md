## 2. 항목별 내용

### B1 (차단)
- 통합 워커가 넣은 것은 "자리 `active` 를 받을 때 `expectFirstFrame()`" 한 곳이었고, H.264 가 돌아오는 경우(NOCODEC)는 빠져 있었습니다.
- 지금은 **세션이 WAITING 이나 NOCODEC 에 들어갈 때마다**(`Session.setState`) 디코더에 "다음에 화면으로 넘기는 프레임에서 알려 달라"고 겁니다. 이 두 상태를 벗어나는 길이 그것 하나이므로, 디코더를 새로 만들었는지와 상관이 없습니다.
- 확인: 재생 서버에서 대기(`/ctl?standby=1`) → [여기서 보기] → `STANDBY → WAITING → PLAYING`(0.05초), 문구 사라지고 영상. 실제 Unity 서버에서 `hosttest.js withapp` 6/6 통과(`STANDBY → WAITING → PLAYING` 0.4초).
- 미확인: JPEG 가 2초 넘게 오다가 H.264 로 돌아오는 경우(재생 서버에 JPEG 를 보내는 기능이 없음). 같은 코드 길을 탑니다.

### M1 표시 일정 → 3장

### M2 세션 경계 (+ m4)
- `Session.run`: 막히는 단계(소켓 연결, 업그레이드 2번) 뒤마다 `stopped` 확인. 끊김 신호는 연결 시도마다 새 객체(`Attempt`)라서 `stop()` 의 신호가 다음 시도에서 지워지지 않습니다.
- `stop()` 은 걸고 있는 소켓(`dialing`)과 듣기 소켓까지 닫습니다.
- `Session.Ui` 의 모든 콜백이 세션 자신을 넘기고, `MainActivity` 는 `session !== this.session` 이면 버립니다(전에는 `session == null` 만 봄).
- `Decoder.attach(owner)`: 디코더의 주인을 정하고, 주인이 아닌 세션의 `reset / onConfig / onFrame / expectFirstFrame` 은 버립니다. `reset` 이 false 면 세션은 물러납니다.
- m4: 입력 번호는 연결마다 "입력 세대"와 함께 다시 시작하고, 세대가 다른 포인터 메시지는 세션이 버립니다.

### M3 주사율
- `rr=match` 가 `Surface.setFrameRate(원본 프레임률)` 을 씁니다. 원본 프레임률은 캡처 시각 간격의 중앙값(31장마다)에서 재고, 바뀌면 다시 요청합니다.

## 3. 표시 일정(M1): 규칙, 재현, 전후

### 규칙 (`video/Pacer.kt`, Android 클래스 없음)
웹 페이지의 `schedEnqueue / schedTake` 와 같은 규칙, 같은 상수입니다.
- 표시 예정 = 캡처 시각 + base(최근 10초 중 가장 빨리 준비된 프레임의 "디코딩 완료 − 캡처") + delay
- delay = 최근 120장 흔들림의 95% 지점 + 2ms, 3 ~ 25ms(처음 16.7ms). 10장마다 목표를 다시 계산
- vsync 마다: 예정 + 위상 ≤ vsync 인 것 중 가장 새 것 1장, 그보다 오래된 것은 버림. 대기열 6장
- 위상: 예정이 vsync 사이 한가운데에 오도록 0.1 씩 보정, ±3/4칸을 넘으면 한 칸 넘김
- **페이지와 다른 점 하나**: delay 를 한 번에 바꾸지 않고 프레임당 0.25ms 이하로 움직입니다(리뷰 M1 의 3). 아래 표의 "slew" 비교가 근거입니다.

v3 의 "간격 지키기"(1.5칸 따라잡기, 예정이 반 칸 지난 프레임 버리기)는 없앴습니다.

### 재현 방법

### 읽는 법과 한계 (좋은 것만 적지 않습니다)
- v3 기록 2개에서: 제때 왔는데 버린 프레임이 줄고(skip 22 → 8, 30 → 18) 디코딩 뒤 기다리는 시간이 5ms 쯤 줄었습니다(리뷰가 짚은 두 가지). **대신 `w2_tap1` 의 hold 는 10 → 28 로 늘었습니다.** v3 가 프레임을 버려서 얻던 고른 간격을 잃은 것이고, 120Hz 패널에서 위상이 한 칸 넘어갈 때(slips 9번)마다 8.3ms 가 어긋나 hold 로 셉니다.
- 전체 13개에서는 hold 가 31% 줄고 skip 은 같은 수준입니다. 120Hz 로 받은 버전 2 기록(`w_tap*`)은 skip 이 늘었습니다(22 → 39 등).
- USB 기록(`t_*`)에서는 wait 가 오히려 늘었습니다(7.5 → 17.2ms). 이 규칙은 예정 시각을 vsync 사이 한가운데에 두므로 반 칸(60Hz 에서 8.3ms)을 기본으로 얹고, 위상이 ±3/4칸 안 어디서든 멈출 수 있어 같은 조건에서도 최대 한 칸 차이가 납니다. 페이지도 같은 성질입니다(`08_interop_notes.md` 에 적음). 페이지와 같은 규칙을 쓰라는 지시에 따라 그대로 두었습니다.
- 그러므로 "v3 보다 낫다"는 것은 **v3 의 두 문제(지연, 제때 온 프레임 버리기)에 한해서**이고, 멈춤 수는 기록에 따라 늘기도 줄기도 합니다. 실제 폰에서 다시 재야 결론을 낼 수 있습니다(5장).
- 가상 기기에서는 동작(재생, 재접속, 방식 전환)만 봤습니다. 가상 기기의 holds / skipped 값은 의미가 없습니다.
