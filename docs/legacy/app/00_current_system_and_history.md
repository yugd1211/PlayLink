- 목적: 나중에 안드로이드 앱에서 문제가 생겼을 때 이 문서를 먼저 읽고 같은 시행착오를 반복하지 않게 합니다.
- **최종 목표는 무선(Wi-Fi) 연결입니다**(브리프 소유자 요구사항 11). 지금까지 USB로 진행한 것은 USB가 더 빨라서 먼저 맞춰 본 것일 뿐이고, 앱의 기본 경로와 합격 기준은 무선(무선 adb 터널이 아닌 LAN 직접 연결)입니다. USB는 개발 중 기준선과 대체 수단입니다. 그래서 이 문서의 수치를 읽을 때는 **어느 경로에서 잰 것인지**를 먼저 봐야 합니다. 대부분의 "고쳤다"는 수치는 USB에서 잰 것이고, 무선에서 잰 것은 [3.6절](#36-무선-사실-모음-최종-목표-경로)에 따로 모았습니다. [브리프]
- 급할 때 읽는 순서: [3.6 무선 사실 모음](#36-무선-사실-모음-최종-목표-경로) → [5장 교훈과 함정](#5-교훈과-함정-앱에-그대로-적용되는-것) → [1.5 프로토콜](#15-전송-프로토콜-지금-구현-그대로) → [6장 측정 방법](#6-측정-방법-다시-할-수-있게) → [7장 열린 문제](#7-알려진-열린-문제와-모르는-것).

## 1. 도구가 무엇이고 어떻게 흐르는가

### 1.1 한 줄 요약

Unity 에디터에서 Play 중인 Game 뷰 화면을 안드로이드 폰 Chrome 페이지에 실시간으로 보내고, 폰 터치를 에디터에 실기기 터치처럼 넣는 에디터 전용 도구입니다. Unity Remote 5를 대신합니다. [코드, 개발문서 1]

- 대상: Unity 2022.3.62f2, Windows 에디터, 레거시 Input Manager(`activeInputHandler: 0`). 게임 스크립트 22개가 `Input.touches` 등을 직접 읽어서 입력은 레거시 `Input.touches` 자체를 채워야 합니다. [개발문서 1]
- 전부 `Editor` 폴더 아래라 빌드에 들어가지 않고 게임 코드를 바꾸지 않습니다. [코드]
- 서버는 **Play 중에만** 돕니다. Play 종료, 도메인 리로드, 에디터 종료 때 닫습니다. Play 중 재컴파일이면 `SessionState` 표시로 리로드 뒤 다시 엽니다. [코드: `GameViewRemote.cs`]

### 1.2 전체 흐름 그림

```
┌──────────────────────── Unity Editor (Play 중, Windows) ────────────────────────┐
│ [메인 스레드] PlayerLoop: EarlyUpdate.UpdateInputManager 직전 = RemoteUpdate    │
│   ① 프레임 시간 기록 (Trace)                                                    │
│   ② 캡처: 끝난 리드백 확인 → Game 뷰 렌더 타깃(PlayModeView.m_TargetTexture)    │
│      → (필요 시 GPU Blit: 상하 반전/축소) → AsyncGPUReadback(RGBA32, 최대 3개)   │
│      ※ 이 시점의 화면은 "직전 프레임" 렌더 결과                                 │
│   ③ 입력 주입: 큐 → Input.SimulateTouch(리플렉션) + EventSystem 포커스 강제     │
│   ④ 1초 통계 + 자동 프레임 간격 판정                                            │
│ [메인 스레드] PostLateUpdate 맨 끝 = RemoteLateUpdate                           │
│   저지연 리드백(기본 켬): 이번 프레임 리드백을 Update()/WaitForCompletion()     │
│                                                                                 │
│ 리드백 콜백(메인) → 픽셀 복사(버퍼 풀) → 인코딩 대기 "최신 1장"                 │
│        │                                                                        │
│ [GVR Encoder 스레드] 프레임 검사(검정/크기) → 전체 픽셀 해시(같은 화면 판정)    │
│        ├─ H.264: stdin(RGBA) ─▶ ffmpeg h264_nvenc ─▶ stdout(FLV)                │
│        │         [GVR H264 Reader 스레드] FLV 태그 1개 = 프레임 1장             │
│        │         → 헤더 28B + AVCC → 클라이언트 "순서 큐"(버리지 않음)          │
│        └─ MJPEG: EncodeArrayToJPG → 헤더 28B + JPEG → 클라이언트 "최신 1장 슬롯"│
│                                                                                 │
│ [GVR Video Send 스레드, 영상 연결당 1개] 수신 확인/역압을 보고 메시지 1개를     │
│   소켓 쓰기 1번으로 전송                                                        │
│ [GVR Client 스레드, 연결당 1개] HTTP 파싱, WebSocket 수신(ack, caps, key, 입력) │
│ TcpListener 127.0.0.1:7300 (기본) 또는 0.0.0.0:7300 ("Wi-Fi 접속 허용")         │
└───────────────┬─────────────────────────────────────────────▲───────────────────┘
                │ ws /video (바이너리 프레임, 상태 텍스트)      │ ws /input (포인터 JSON, ping, 보고)
                │                                             │ ws /video ("a", caps, key)
        ┌───────▼─────────────────────────────────────────────┴───────┐
        │ 전송 구간: USB adb reverse / 무선 adb + adb reverse / Wi-Fi 직접 │
        └───────┬─────────────────────────────────────────────▲───────┘
┌───────────────▼──────────────── 폰 Chrome 페이지 ───────────┴───────────────────┐
│ onmessage: 받자마자 "a" 전송 → H.264면 WebCodecs VideoDecoder.decode (받은 순서) │
│            MJPEG면 createImageBitmap (최대 2개 병렬, 받은 순서대로 넘김)        │
│ 표시 일정(기본 켬): 헤더의 캡처 시각 + base + delay = 표시 예정 시각            │
│ requestAnimationFrame: 예정 시각이 지난 것 중 최신 1장을 2D 캔버스에 drawImage   │
│ pointer 이벤트 → 0~1 좌표 JSON → ws /input (move는 rAF당 포인터별 1개)          │
└─────────────────────────────────────────────────────────────────────────────────┘
```
[코드: `GameViewRemote.cs`, `GameViewRemoteCapture.cs`, `GameViewRemoteServer.cs`, `GameViewRemoteH264.cs`, `GameViewRemotePage.html`]

단계별 핵심:

| 단계 | 하는 일 | 근거 |
|---|---|---|
| 캡처 | `PlayModeView.m_TargetTexture`(private, 리플렉션)를 읽음. `ScreenCapture`는 에디터 창 백버퍼(툴바 포함)를 잡아서 안 씀. 캡처 간격 = `max(TransportStride, ceil(Unity fps / FPS Cap − 0.05))` 프레임마다 1번. 리드백은 최대 3개 겹침, 넘으면 건너뜀 | [코드] |
| 행 순서 | D3D11 + JPEG면 GPU에서 뒤집고, D3D11 + H.264면 그대로. 형식이 바뀌는 순간의 프레임은 인코더 스레드가 행을 바꿈 | [코드] |
| 전송 해상도 | Game 뷰 대비 100/75/50%, GPU에서 줄인 뒤 읽음. 크기는 짝수로 맞춤 | [코드] |
| 같은 화면 | 전체 픽셀 해시가 같으면 H.264는 **아예 안 보냄**(키프레임 요청이 와 있을 때만 예외), MJPEG는 200ms마다 이전 JPEG를 flags=1로 다시 보냄 | [코드] |
| H.264 인코딩 | ffmpeg 외부 프로세스. 인자: `-f rawvideo -pix_fmt rgba -s WxH -framerate 60 -i pipe:0 -c:v h264_nvenc -preset p1 -tune ull -zerolatency 1 -delay 0 -bf 0 -g 600 -rc cbr -b:v {kbps}k -maxrate {kbps}k -bufsize {max(100, kbps/30)}k -profile:v high -flush_packets 1 -flvflags no_duration_filesize -f flv pipe:1` | [코드: `GameViewRemoteH264.cs`] |
| H.264 출력 형식 | FLV 태그에서 앞 5바이트를 뗀 것. 첫 태그 = **avcC**(AVCDecoderConfigurationRecord), 이후 = **AVCC**(길이 4바이트 + NAL) 프레임 1장. **Annex B(시작 코드)가 아닙니다** | [코드] |
| 인코딩 성능 | 파이프(720x1280, 5Mbps) 입력→FLV 태그 p50 3.0ms, p95 3.5ms, 시작 약 0.3초, 프레임 약 10KB | [측정·개발문서 13.3] |
| 입력 주입 | `Input.SimulateTouch(Touch)`(internal static, 리플렉션)를 `EarlyUpdate.UpdateInputManager` 직전에 호출. 같은 프레임에 `Input.touches`에 들어감 | [코드, 개발문서 1.1] |

Unity 내부 API 의존(버전을 올리면 다시 확인): `Input.SimulateTouch`, `PlayModeView.m_TargetTexture`, `EventSystem.m_HasFocus`, `EditorWindow.m_Parent` + `HostView.actualView`. [코드, 개발문서 9.1]

#### 1.5.3 `/video` : 서버 → 클라이언트

접속 직후 순서: ① 텍스트 `{"t":"hello","v":2}` ② (있으면) 마지막 상태 텍스트 ③ 마지막 프레임(seed, MJPEG일 때 의미 있음) ④ 이후 프레임. [코드]

텍스트 메시지:

| 메시지 | 뜻 | 근거 |
|---|---|---|
| `{"t":"hello","v":2}` | 프로토콜 번호. 페이지는 자기 번호와 다르면 스스로 새로 고침(5초에 1번까지) | [코드] |
| `{"t":"s","stale":true,"msg":"…"}` / `{"t":"s","stale":false}` | 게임 카메라가 0.7초 넘게 안 그림(일시정지 / Game 뷰 탭 가려짐 / 그 밖). 바뀔 때만 보냄 | [코드] |

바이너리 메시지 = **헤더 28바이트(little-endian) + 내용**:

| 오프셋 | 타입 | 필드 | 내용 | 근거 |
|---|---|---|---|---|
| 0 | u32 | frameId | 헤더를 쓸 때마다 1 증가하는 공용 번호. H.264는 **ffmpeg 출력 시점**에 매김. **설정(avcC) 메시지도 번호를 하나 씀** | [코드: `WriteHeader`] |
| 4 | u16 | width | 보내는 영상 너비(축소 적용 후) | [코드] |
| 6 | u16 | height | 높이 | [코드] |
| 8 | i32 | inputSeq | 이 화면을 캡처할 때까지 주입된 마지막 입력 번호. 설정 메시지에서는 0 | [코드] |
| 12 | u32 | encodeUs | 인코딩 시간(μs). H.264는 ffmpeg에 넣은 때 → 출력까지 | [코드] |
| 16 | u32 | captureToEncodedUs | 캡처 요청 → 헤더 작성까지(μs) | [코드] |
| 20 | u32 | flags | 1 = 같은 화면 재전송(JPEG), 2 = H.264, 4 = 키프레임, 8 = H.264 설정(avcC, 프레임 아님) | [코드] |
| 24 | u32 | captureTime | 캡처 시각. 서버 Start 뒤 흐른 시간, **0.1ms 단위**. 서버를 다시 시작하면 0부터 | [코드] |
| 28 | — | 내용 | JPEG 파일 1개 / AVCC(길이 4B + NAL) 프레임 1장 / avcC 레코드 | [코드] |

- H.264 스트림의 순서: (인코더 시작 또는 재시작) → `flags = 2|8` 설정 1개 → `flags = 2|4` 키프레임 → `flags = 2` 델타들. 설정이 `2|4|8`로 올 가능성도 코드상 열려 있으므로(FLV 시퀀스 헤더 태그의 frameType에 따름) 플래그는 비트로 판정해야 합니다. [코드]
- 페이지는 avcC의 1~3번째 바이트(profile, compatibility, level)로 `avc1.PPCCLL` 코덱 문자열을 만들고, avcC를 `description`으로 넘깁니다. 실세션에서 `avc1.640020`. [코드], [측정·진단]
- GOP는 600프레임. 주기적 키프레임에 기대지 말고 요청해야 합니다. [코드]

#### 1.5.5 수신 확인과 역압

| 항목 | 값/동작 | 근거 |
|---|---|---|
| MJPEG | 확인 안 된 프레임이 2장(`MAX_FRAMES_IN_FLIGHT`)이면 더 안 보냄. 그사이 새 프레임은 슬롯의 이전 프레임을 덮어씀(전송 버림으로 셈) | [코드] |
| H.264 | 인코딩한 프레임은 버리지 않음(순서 큐). 가장 오래된 미확인 프레임의 나이가 150ms(`MAX_H264_BACKLOG_MS`) 이상이거나 미확인이 32장이면 더 안 보냄 | [코드] |
| H.264 인코딩 전 건너뜀 | 가장 오래된 미확인(없으면 아직 못 보낸) 프레임 나이가 150ms 이상이면 캡처한 프레임을 **인코딩하지 않고** 버림(전송 버림으로 셈, Trace `ENCODE_BACKLOG_SKIP`) | [코드] |
| 확인 시간 초과 | 미확인이 있는데 1초(`ACK_TIMEOUT_MS`) 동안 확인이 하나도 없으면 미확인 목록을 비우고 다시 보냄(`ackTimeouts` 증가). 기한은 보낼 때(목록이 비어 있었을 때)와 확인이 올 때마다 미룸 | [코드] |
| 확인이 1초 동안 0개 | 자동 프레임 간격을 매 프레임으로 되돌리고 4초 유예. "링크가 느린 것이 아니라 폰이 읽지 않는 중"으로 봄. **진행 중(22:54 코드)** | [코드] |
| 확인 시간의 뜻 | 보내기 시작 → 확인 도착 = 전송 + 왕복 + 클라이언트 수신 처리. 창 `ack avg/max` | [코드] |

### 1.6 서버 동작 중 앱이 알아야 하는 규칙

- 폰 표시 대기열이 넘칠 때 1장씩 버리던 것 → 최신 1장으로 한 번에 건너뜀.

### 3.3 자동 프레임 간격이 바뀐 과정

자동 프레임 간격 = 전송이나 폰 디코딩이 못 따라갈 때 프레임이 불규칙하게 버려지는 대신 N프레임마다 1번(최대 4) **고르게** 보내는 기능입니다(`TransportStride`). 판정 기준이 다섯 번 바뀌었고, 매번 원인은 "포화가 아닌 상황을 포화로 오인"이었습니다.

### 3.4 탭할 때 끊김 (2026-11-13, **확정되지 않음**)

#### 3.4.1 증상

손을 대지 않으면 고른데 탭(한 번 누르기)만 해도 끊겨 보임. [소유자·개발문서 12.8]

#### 3.4.2 당시의 설명 (120Hz 전환)

폰(Galaxy Z Flip5, 가변 주사율)은 전체 화면 페이지에서 평소 60Hz로 그리다가 터치하면 120Hz로 올라갑니다. 페이지는 프레임을 "디코딩이 끝난 순서대로 다음 화면 갱신에" 그렸고, 수 ms의 도착 · 디코딩 흔들림이 60Hz(16.7ms 칸)에서는 묻히지만 120Hz(8.3ms 칸)에서는 60fps 영상이 8 / 17 / 25ms 간격으로 섞여 그려진다는 설명입니다. [터치보고, 개발문서 12.8]

| 근거 | 값 | 종류 |
|---|---|---|
| rAF 횟수 | 무터치 60회/초 → 탭(1.5초마다) 113회/초, 드래그 114~115회/초. 탭 간격 1.5초 동안 계속 유지 | [측정·터치보고] |
| 고르지 않은 표시 간격(9ms 미만 또는 25ms 초과) | 무터치 0.4%, 탭 16.2%, 드래그 15.9% (표시 일정 끔) | [측정·터치보고] |
| 전체 화면이 아닐 때 | 탭해도 60Hz로 남아 재현되지 않음 | [측정·터치보고] |
| "8 / 17 / 25ms로 섞여 그려진다" | 간격 분포에서 읽은 해석 | [추론·터치보고] |

#### 3.4.3 수정: 표시 일정 (페이지, 기본 켬, `?sched=0`으로 끔)

- 서버가 헤더에 캡처 시각을 넣음(프로토콜 2). [코드]
- 표시 예정 시각 = 캡처 시각 + base + delay. base = 최근 10초 중 가장 빨리 온 프레임의 "디코딩 완료 − 캡처"(두 기기 시계 차이 포함). delay = 최근 120장 흔들림의 95% 지점 + 2ms(처음 16.7ms, 범위 3~25ms). [코드]
- 화면 갱신(rAF)마다 예정 시각이 지난 프레임 중 가장 새 것 1장을 그리고 더 오래된 것은 닫음. 대기열 최대 6장. [코드]
- phase 보정: 예정 시각이 갱신 경계에 걸쳐 한 칸씩 흔들리지 않게 칸 가운데로 맞춤(이득 0.1). 보정이 3/4칸을 넘으면 한 칸 넘김(`gvr.sched.slips`: 60Hz에서는 1장 건너뜀/반복, 120Hz에서는 한 번 8ms 빠르거나 늦음). [코드]
- 주사율은 rAF 간격으로 재므로 프레임이 오는 동안에는 대기열이 비어도 rAF를 이어 감(0.3초). [코드]

전후(Z Flip5, USB adb reverse, H.264 720x1280 6Mbps, 전체 화면, 테스트 패턴 60fps, 각 9.5초, 표시 일정 끔 → 켬): [측정·터치보고]

| 항목 | 무터치 | 탭(1.5초마다) | 드래그(연속) |
|---|---|---|---|
| 고르지 않은 표시 간격 | 0.4% → 0.0% | 16.2% → 1.1% | 15.9% → 0.6% |
| 표시 간격 25ms 초과 | 0.4% → 0.0% | 6.0% → 0.4% | 6.2% → 0.2% |

| 도착 간격 40ms 이상 | 0.2% → 0.2% | 0.0% → 0.2% | 0.0% → 0.2% |
| 표시 fps | 59.7 → 59.8 | 60.1 → 60.0 | 59.9 → 59.9 |
| 그리지 않고 버린 프레임 | 0.4% → 0.2% | 0.4% → 0.2% | 0.4% → 0.2% |

#### 3.4.4 왜 확정되지 않았는가

| 사실 | 종류 |
|---|---|
| 수정 뒤에도 소유자는 "탭하는 순간 화면이 끊긴다"고 봅니다 | [소유자·브리프] |
| 에디터에서 마우스 클릭은 끊기지 않습니다 | [소유자·브리프] |
| **폰을 60Hz 고정으로 바꾸면 더 끊깁니다** | [소유자·브리프] |
| 120Hz 전환이 원인의 전부라면 60Hz 고정에서는 사라지거나 줄어야 합니다. 반대로 나왔으므로 120Hz 설명은 틀렸거나 일부만 맞습니다 | [추론] |
| 60Hz 고정 상태는 누구도 계측하지 않았습니다. 소유자의 눈 관찰뿐입니다 | [터치보고에 해당 측정 없음] |
| 위 표의 측정은 **손가락이 아니라** `adb shell input tap` / `input swipe`로 넣은 터치이고, 게임이 멈춘 화면에서 **테스트 패턴**으로 잰 것입니다 | [측정·터치보고] |
| 게임이 탭에 반응할 때(점프, 효과음) 에디터 프레임이 튀는지는 보지 못했습니다. 에디터 마우스 클릭과의 비교도 하지 않았습니다 | [터치보고 "확인 못 한 것"] |
| 페이지의 "표시 간격"은 `drawImage` 직후의 `performance.now()` 차이입니다. 실제로 패널에 나간 시각이 아닙니다. 계측이 고르게 나와도 눈에 보이는 화면이 고르다는 보장은 없습니다 | [코드: `present` 의 `f.drawnAt`], [추론] |
| 브리프는 원인을 Chrome 쪽 표시 단계(메인 스레드에서 그리기, 주사율 전환)로 **의심**하고 있고, 별도 워커가 진단 중입니다 | [브리프] |
| **(진행 중)** 소유자의 60Hz 고정 시험은 USB가 아니라 **Wi-Fi(무선 adb) 위에서** 돌았습니다. 같은 폰이 USB와 무선으로 동시에 붙어 있어 포트 7300 터널이 무선 쪽으로 넘어가 있었습니다(3.6.3) | [조정자] |
| 그러면 "60Hz 고정이 더 끊긴다"는 관찰에는 주사율 효과와 **무선 구간의 100~290ms 정체**가 섞여 있습니다. 이 관찰만으로는 120Hz 설명을 기각할 수도, 지지할 수도 없습니다. USB로 확실히 고정한 뒤(`reverse --list`가 `UsbFfs`) 60Hz 고정을 다시 봐야 갈립니다 | [추론] |

확정되지 않은 후보(어느 것도 측정으로 갈리지 않음): [추론]

1. Chrome 표시 단계: 터치 이벤트 처리와 2D 캔버스 그리기가 같은 메인 스레드에 있고, 터치 때 합성/주사율이 바뀌는 순간의 프레임 처리.
2. 표시 일정 자체: 고정 60Hz에서는 Unity 약 60.2fps와 패널 60Hz의 차이를 phase 넘김(slip)으로 흡수하는데, 그때 1장이 건너뛰거나 반복됩니다(코드 주석에 적힌 동작). 60Hz 고정에서 더 끊겨 보이는 것과 방향은 맞지만 측정은 없습니다.
3. Unity 쪽: 실제 게임이 터치에 반응하는 프레임의 시간. 주입 자체는 0.03~0.06ms로 쟀지만 게임 반응은 재지 않았습니다. "에디터 마우스 클릭은 안 끊긴다"가 이 후보를 약하게 하지만, 마우스 경로와 터치 경로는 게임 코드에서 다릅니다(`GameManager.cs:1059~1079` 에디터 전용 마우스 경로, 개발문서 6).

| Wi-Fi 직접 접속의 처리량/지연/정체(방화벽에 막혀 사실상 안 씀). 무선 수치는 전부 **무선 adb** 경로 | [개발문서 14-1] |
| 5GHz Wi-Fi | [개발문서 13.4: "예상이며 측정하지 않았습니다"] |
| 실제로 포화된 링크에서의 시간 기준 역압 | [터치보고] |
| `decodeQueueSize` 감시가 실제로 걸리는 상황, 디코딩 오류 → 키프레임 요청 경로(오류가 안 나서) | [터치보고, 개발문서 13.4] |
| 다른 폰(120Hz 전환 조건은 기기와 설정에 따라 다름) | [개발문서 12.8] |
| 1080p 이상(프레임당 약 20~25ms로 **예상**) | [개발문서 14-6] |
| USB 케이블을 뽑은 상태의 무선 adb | [개발문서 14-7] |
| 캡처 시점을 Game 뷰 렌더 직후로 옮기면 줄어드는 지연(약 10ms **추정**) | [터치보고] |
| ffmpeg 출력의 VUI(`bitstream_restriction`, `max_num_reorder_frames`) | [조사] |
| 폰 터치 패널과 디스플레이 자체 지연(터치 → 화면 수치에 포함 안 됨) | [개발문서 8] |

### 3.6 무선 사실 모음 (최종 목표 경로)

최종 목표가 무선이므로 무선에서 실제로 잰 것, 남은 것, 속았던 것을 한곳에 모았습니다. **아래 수치는 전부 "무선 adb 터널 + adb reverse"(PC → 폰 adb 연결 위의 TCP 터널) 경로이고, 앱이 쓸 "LAN 직접 연결"에서 잰 수치는 하나도 없습니다.** 조건: 이 PC/공유기, 폰 SM-F731N, 2.4GHz 802.11n. [개발문서 13, 터치보고]

#### 3.6.1 무선 adb 터널에서 잰 수치

| 항목 | 값 | 출처 |
|---|---|---|
| 링크 | 2.4GHz 802.11n, 링크 속도 104/72Mbps, RSSI −46 | [측정·개발문서 13.1] |
| adb 무선 처리량 | 8.3Mbps (20MB push 20.3초). USB는 176Mbps | [측정·개발문서 13.1] |
| 영상 중 폰 `wlan0` 수신 상한 | 10~15Mbps | [측정·개발문서 13.1] |
| 왕복(입력 소켓) | 7~22ms. USB는 2~6ms | [측정·개발문서 13.1, 진단] |
| MJPEG 100% q10 (720x1280, 64KB/장) | 18.8fps, 10.6Mbps, 폰 디코딩 14.9ms | [측정·개발문서 13.4] |
| MJPEG 50% q40 (360x640, 50KB/장) | 28fps(로비), 12.1Mbps, 디코딩 7.9ms | [측정·개발문서 13.4] |
| H.264 6Mbps 100% 로비 (12KB/장) | 29.6fps(화면 내용 속도), 3.5Mbps, 디코딩 3.8~7.5ms, 터치 → 화면 평균 68ms(15회) | [측정·개발문서 13.4] |
| H.264 6Mbps 100% 계속 점프 | 38.1fps, 4.0Mbps, 디코딩 6.1ms, 터치 → 화면 평균 70ms, p50 65, p90 96(45회). 화면을 보지 않고 탭해 정지 구간이 섞였을 수 있음 | [측정·개발문서 13.4] |
| 서버(H.264) | 인코딩 2.9~5.7ms, 캡처 → 전송 6.3~10ms | [측정·개발문서 13.4] |
| frameId 건너뜀(계속 점프) | 5.7%. 폰 쪽 표시 대기열에서 버려진 것으로 봄(추정, 미확인) | [측정·개발문서 13.4], 해석은 [추론] |
| 인코딩 전 건너뜀(누적) | 39,160캡처 중 434건(1.1%) | [측정·개발문서 13.4] |

왜 MJPEG가 무선에서 안 됐는가: 720x1280 q10도 프레임당 약 50~64KB라 30fps면 약 12~15Mbps로 터널 상한을 넘습니다. H.264는 프레임이 약 12KB라 3.5~4Mbps입니다. [측정·개발문서 13.2]

#### 3.6.2 무선에서 남은 정체 (고쳐지지 않은 것)

표시 일정 끔 → 켬, 같은 폰 · 같은 조건(H.264 720x1280 6Mbps, 전체 화면, 테스트 패턴): [측정·터치보고, 개발문서 12.8]

| 항목 | 무선 adb | 참고: USB |
|---|---|---|
| 고르지 않은 표시 간격, 무터치 | 2.9% → 0.8% | 0.4% → 0.0% |
| 고르지 않은 표시 간격, 탭 | 28.8% → **3.8%** | 16.2% → 1.1% |
| 캡처 → 표시 평균 | 31.5 → 39.1ms / 19.9 → 32.4ms | 35.7 → 28.3ms / 17.2 → 25.0ms |
| 터치 → 표시 평균 | 73.5 → 80.6ms | 54.6 → 61.9ms |
| 전송이 밀리는 순간 | **100~290ms씩**, 도착 지연(도착 − 캡처 초과) 40ms 이상이 1.4~5.9% | 도착 간격 40ms 이상 0.0~0.2% |
| 탭에서 그리지 않고 버린 프레임 | 3.5% → **8.9%**(몰려 온 프레임 중 최신만 그림) | 0.4% → 0.2% |

- 100~290ms 정체는 표시 일정(지터 버퍼 범위 3~25ms)으로 흡수되지 않습니다. 그 순간 화면은 멈췄다가 몰려 온 프레임 중 최신만 그립니다. [측정·터치보고], [코드]
- 정체의 원인(2.4GHz 혼잡, adb 터널의 TCP 재전송, adbd 처리 중 무엇인지)은 **재지 않았습니다**. [터치보고에 해당 측정 없음]
- TCP라서 한 번 밀리면 뒤 프레임이 모두 밀립니다. 조사 보고서는 무선 손실 환경에는 UDP 계열(WebRTC 등)이 가장 안정적이라고 봤지만 `adb reverse`로는 UDP를 못 넘겨 범위 밖으로 뒀습니다. LAN 직접 연결이면 이 제약이 없어집니다. [조사 P11], [추론]
- 무선에서 서버 판정이 틀렸던 것: "수신 확인 간격"을 전송 비용으로 쓰던 때에는 왕복이 프레임 간격보다 긴 무선에서 포화가 아닌데도 30fps와 60fps를 오갔습니다(3.3절 #4). 장 수 기준 역압(미확인 4장)은 왕복이 20ms에서 잠깐 80ms로 튈 때마다 프레임을 불규칙하게 빠뜨렸습니다 → 시간 기준 150ms로 바꿈. [코드 주석, 개발문서 12.8]
- 개발 문서 14-10: "2.4GHz Wi-Fi에서는 지연이 튈 때 고른 30fps로 내려갑니다. 5GHz를 권장합니다." 5GHz는 측정하지 않았습니다. [개발문서 14-10, 13.4]

#### 3.6.3 터널이 말없이 무선으로 넘어가 있었다 (진행 중)

| 사실 | 종류 |
|---|---|
| 같은 폰이 USB와 무선 adb로 **동시에** 붙어 있으면 `adb reverse tcp:7300`을 두 기기 항목에 각각 걸 수 있지만, 폰의 `localhost:7300`은 하나라 **나중에 건 쪽**이 가져갑니다 | [코드 주석: `ReversePreferUsb`] |
| 예전 코드는 Start 때 연결된 기기 모두에 USB → 무선 순서로 걸었습니다. 그래서 케이블이 꽂혀 있어도 영상이 Wi-Fi로 갔습니다 | [코드 주석] |
| 그 상태에서 창과 폰에는 아무 표시가 없었습니다. 폰은 똑같이 `http://localhost:7300/`을 열고, 창은 "준비됨"으로 보였습니다 | [코드: 예전 상태 표시는 reverse 유무만 봄], [추론] |
| **소유자의 60Hz 고정 시험은 이 상태(Wi-Fi 경유)에서 돌았습니다** | [조정자] (진단 워커의 최신 상태, 보고서 미반영) |
| 따라서 "USB에서 60Hz 고정이 더 끊긴다"로 읽었던 관찰은 실제로는 무선 관찰이고, 3.6.2의 100~290ms 정체가 섞였을 수 있습니다 | [추론] |
| 수정(22:54 코드, 진행 중): 무선 기기의 `ro.serialno`가 USB 기기 일련번호와 같으면 그 무선 항목의 reverse를 지우고 USB에만 겁니다. 케이블을 뽑으면 5초 주기 상태 확인이 무선에 다시 겁니다. 창 상태 줄에 "영상 경로: USB/무선"을 표시하고, USB가 있는데 무선으로 가면 경고합니다 | [코드] |
| 이 문서를 쓰는 시점(22:56:29)에도 `R3CW70LJ2VP`(USB)와 `192.168.25.60:5555`(무선)가 함께 붙어 있었습니다. 그 순간 터널이 어느 쪽이었는지는 확인하지 않았습니다(`-s` 없이 실행해 오류) | [이번확인] |
| 터치보고(22:09)의 USB 표는 측정 뒤 "지금은 USB reverse만 있고 무선 연결과 임시 forward는 제거했습니다"라고 적고 있어 그 표는 USB로 봅니다. 다만 측정 **도중** 경로를 `reverse --list`로 확인했다는 기록은 없습니다 | [터치보고], 판단은 [추론] |

진단 워커의 조사는 계속 중입니다. 이 절은 그 워커의 보고서가 나오면 대조해서 고쳐야 합니다.

#### 3.6.4 무선(LAN 직접)에서 아직 아무도 모르는 것

| 모르는 것 | 근거 |
|---|---|
| LAN 직접 TCP의 처리량, 왕복, 정체 분포. 무선 adb의 8.3Mbps 상한이 Wi-Fi의 한계인지 adb 터널의 한계인지 | 링크 속도는 104/72Mbps인데 터널은 8.3Mbps [측정·개발문서 13.1]. 차이의 원인은 재지 않음 |
| 100~290ms 정체가 adb 없이도 생기는가 | 미측정 |
| 5GHz에서의 수치 | 미측정 [개발문서 13.4] |
| 이 PC에서 LAN 직접 접속이 실제로 되는가 | 방화벽에 막혀 있음 [개발문서 14-1] |
| 무선 + 실제 손가락 + 실제 게임 플레이 | 미측정 |
| 무선에서 키프레임 재요청(0.43초 공백)이 얼마나 자주 필요한가 | 디코딩 오류가 난 적이 없어 미확인 [개발문서 13.4] |

## 4. 왜 네이티브 앱을 시작했는가

### 4.1 이유

- 폰에서 탭하는 순간 화면이 끊기는 문제가 서버 · 링크 · 인코더 · 디코더 쪽 측정으로는 설명되지 않았고(3.5), 남은 의심 지점이 **브라우저의 표시 단계**(메인 스레드에서 그리기, 주사율 전환)입니다. [브리프], [측정·진단/터치보고]
- 브라우저 안에서는 그 단계를 더 고칠 수단이 적습니다: 그리기는 메인 스레드의 rAF에 묶여 있고, 주사율은 페이지가 정할 수 없고, 실제 표시 시각을 알 수 없습니다. [추론]
- 네이티브 앱에서는 하드웨어 디코더(MediaCodec)가 Surface에 직접 그리므로 터치 처리와 영상 표시가 분리됩니다. [브리프]
- 소유자 요구: 주소나 포트를 입력하지 않고 QR 한 번으로 설치와 연결. [브리프 2장]

### 4.2 앱이 고칠 것으로 기대하는 것 (전부 기대이며 아직 확인된 것 없음)

| 기대 | 근거 종류 |
|---|---|
| 디코더 출력이 UI 스레드를 거치지 않고 Surface로 감 → 터치 순간 그리기가 밀리는 일이 없어짐 | [추론·브리프] |
| 주사율을 앱이 요청할 수 있음(`Surface.setFrameRate`) → 터치 때 60↔120Hz 전환 문제를 피하거나 고정 | [추론·브리프 3장] |
| 표시 시각을 프레임 단위로 지정하거나 알 수 있음 → 3.4.4의 "그리기 호출 시각 ≠ 실제 표시" 문제 해소 | [추론] |
| WebCodecs의 보안 컨텍스트 제약이 없음 → Wi-Fi 직접 접속에서도 H.264 | [추론] (브라우저 제약은 [코드, 개발문서 13.3]) |
| "탭하면 전체 화면" 단계, 주소창, Chrome 탭 관리가 없어짐 | [추론] |
| QR 연결로 주소 입력이 없어짐 | [브리프] |

### 4.3 앱으로 고쳐지지 않는 것

| 남는 문제 | 이유 | 근거 |
|---|---|---|
| **Unity 터치 주입 경로나 게임 반응에서 생기는 멈칫** | 서버 쪽 일이라 클라이언트를 바꿔도 그대로. 지금까지 실제 게임 반응은 재지 않았음 | [추론], [터치보고] |
| Unity 자체 프레임 튐 | 에디터 프레임이 45~106ms로 튀는 일이 터치와 무관하게 10초에 1번쯤. 에디터 GC는 1번에 50~120ms(힙 1.2~1.3GB, 약 16초에 1번) | [측정·터치보고, 개발문서 12.3] |
| 게임 화면이 실제로 같은 그림인 구간 | 서버가 같은 화면을 안 보냄(8fps 스프라이트 화면 등). 낮은 fps로 보이는 것이 정상 | [측정·터치보고] |
| 무선 구간의 정체 | 무선 adb 2.4GHz에서 전송이 100~290ms 밀리는 순간(도착 지연 40ms 이상 1.4~5.9%). TCP라 한 번 밀리면 뒤 프레임이 모두 밀림. Wi-Fi 직접 접속에서 얼마나 달라지는지는 **모름** | [측정·터치보고], [추론] |
| 키프레임 요청 공백 | ffmpeg 재시작이라 약 0.43초 | [측정·터치보고] |
| 캡처가 "직전 프레임"을 읽는 구조의 지연, 리드백 대기 | 서버 구조 | [코드] |
| H.264 클라이언트 1개 제한, NVIDIA 전용, ffmpeg 필요 | 서버 구조 | [코드, 개발문서 14-9] |
| Windows 방화벽, 인증 없음 | QR 직접 접속은 오히려 이 둘을 **새로 풀어야** 함 | [개발문서 14-1, 14-5] |
| Game 뷰 탭이 가려지면 화면이 멈춤, Unity 창 최소화 | 엔진이 Game 뷰를 그리지 않음 | [개발문서 5, 14-4] |
| 서버 쪽 판정 오류(자동 프레임 간격, 역압) | 앱이 수신 확인과 보고를 다르게 보내면 오히려 새로 생길 수 있음(5장 L3, L4) | [추론] |

### 4.4 조사 보고서가 말한 다른 선택지 (참고)

브라우저를 유지한 채의 선택지는 캡처 시점 이동(약 10ms 추정, Overlay UI 누락 위험), NVENC 네이티브 플러그인(키프레임 0.43초 → 1프레임, 크래시 위험), WebRTC(무선 정체에 가장 효과적이나 `adb reverse`(TCP)로는 불가)였고 모두 범위 밖으로 남았습니다. [터치보고, 조사]

유사 제품에서 앱 설계에 직접 쓸 만한 관찰: [조사]

- Moonlight(안드로이드) "균형(권장)": Choreographer 콜백에서 그리고 최대 1프레임 버퍼링. "최저 지연": 디코딩 즉시 그림(아직 안 나간 이전 프레임은 버림).
- scrcpy 클라이언트: 대기 1장뿐이고 새 프레임이 오면 덮어씀. 지터가 있을 때만 `--video-buffer`.
- 조사한 제품 중 앱 수준의 프레임별 수신 확인으로 전송을 막는 것은 없었습니다. 지금 도구는 수신 확인이 있습니다(1.5.5).
- 인코더 설정(p1, ull, zerolatency, bf 0, CBR, 작은 VBV)은 Sunshine과 거의 같아 우선순위가 낮다는 판단. [추론·조사]

### L0. 무선 함정: 어느 경로로 가고 있는지 모르는 채 재고 판단했다 (상, 진행 중)

| | |
|---|---|
| 증상 | USB 케이블이 꽂혀 있는데도 끊김이 무선 수준으로 보임. 소유자의 60Hz 고정 시험이 "USB에서 더 끊긴다"로 읽혔지만 실제로는 Wi-Fi 위에서 돌았음 [조정자] |
| 원인 | 같은 폰이 USB와 무선 adb로 동시에 붙어 있었고, `adb reverse tcp:7300`이 나중에 걸린 무선 쪽으로 넘어감. 화면 어디에도 표시가 없었음 [코드 주석], [조정자] |
| 어떻게 찾았나 | 진단 워커가 찾음(방법은 보고서에 아직 없음). 코드에는 `reverse --list` 줄 맨 앞으로 경로를 가르는 로직이 들어감 [코드] |
| 빨리 확인 | ① `adb devices -l`에 같은 모델이 두 줄(일련번호 + `IP:5555`)인지 ② `adb -s <serial> reverse --list`의 줄 맨 앞: `UsbFfs` = USB, `host-N` = 무선 ③ 창 상태 줄 "영상 경로" ④ 폰 `wlan0` 수신량이 영상 비트레이트만큼 오르는지 ⑤ `/stats`의 `ackMs`: USB는 평균 4~6ms대, 무선은 왕복만 7~22ms |
| 앱에서 | 측정 결과마다 **경로(USB adb / 무선 adb / LAN 직접, 2.4/5GHz)를 같이 기록**합니다. 앱 HUD에 지금 붙은 서버 주소(127.0.0.1이면 adb 터널)를 표시합니다. 앱이 "LAN 직접 실패 시 adb reverse로 대체"를 하면 같은 종류의 말없는 경로 전환이 다시 생기므로, 대체했을 때 화면에 드러나야 합니다 [추론] |

### L0-2. 무선 함정: 무선 adb 수치를 Wi-Fi의 수치로 읽으면 안 된다 (상)

| | |
|---|---|
| 사실 | 지금 있는 무선 수치(8.3Mbps, 100~290ms 정체, 터치 → 표시 80.6ms)는 전부 무선 adb 터널 경로. 링크 속도는 104/72Mbps였음 [측정·개발문서 13.1, 터치보고] |
| 함정 | 이 수치로 "Wi-Fi는 6Mbps가 한계", "지터 버퍼는 300ms가 필요" 같은 설계 결정을 하면 근거가 없음. 반대로 "LAN 직접이면 다 해결"도 근거가 없음 [추론] |
| 빨리 확인 | 앱 시제품의 첫 측정 항목으로 LAN 직접 TCP에서 3.6.2 표와 같은 지표(도착 지연 40ms 이상 비율, 최대 정체, 터치 → 표시)를 같은 폰 · 같은 공유기로 잽니다. 무선 adb 수치와 나란히 놓으면 정체가 Wi-Fi 탓인지 터널 탓인지 갈립니다 [추론] |
| 서버 쪽 주의 | 서버의 역압(150ms)과 자동 프레임 간격(확인 평균 100ms 초과, 버림 10% 초과)은 무선의 정체에 반응해 fps를 내립니다. 무선에서 끊겨 보이면 창 `Pacing`의 `every k frame`과 Editor.log `auto pacing`부터 봅니다 [코드] |

### L1. 메시지를 여러 번에 나눠 쓰면 adb 구간에서 40ms씩 묶인다 (상)

| | |
|---|---|
| 증상 | Unity는 60fps로 고르게 보내는데 폰 표시가 45~58fps. 도착 간격이 약 16ms와 약 55ms 두 값으로 갈리고, 정체 뒤 2~3장이 6ms 안에 몰려 옴 [측정·진단] |
| 원인 | WebSocket 메시지 1개를 소켓 쓰기 3번으로 보냄 + `NoDelay` [측정·진단]. 폰 안쪽 기전은 [추론] |
| 어떻게 찾았나 | 폰 DevTools로 도착 간격 분포를 봄 → 별도 포트에서 "쓰기 3번 대 1번" A/B(6.5절) |
| 빨리 확인 | 창 `ack max`가 45ms 근처인지(정상은 20ms 아래), `/stats`의 `snapshot.ackMaxMs`. 폰 쪽 도착 간격이 두 봉우리인지. 3ms 안에 몰려 온 프레임 수 |
| 앱에서 | 앱이 보내는 쪽(입력, 수신 확인)도 메시지 1개 = 쓰기 1번이어야 합니다. WebSocket 라이브러리가 헤더와 내용을 따로 쓰는지 확인. USB/adb reverse를 대체 경로로 남기면 그대로 해당. Wi-Fi 직접 접속에서 같은 현상이 나는지는 재지 않았습니다 [추론] |

### L2. 화면 표시 문제는 스크린샷 · 녹화 · 에뮬레이터로 검증되지 않는다 (상)

| 어떻게 찾았나 | 서버와 폰 양쪽 프레임 검사 카운터가 모두 0 → 데이터가 아니라 표시 단계로 좁힘 → `?desync=1` A/B + 소유자 눈 확인 |

### L3. "못 따라간다"는 판정이 다섯 번 틀렸다 (상)

### L4. 수신 확인 규칙을 어기면 영상이 멈춘다 (상)

| | |
|---|---|
| 증상 | 영상이 1초마다 조금씩만 오거나, 150ms 분량 뒤 멈춤 |
| 원인 | 확인이 없으면 MJPEG는 2장, H.264는 "가장 오래된 미확인 150ms" 또는 32장에서 전송 중단. 1초 뒤 목록을 비우고 다시 보냄 [코드] |
| 어떻게 찾았나 | 스크립트 클라이언트로 확인을 1.5초 멈춰 봄: 약 150ms 분량 뒤 전송 정지, 72장 인코딩 전 건너뜀 [측정·터치보고] |

### L5. frameId 건너뜀을 잘못 읽었다 (상)

| | |
|---|---|
| 증상 | 무선 측정에서 frameId 건너뜀 5.7%를 "인코딩 전 건너뜀"이라고 적었다가 정정 |
| 원인 | H.264의 frameId는 **ffmpeg 출력 때** 매기므로 인코딩 전 건너뜀은 frameId 건너뜀으로 나타나지 않음. 서버는 인코딩한 H.264 프레임을 버리지 않으니 그 건너뜀은 폰 쪽에서 버린 것(추정, 미확인) [개발문서 13.4] |
| 빨리 확인 | 서버 쪽 버림은 `/stats`의 `encodes`(kind 2), `sendDrops`. 클라이언트 쪽 버림은 클라이언트 카운터(페이지는 `gvr.superseded`) |
| 앱에서 | 설정(avcC) 메시지도 frameId를 하나 씁니다. 인코더가 재시작될 때마다 영상 프레임의 frameId가 1 건너뛰는 것은 손실이 아닙니다. 앱이 "받은 frameId가 연속인가"로 손실을 세려면 설정 메시지를 포함해 세야 합니다 [코드] |

### L6. "끊김"의 일부는 게임이 같은 그림을 그린 것이었다 (상)

| | |
|---|---|
| 증상 | 소켓 수정 뒤에도 33~50ms 간격이 남음 |
| 원인 | 그 프레임들은 Game 뷰가 다시 그려졌는데 그림이 같아서 서버가 안 보냄(8fps 스프라이트 화면: 480장 중 415장 동일) [측정·터치보고] |

### L9. 프로토콜/형식 가정 (상)

| 함정 | 내용 | 근거 |
|---|---|---|
| H.264는 Annex B가 아님 | 내용은 AVCC(길이 4바이트 + NAL), 설정은 avcC. 브리프 3장의 "H.264 Annex B"는 지금 구현과 다릅니다. MediaCodec에 넣으려면 변환(avcC → SPS/PPS, 길이 → 시작 코드)을 앱에서 하거나 서버가 다른 형식을 내야 합니다 | [코드], 변환 필요성은 [추론] |
| `caps`는 문자열 검사 | `{"t":"caps","h264":1}`을 공백 없이 그대로 보내야 함. JSON 라이브러리가 `"h264": 1`이나 `1.0`으로 내면 MJPEG가 옴 | [코드] |
| 프로토콜 번호 | `hello`의 `v`가 앱이 아는 번호와 다르면 헤더 해석이 틀립니다(24B ↔ 28B). 페이지는 새로 고침으로 해결하지만 앱은 그럴 수 없으니 명확한 오류가 필요 | [코드], [추론] |
| 클라이언트 → 서버 메시지 64KB 제한 | 넘으면 서버가 연결을 닫음 | [코드] |
| 영상 클라이언트 2개 = MJPEG | 1.6절 | [코드] |
| 행 순서 | 처음 H.264 구현에서 화면이 위아래로 뒤집힘(Unity JPEG는 맨 아래 행부터, ffmpeg rawvideo는 맨 위 행부터). 서버에서 해결됨 | [개발문서 13.3] |
| 타임스탬프 | 페이지는 디코더 타임스탬프로 frameId를 써서 출력과 메타를 짝 맞춤. 앱도 프레임 메타(캡처 시각, inputSeq)를 디코더 출력과 짝 맞출 키가 필요 | [코드], [추론] |
| 프레임 크기 상한 | `-bufsize`가 비트레이트/30이라 6Mbps에서 프레임이 약 12.5KB로 묶임(측정 p50 12525B). 키프레임도 같은 틀 안 → 화질 문제일 수는 있어도 끊김 원인은 아님 | [측정·진단] |

### L10. 연결과 adb (중)

### 6.2 `/stats` (JSON)와 `/debug`

서버가 127.0.0.1에 묶여 있으므로 PC에서:

```powershell
# 1초 통계 + 누적 + 최근 프레임 기록 (읽기 전용, 영상 클라이언트로 세지 않음)
Invoke-WebRequest -Uri "http://127.0.0.1:7300/stats" -UseBasicParsing | Select-Object -ExpandProperty Content

# 테스트 패턴 켜기 / 끄기 (화면에 네모가 생기므로 다른 사람이 측정 중이면 하지 않음)
Invoke-WebRequest -Uri "http://127.0.0.1:7300/debug?pattern=1" -UseBasicParsing
Invoke-WebRequest -Uri "http://127.0.0.1:7300/debug?pattern=0" -UseBasicParsing
```

응답 구조: [코드: `GameViewRemoteTrace.BuildJson`, `GameViewRemote.BuildStatsJson`]

| 키 | 내용 |
|---|---|
| `nowMs` | 서버 Start 뒤 흐른 시간(헤더 캡처 시각과 같은 시계) |
| `pointerMessagesReceived` / `pointerEventsApplied` | 받은 포인터 메시지 수 / 메인 스레드가 꺼낸 이벤트 수(연결 끊김 표시 포함) |
| `snapshot` | 창의 1초 통계 전부(`unityFps`, `sentFps`, `kbps`, `avgFrameKb`, `encodeMs`, `captureToSendMs`, `readbackMs`, `readbackWaitMs`, `readbackMaxWaitMs`, `injectLatencyMs`, `injectLatencyFrames`, `width`, `height`, `skippedIdentical`, `captureFps`, `inflightSkips`, `encoderDrops`, `sendDrops`, `ackMs`, `ackMaxMs`, `ackCount`, `sendCostMs`, `ackTimeouts`, `bufferAllocs`, `gcCount`, `unityFrameMaxMs`, `unityHitches`, `sendGapMaxMs`, `captureStride`, `clientDecodeMs`, `clientDrops`, `transportStride`) |
| `extra` | `codec`, `transportStride`, 누적 `captures`, `encoderDrops`, `inflightSkips`, `noRenderCaptures`, `guardedFrames` |
| `frames` | 최근 2048개 Unity 프레임(60fps면 약 34초). 행 = `[frame, timeMs, deltaMs, capture, renders, screenRenders, fingers, pointerEvents, captureMs, injectMs, readbackWaitMs]` |
| `encodes` | 최근 2048개 인코딩 결정. 행 = `[captureFrame, timeMs, kind]` |

- `capture` 값: 0 = 영상 클라이언트 없음, 1 = 요청함, 2 = 간격 때문에 건너뜀, 3 = 리드백 3개가 차서 건너뜀, 4 = 렌더 타깃 없음. [코드]
- `kind` 값: 0 = H.264 인코딩, 1 = 같은 화면이라 건너뜀, 2 = 밀려서 인코딩 전 건너뜀, 3 = JPEG, 4 = 안전장치로 안 보냄. [코드]
- 쓰는 법: 클라이언트에서 간격이 벌어진 시각을 캡처 시각(헤더 `captureTime`)으로 바꿔 `frames`의 `timeMs`와 맞춰 보고, 그 프레임의 `deltaMs`(Unity가 튐), `capture`(캡처 안 함), `encodes`의 kind(같은 화면/밀림)를 봅니다. `fingers`와 `pointerEvents`로 터치가 있던 프레임인지도 보입니다. [코드], [터치보고에서 쓴 방식]

이번확인(22:56:29, 1회 읽기, 다른 워커의 세션이 도는 중): 응답 200, 134153바이트, `frames` 2048개, `encodes` 2048개. `snapshot`: unityFps 57.9, sentFps 57.9, 5807kbps, 프레임 12.2KB, 인코딩 5.9ms, 캡처→전송 10.5ms, ackMs 6.0 / ackMaxMs 49.0, ackCount 58, unityFrameMaxMs 62.4, unityHitches 1, gcCount 1, sendGapMaxMs 59.9, clientDecodeMs 3.1, transportStride 1. `extra.codec` = `H.264 (NVENC) 6.0 Mbps, 720x1280`. 이 한 번의 표본에서 Unity 프레임 튐 1회(62ms)와 GC 1회가 같은 1초에 있었고 전송 간격 최대도 그만큼 벌어졌습니다(인과는 확인하지 않음). 보고서에 쓰인 지표의 계산: [터치보고, 진단, 코드]

| 지표 | 계산 |
|---|---|
| 도착 간격 | 연속 프레임의 `recvAt` 차이. "40ms 이상" 비율과 "3ms(또는 6ms) 안에 몰려 온 수" |

| 주의 | `drawnAt`은 그리기 호출 직후 시각이고 실제 패널 표시 시각이 아님 |

## 8. 조정자가 알아야 할 것 (이 문서를 쓰며 찾은 것)

1. **H.264는 Annex B가 아니라 AVCC + avcC입니다.** 브리프 3장 "전송" 질문의 전제("지금의 WebSocket(TCP) + H.264 Annex B")가 코드와 다릅니다. 앱에서 변환할지, 서버가 앱용 형식을 낼지 설계에서 정해야 합니다. [코드]
2. **영상 클라이언트가 2개면 둘 다 MJPEG**로 떨어집니다. 브리프 4장은 다른 워커의 Chrome 세션(포트 7300)을 건드리지 말라고 하므로, 앱 시험은 다른 포트의 서버가 필요하고, 같은 서버에 붙는 공존 방식은 설계에서 정해야 합니다. [코드]
3. **탭 끊김의 원인이 확정되지 않았습니다.** 앱이 그 문제를 고친다는 것은 기대입니다. 원인이 Unity 쪽(게임 반응, 주입 경로)이면 앱에서도 남습니다. 앱 시험 계획에 "같은 조건에서 Chrome 페이지와 앱을 비교"와 "`/stats`로 그 순간의 Unity 프레임 시간 확인"을 넣는 것을 권합니다. [추론]
4. **Unity 도구 폴더가 지금도 바뀌고 있고 git에 없습니다.** 이 문서의 프로토콜 절은 22:55~22:56 시점입니다. 6단계(Unity 쪽 구현) 전에 다시 읽어 대조해야 합니다. [이번확인]
5. 서버의 `caps`/`key`/수신 확인 판정이 문자열 검사라 앱이 보내는 텍스트 형식에 민감합니다(1.5.4). 앱용으로 서버를 고칠 때 함께 정리할 후보입니다. [코드]
6. 같은 폰이 지금 USB와 무선 adb로 동시에 잡혀 있습니다. 앱 설치와 시험에서 adb 명령에 `-s R3CW70LJ2VP`를 붙이지 않으면 실패합니다. [이번확인]
7. **무선(LAN 직접) 수치는 아직 없습니다.** 기존 무선 수치는 전부 무선 adb 터널에서 잰 것이라 요구사항 11의 합격 기준을 정할 근거로는 부족합니다. PRD의 무선 기준은 "잠정"으로 두고 앱 시제품의 첫 LAN 직접 측정으로 고치는 것을 권합니다. [추론]
8. 3.6.3(터널이 무선으로 넘어가 있었고 60Hz 시험이 Wi-Fi에서 돌았다)은 조정자 메시지에만 근거합니다. 진단 워커의 보고서가 나오면 이 문서의 3.4.4, 3.6.3, L0을 대조해 고쳐야 합니다. [조정자]

이 문서를 쓰며 한 것: 파일 읽기, `adb devices -l` 1회, `-s` 없는 `adb reverse --list` 1회(오류로 끝남, 아무것도 바꾸지 않음), `GET http://127.0.0.1:7300/stats` 1회. 폰 화면, 터널, Unity 상태는 건드리지 않았습니다. Editor.log, 하네스 스크립트 내용, `game-view-remote-plan.md` / `phase1-result.md` / `phase2-result.md`(개발 문서가 근거로 드는 문서, 위치를 찾지 않음)는 읽지 않았습니다.

### A2. 가상 기기의 NAT 가 바이트를 잃는다 [확인]

| | |
|---|---|
| 증상 | 가상 기기에서 PC 의 LAN 주소(`192.168.25.5`)나 `10.0.2.2` 로 받으면 3.5MB 앱 파일이 5~20바이트 모자라 내려받기가 끝나지 않음. 6.5KB 페이지도 절반쯤은 1바이트가 빠져 빈 화면이 됨 |
| 원인 | 에뮬레이터의 사용자 모드 네트워크(NAT). 제품의 문제가 아님 |
| 어떻게 찾았나 | ① PC 에서 같은 주소로 받으면 매번 온전(sha256 일치) ② **Unity 가 아닌 node 로 같은 파일을 내줘도 똑같이 모자람** ③ `adb reverse`(127.0.0.1)로 받으면 매번 온전 ④ 받은 것과 원본을 맞춰 보니 중간중간 1바이트씩 빠짐 |
| 빨리 확인 | 기기에서 `(printf 'GET /apk HTTP/1.1\r\nHost: x\r\n\r\n'; sleep 3) \| toybox nc -w 5 <주소> 7300 \| wc -c` 를 몇 번 돌려 크기가 같은지 본다. `nc` 는 입력이 끝나면 바로 닫으므로 `sleep` 으로 붙들어야 한다(처음에 이것 때문에 0바이트가 나와 헷갈렸다) |
| 대가 | 서버가 소켓을 너무 빨리 닫는다고 잘못 짚어 서버 코드를 고쳤다가 컴파일 오류를 냈다(되돌림). **대조군(node)을 먼저 돌렸어야 했다** |
| 돌아가는 길 | 손실 없이 LAN 쪽 서버를 시험하려면 `tools\device-lab\lan-relay.js` + `adb reverse tcp:7320 tcp:7320`. 영상은 NAT 로도 재생되지만 큰 파일은 안 된다 |

### A3. adb: 버전, 일련번호, 터널

| | |
|---|---|
| 증상 | (가) 기본 대상이 실제 폰인 스크립트 (나) adb 를 섞어 쓰면 서버가 다시 뜰까 걱정 (다) 재부팅 뒤 `adb reverse` 가 목록에는 있는데 통하지 않음 (라) 딥링크가 앱에 안 읽힘 (마) Git Bash 에서 경로가 바뀜 |
| 원인 | (가) `tools/env.sh` 의 기본 일련번호가 폰이었음 (나) Unity 의 adb(32.0.0)와 SDK 의 adb(35.0.2)는 서버 프로토콜이 같아(1.0.41) 섞여도 서버가 다시 뜨지 않음. 버전이 다르면 서버를 죽이고 다시 띄워 모든 연결이 끊긴다 (다) reverse 는 기기 재부팅에 사라짐 (라) `adb shell "am start -d '…&…'"` 에서 `&` 앞에 역슬래시를 붙이면 작은따옴표 안이라 그대로 들어감 (마) MSYS 가 `/sdcard/…` 를 Windows 경로로 바꿈 |
| 빨리 확인 | 항상 `-s emulator-5554`. `adb devices` 로 대상이 하나인지. `adb -s … reverse --list`. Git Bash 는 `MSYS_NO_PATHCONV=1`. `adb kill-server`, `start-server`, `connect` 는 쓰지 않는다 |
| 고친 것 | `env.sh` 는 `emulator-*` 가 아닌 일련번호를 거부. Unity 의 앱용 adb 도우미는 가상 기기 전용이고 대상이 둘이면 멈춤 |
| 알아 둘 것 | `adb reverse` 는 PC 의 127.0.0.1 로만 간다. 그래서 그 길은 "USB 경로"이고 QR(LAN) 경로와 다른 접수 창구를 탄다. 기존 도구는 Play 중에 꽂힌 폰에 reverse 를 걸고 저장된 무선 주소로 `adb connect` 를 시도한다(폰을 쓰지 말라는 지시와 부딪혀 주소를 백업 키로 옮김) |

### A5. 설치 직후 첫 실행에서만 화면이 안 나왔다 [확인]

| | |
|---|---|
| 증상 | 연결, 인증, 디코더 생성까지 되고 "연결됨. 화면을 기다리는 중"에서 멈춤. 앱을 껐다 켜면 됨. 로그에 `key request: backlog` 가 11초마다 |
| 원인 | Kotlin 은 선언 순서대로 초기화한다. 화면 박자 루프를 시작하는 `init` 블록이 `running = true` 선언보다 앞에 있어, 생성자가 느린 첫 실행에서는 박자 스레드가 `running == false` 를 보고 시작하지 않음 |
| 어떻게 찾았나 | 처음에는 A2(바이트 손실) 탓으로 봤다. "되는 실행"과 "안 되는 실행"을 나열하니 주소가 아니라 **설치 직후인지**로 갈림. 다시 설치해 3번 재현한 뒤 코드에서 순서를 찾음 |
| 빨리 확인 | `adb uninstall` → `install` → 첫 실행을 시험에 넣는다. 두 번째 실행부터 되는 결함은 개발 중에는 안 보인다 |

### A6. 상태 안내가 영상을 가린 채 남았다

| | |
|---|---|
| 증상 | 자리를 되찾았는데 "화면을 기다리는 중" 안내가 계속 영상 위에 있음 |
| 원인 | "첫 프레임을 내보냈다"는 알림이 디코더당 한 번만 나감. 같은 디코더를 이어 쓰면 다시 오지 않음 |
| 고친 것 | 세션이 기다리는 상태에 들어갈 때마다 "다음 프레임에서 알려 달라"고 건다 |
| 빨리 확인 | `hosttest.js withapp`: 앱이 보는 중에 페이지가 자리를 가져갔다가 앱이 [여기서 보기]. 로그가 `STANDBY → WAITING → PLAYING` 인지 |

### A7. 닫을 때 닫기 코드가 사라졌다

| | |
|---|---|
| 증상 | 서버가 거절하며 4401 을 보냈는데 클라이언트는 코드 없이 끊김으로 받음. 4번 중 3번 |
| 원인 | 상대가 보낸 데이터를 다 읽지 않은 채 소켓을 닫으면 Windows 가 정상 종료 대신 RST 를 보내고, 앞서 보낸 닫기 프레임이 버려짐 |
| 고친 것 | 닫기 프레임 → 보내는 쪽만 닫기 → 남은 입력을 잠깐 읽어 버림 |
| 빨리 확인 | `hosttest.js abuse` 를 3번 연속 |

### A8. Unity 에디터에서 알아 둘 것

| | |
|---|---|
| 컴파일 오류가 조용하다 | 스크립트에 오류가 있으면 Unity 는 **이전에 컴파일된 코드로 계속 돈다.** 서버가 멀쩡히 응답해서 고친 것이 들어간 줄 알았다. `EditorUtility.scriptCompilationFailed` 와 콘솔의 `error CS` 를 고칠 때마다 본다 |
| Play 중 리로드 | Play 중에 스크립트를 다시 불러오면 도구는 견디지만 게임 스크립트(`BattlePassManager`, `TimeManager`)가 매 프레임 오류를 낸다. Play 를 다시 시작하면 없어진다. 도구의 오류와 섞어 보지 않게 `[GVR]` 로 거른다 |
| 이름 충돌 | Editor 스크립트에서 `SelectMode` 는 `System.Net.Sockets` 것과 `UnityEditor` 것이 겹친다 |
| 버튼을 누르지 못한다 | 원격 도구로는 IMGUI 창의 버튼을 누를 수 없어 버튼이 부르는 함수를 직접 불렀다. 창의 글자와 배치는 사람 눈이 필요하다 |
| 가상 기기 재부팅 직후 | 앱의 LAN 연결이 `ENETUNREACH`. 가상 Wi-Fi 의 경로가 비어 있었고 Wi-Fi 를 껐다 켜니 됨 |

### A9. 시험 자동화의 작은 함정

| | |
|---|---|
| 글자로 눌렀더니 다른 곳 | `uiautomator dump` 에서 "연결", "취소", "Settings" 를 찾으면 버튼보다 본문 글자가 먼저 걸린다. 버튼은 좌표나 `Button` 종류로 고른다 |
| 확인 창 | 앱이 PC 를 기억한 뒤에는 브라우저에서 온 링크에 "연결할까요?" 를 묻는다. 자동 시험은 이 창의 [연결]을 눌러야 넘어간다. 깨끗한 상태가 필요하면 `pm clear` |
| Chrome 의 경고 | http 주소의 앱 파일은 "안전하게 다운로드할 수 없음" 과 "유해할 수 있는 파일" 두 번을 넘겨야 받는다. Play 프로텍트의 "앱 검사"는 앱 파일을 Google 로 보내므로 "검사 없이 설치"를 고른다 |
| 진단 입구 | 진단 값과 `--es t` 는 `kr.co.seeplay.gvr/.Diag` 로 보낸 인텐트만 받는다. 패키지 이름만 준 `am start` 는 "밖에서 온 링크"다 |
| 문서의 시각 | 작업자마다 적은 시각이 PC 시계와 10분~1시간 어긋났다. 순서의 근거는 파일 수정 시각과 로그로 삼는다 |
| 스크립트로 파일 고치기 | Bash 의 여기 문서로 Python 을 넘기면 `\b`, `\t`, `\a` 가 제어 문자가 된다. 역슬래시가 든 내용은 파일로 써서 읽는다 |
