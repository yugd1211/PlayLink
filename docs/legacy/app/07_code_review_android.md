## 2. 차단 결함

### B1. 자리를 되찾거나 H.264 가 다시 올 때 상태가 WAITING/NOCODEC 에 고정됩니다 [정적]

- 위치: `video/Decoder.kt:143`(`if (!firstReleased) { … host.onFirstFrameReleased() }`), `Decoder.kt:280`(`firstReleased = false` 는 디코더를 **새로 만들 때만**), `Decoder.kt:300~301`(같은 크기의 설정 메시지는 디코더를 유지), `session/Session.kt:345`(`seat active` → `WAITING`), `Session.kt:381`(`NOCODEC` 진입), `Session.kt:409`.
- 왜: `PLAYING` 으로 가는 유일한 길이 "디코더를 만든 뒤 첫 프레임"입니다. 그런데 자리가 `standby` → `active` 로 돌아오면 서버는 인코더를 다시 시작해 **같은 크기의** 설정 + 키프레임을 보내고, 앱은 디코더를 유지합니다. `firstReleased` 가 이미 `true` 라 콜백이 다시 오지 않습니다.
- 실패 장면 1(자리): 폰 A 가 재생 중 → 다른 기기가 자리를 가져감(`STANDBY`) → A 에서 [여기서 보기] → 서버가 `seat active` → 앱은 `WAITING`("연결됨. 화면을 기다리는 중") → 영상은 다시 나오지만 **문구 패널(반투명 검정)이 영상 위에 계속 남고**, Wi-Fi 저지연 잠금도 다시 잡히지 않습니다(`MainActivity.kt:244, 252`). 앱을 뒤로 보냈다 돌아와야 풀립니다.
- 실패 장면 2(MJPEG): 재생 중 Chrome 탭이 같이 붙어 서버가 2초 넘게 JPEG 를 보냄 → `NOCODEC` → Chrome 탭이 떠나 H.264 가 다시 옴 → 같은 이유로 "PC가 H.264 를 보내지 않습니다…" 문구가 영상 위에 남습니다. 05 문서가 확인한 것은 "처음부터 JPEG" 인 경우뿐입니다.
- 고칠 것: "첫 프레임" 통지를 디코더 생성이 아니라 **세션 상태에 묶습니다**. 예: `Decoder` 에 `@Volatile var notifyNextRelease`, `Session.setState` 가 `WAITING`/`NOCODEC` 에 들어갈 때 `true` 로 두고 `release()` 가 `true` 면 통지 후 `false`. 재현 시험: `replay.js --auth` 에 `/ctl?standby=1` → `/ctl?active=1`(이미 있음) 뒤 상태가 `PLAYING` 인지.

## 3. 주요 결함

### M1. 표시 일정(Pacer): v3 의 "간격 지키기"는 지연 13ms 와 제때 온 프레임 버리기로 값을 치릅니다 [확인: 기록 재분석]

위치: `Decoder.kt:104~134`(vsync 콜백의 결정), `Decoder.kt:154~183`(`computeDue`).

**(1) 기록에서 나온 사실** (`tools/rec/…005428-w2_tap1.json` = 05 문서의 "탭 4", v3 최종, 39초)

| 항목 | v2 (`w_tap1`) | v3 (`w2_tap1`) |
|---|---|---|
| 넘긴 시각 − `due` 중앙값 / p90 | 0.8 / 4.9 ms | **13.6 / 19.3 ms** |
| 건너뛴 프레임 중 **제때 디코딩됐는데 버린 것** | 0 / 22 | **16 / 22** |

- 05 문서 4.4 의 3번은 건너뜀을 "늦게 온 프레임 뒤에 따라잡으면서 버리는 것"이라고 적었지만 v3 에서는 22장 중 16장이 **제때 온 프레임**입니다. 무터치 구간(`w2_idle1`)도 30장 중 19장이 그렇습니다.
- 원인: `Decoder.kt:124` 의 미루기 조건(`spacing < want − 주기/2` 이고 밀림이 1.5주기 미만이면 한 vsync 미룸)이 **늦은 프레임 한 장 뒤의 따라잡기를 막습니다.** 그 뒤 모든 프레임이 원본 간격(16.7ms)대로 한 칸씩 늦게 나가 `due + 13~19ms` 에 머뭅니다. 버리는 문턱은 `Decoder.kt:128`(`다음 프레임의 due ≤ vsync − 주기/2` = 120Hz 에서 `due + 20.9ms`)이라 **평소 위치가 문턱 바로 앞**입니다. 작은 흔들림 한 번이면 멀쩡한 프레임을 버립니다.
- 05 문서가 적은 "v3 에서 터치 → 표시가 약 10ms 늘어남"의 정체가 이것입니다. 일시적인 것이 아니라 정상 상태의 위치입니다.
- 60Hz(무터치)에서는 v2·v3 모두 `넘긴 시각 − due` 중앙값이 14~17ms 입니다. 늦은 프레임 한 장 뒤로 **전부 한 vsync 늦게** 나가고, 돌아오는 길이 "버리기"뿐이기 때문입니다(`Decoder.kt:126~130`).
- `auto` 지연 목표가 p95 + 2ms 라(`Decoder.kt:176`) 설계상 프레임의 5%(초당 3장)가 `due` 보다 늦게 준비됩니다. 기록에서도 3.7~5.1% 입니다. 이 프레임 하나하나가 멈춘 갱신 후보입니다.
- `due` 자체가 계단으로 움직입니다: 지연 목표를 30장마다 한 번에 바꾸고(`Decoder.kt:172`), 기준값은 5초마다 창을 통째로 갈아(`Decoder.kt:157~159`) 0.5ms 넘는 계단이 초당 1.3~1.7번, 2ms 넘는 계단이 구간당 11~24번 있습니다. 120Hz(8.35ms 칸)에서 계단 한 번은 칸 넘김 한 번이 될 수 있습니다.
- 120Hz 에서 지표의 문턱(+8ms)이 한 칸(8.35ms)보다 0.35ms 작아서 **한 칸 밀림 = 멈춘 갱신 1회**로 세어집니다. 앱과 페이지에 똑같이 적용되지만, 작은 차이가 수치로 크게 보이는 이유입니다.

**(2) 웹 페이지와 무엇이 다른가** (`GameViewRemotePage.html` `schedTake`, 읽기만 함)

페이지는 `due + phase ≤ t` 인 것 중 가장 새 것을 내고, 낼 때마다 `phase += 0.1 × (r − 주기/2)` 로 **`due` 가 vsync 사이 한가운데에 오도록 위상을 맞춥니다**(±0.75주기에서 한 칸 넘김). 경계 근처에서 8/25ms 로 오가는 것을 이 위상 고정이 막습니다. 앱에는 위상 고정이 없고, v3 의 미루기 규칙이 그 자리를 대신하면서 위의 부작용을 냅니다. 지연 목표도 페이지는 3~25ms 로 자르고 10장마다 갱신, 기준값은 10초 미끄럼 최솟값입니다.

읽는 법:

- 깨끗한 입력(USB)에서는 페이지 규칙이 v3 와 같은 멈춘 갱신을 **9ms 적은 지연**으로 냅니다. v3 의 미루기는 필요 없습니다.

**(4) 넘긴 뒤의 지연이 지표에 보이지 않습니다** [확인: 기록 / 가설: 실제 화면]

`Decoder.kt:83` 은 표시 목표 시각으로 `preferredFrameTimeline.expectedPresentationTimeNanos` 를 씁니다. 기록에서 `target − release` 는 120Hz 에서 15.8ms, **60Hz 에서 32.2~32.5ms**(둘 다 2주기)입니다. 이 값은 "앱이 뷰를 그려 합성기에 넘기는" 길의 예정 시각이라 디코더 버퍼를 곧바로 넘기는 경우에는 한 주기쯤 남습니다. 그런데 견주는 지표가 전부 `releaseNs` 기준이라(설계 8.2, B1 결정) **이 16~33ms 는 터치 → 표시, 캡처 → 표시 어디에도 들어가지 않습니다.** 앱의 실제 지연은 05 문서의 74.5ms 보다 이만큼 클 수 있고, 한 주기는 줄일 수 있을 가능성이 큽니다. 실제 화면 시각의 독립 근거가 없다는 05 문서의 한계(4.1)와 같은 문제라 기기 측정이 필요합니다.

**고칠 것(구체안)**

1. `Decoder.kt:118~125` 의 미루기 규칙을 지우고 페이지와 **같은 규칙**으로 바꿉니다: 후보 = `due + phase ≤ frameTimeNs`, 가장 새 것을 내고 그보다 오래된 후보는 버림, 낸 뒤 `r = frameTimeNs − (due + phase)` 가 한 주기 안이면 `phase += 0.1 × (r − 주기/2)`, `|phase| > 0.75 주기` 면 한 주기 넘김. 주기는 15개 중앙값 대신 지수 평균(0.1)으로. 비교 대상과 규칙이 같아야 남는 차이를 경로 탓으로 말할 수 있습니다.
2. 지연 목표를 계단 없이: 기준값은 페이지처럼 미끄럼 최솟값(단조 덱, 10초), 지연 목표는 10장마다 다시 계산하되 프레임당 0.25ms 이하로만 움직이게 하고 3~25ms 로 자릅니다. 목표 백분위(`p95`)는 설정으로 빼서 무선에서 p99 를 재 봅니다.

### M3. 주사율: 60 을 글자로 박았고, "30Hz 로 내려감"의 원인이 가려지지 않았습니다 [정적 + 가설]

- 위치: `MainActivity.kt:350~369`(특히 `:364` `if (settings.rr == "match") 60f`), `Decoder.kt:81~91, 132`, `diag/Diag.kt:11`.
- 사실 [확인: `…003649-t_idle.json`]: `rr=none` 기록에서 `Display.getRefreshRate()` 는 120 → 60 → 48 → 30 으로 단계적으로 내려갔고 콜백 간격은 33.3ms, 받은 862장 중 565장만 넘겼습니다.
- 가려지지 않은 것: (1) 앱이 기록하는 두 값(`Display.getRefreshRate()`, `Choreographer` 콜백 간격)은 **둘 다 앱에 걸린 프레임률 제한을 반영하는 값**이라, 패널이 실제로 30Hz 였는지 앱의 콜백만 30Hz 로 줄었는지 구분하지 못합니다. `display.mode.refreshRate`(물리 모드)를 같이 기록해야 합니다. (2) [가설] 원인이 표시 일정 자신일 수 있습니다. Pacer 는 **콜백 한 번에 한 장만** 넘기므로(`Decoder.kt:132`) 콜백이 48Hz 로 한 번 내려가면 화면에 올라가는 버퍼도 초당 48장이 되고, 시스템은 "이 레이어는 48fps"로 보고 더 내릴 수 있습니다(내려갈수록 스스로 확인해 주는 고리). `rr=none` 을 `pace=now`(디코딩되는 대로 60장을 넘김)로 재면 가려집니다. 05 문서에 그 조합은 없습니다.
- 지금의 처방(`setFrameRate(60, FIXED_SOURCE)`)의 문제:
  - 원본이 60fps 가 아닌 프로젝트(30, 90, 120fps)에서 틀린 요청입니다. 설계 7.5 는 "원본 프레임 간격에서 반올림한 값"이라고 했고 `Decoder` 는 이미 `sourceIntervalMs` 를 잽니다(`Decoder.kt:164`). 요구사항 12(다른 프로젝트).
  - `FIXED_SOURCE` + `ONLY_IF_SEAMLESS` 는 터치 때의 120Hz 올림을 막지 않습니다(05 문서 실측). 그래서 탭마다 60 ↔ 120 전환이 일어나고(`w_tap3` 한 구간에 전환 기록 11개), 전환 순간마다 Pacer 의 주기 추정(15개 중앙값, `Decoder.kt:99`)이 약 8콜백 동안 틀립니다.
- 고칠 것: (1) 요청 값을 `round(1000 / sourceIntervalMs)` 로 하고 원본 간격이 바뀌면 다시 요청. (2) 기본 정책 후보 둘을 기기에서 견줍니다: **항상 높은 주사율**(`setFrameRate(패널 최대, …)` 또는 `preferredDisplayModeId`: 전환이 없고 칸이 8ms 라 지연이 작음) 대 **60 고정**(터치 올림까지 막는 요청 방식이 이 기기에 있는지 확인). 05 문서는 `force60`, `max` 를 재지 못했습니다. (3) 기록에 물리 모드 주사율을 추가. (4) M1 의 1번대로 고쳐도 "콜백보다 많이 넘길 수 없다"는 구조는 남으므로, 콜백 간격이 원본 간격의 1.5배를 넘으면(패널이 원본보다 느림) 경고 카운터를 올리고 HUD 에 표시합니다.

### M4. Wi-Fi 망 고르기가 VPN 을 Wi-Fi 로 집을 수 있습니다(무선 기본 경로, 미검증) [정적]

- 위치: `Session.kt:208~212`, `:221`, `:225`.
- 왜: `cm.allNetworks.firstOrNull { …hasTransport(TRANSPORT_WIFI) }`. Wi-Fi 위에 올라간 VPN 망도 `TRANSPORT_WIFI` 를 함께 가집니다. 목록 순서에 따라 VPN 망이 먼저 잡히면 소켓이 VPN 에 묶이고, 사설 주소의 PC 에는 닿지 않습니다. PRD F-32 가 이 묶기를 넣은 이유가 바로 "VPN 때문에 소켓이 다른 길로 나가는 것을 막기"인데 반대로 동작할 수 있습니다.
- 실패 장면: 광고 차단·회사 VPN 을 늘 켜 둔 폰에서 QR 을 찍으면 "PC에 닿지 않습니다(…)" 만 반복됩니다. 같은 망에서 Chrome 페이지는 됩니다.
- 그 밖: `allNetworks` 는 API 31 부터 폐기 예정이고, 걸 때마다 망 목록을 훑습니다. 설계 7.2 는 `registerNetworkCallback` 이었습니다. Wi-Fi 가 붙는 중이면 "Wi-Fi 가 꺼져 있습니다"로 곧바로 실패하고 재시도 간격을 탑니다.
- 고칠 것: `hasTransport(WIFI) && !hasTransport(VPN)`(API 28 이상은 `NET_CAPABILITY_NOT_VPN` 도 확인), 인터넷·검증 능력은 요구하지 않음. `NetworkRequest(TRANSPORT_WIFI)` 콜백으로 받아 둔 값을 씁니다. 고르는 부분은 순수 함수로 떼어 단위 시험(7.5절).

### M5. 보안: "브라우저가 아니면 adb"라는 판정과 확인 창의 빈틈 [정적]

위치: `MainActivity.kt:160~164`, `:168`, `:172`, `:174~177`, `Session.kt:247~267`, `:319~323`.

1. **폰의 다른 앱이 진단 명령을 쓸 수 있습니다.** `diag = BuildConfig.DIAG && !browsable` 입니다. `BROWSABLE` 이 없는 인텐트는 adb 만이 아니라 **설치된 아무 앱**이 보낼 수 있고(`MainActivity` 는 `exported`), 배포용 `proto` 빌드는 `DIAG = true` 입니다. 그런 앱은 `--es cmd forget`(기억한 서버 삭제), `legacy=1`(LAN 의 인증 없는 서버 허용), `listen=<포트>`(모든 인터페이스에 리슨 소켓), `decoder=<이름>`, `rec=…` 을 넣을 수 있습니다. `legacy=1` 과 주소를 같이 넣으면 **인증 없이 임의의 LAN 서버에 붙여** 화면을 바꾸고 터치 좌표를 받습니다.
2. **브라우저가 아닌 앱으로 열린 링크는 확인 창이 없습니다.** 확인 창 조건이 `browsable && …` 입니다(`:174`). 메신저, QR 스캐너 앱, 메모 앱이 `seeplay-gvr://…` 를 `ACTION_VIEW` 로 열면 `BROWSABLE` 이 붙지 않는 경우가 흔합니다. 그 길은 확인 창도 없고 1번의 진단 값(주소 뒤 `&legacy=1&listen=…`)도 받습니다. "악의적인 QR/링크 → 다른 PC 에 조용히 연결"이 됩니다.
3. **서버 표시(`sid`)가 같으면 확인 창을 건너뜁니다**(`known.sid != r.link.sid` 일 때만 물음). `sid` 는 비밀이 아닙니다(업그레이드 요청 헤더에 평문으로 실림). 공격자가 같은 `sid` 에 자기 주소와 자기 토큰을 넣은 링크를 만들면 확인 없이 연결되고, 성공하면 `store.remember` 가 **진짜 서버의 토큰과 주소를 덮어씁니다**(`Session.kt:162`, `ServerStore.kt:32~36`). 이후 앱 아이콘으로 열면 공격자 서버로 갑니다.
4. 기억한 서버가 없으면(처음 설치) 묻지 않는 것은 조정자 결정(브리프 3.3의 4)입니다. 다만 그 상태에서는 웹 페이지의 링크 하나로 임의의 IPv4(공인 주소 포함, `LinkParser.kt:82~85`)에 붙고 그 서버를 기억합니다. 남는 위험으로 적어 둡니다.
5. `listen=` 의 리슨 소켓은 `ServerSocket(port)` 라 **모든 인터페이스**(모바일 데이터 포함)에 열립니다(`Session.kt:248`). 설계 3.7 은 `wlan0` 입니다. 포트가 쓰이는 중이거나 1024 미만이면 예외가 `gvr-conn` 에서 잡히지 않아 **앱이 죽습니다**(`Session.kt:134`). 한 번 값이 들어오면 `Settings` 에 남아 그 뒤 모든 연결이 "PC가 걸어 오기를 기다리는 중"이 됩니다.

고칠 것:

- 진단 입구를 **adb 만 통과하는 문**으로 옮깁니다. 매니페스트에 `android:permission="android.permission.DUMP"` 를 단 `activity-alias`(또는 `BroadcastReceiver`)를 따로 두고 `cmd`·진단 값·`--es t` 는 그 입구로 들어온 인텐트에서만 받습니다. 셸은 `DUMP` 권한이 있고 일반 앱은 없습니다(androidx 의 `ProfileInstallReceiver` 가 같은 방식). `MainActivity` 의 `VIEW` 필터로 들어온 인텐트에서는 `BROWSABLE` 여부와 상관없이 진단 값을 버립니다. `tools/env.sh` 의 `open`/`cmd` 는 대상 컴포넌트 이름만 바뀝니다.
- 확인 창 조건: 앱 안 스캐너와 위 adb 입구를 뺀 **모든 외부 링크**에 적용하고, 비교 대상을 `sid` 하나가 아니라 "`sid` 가 같고 **토큰도 같고** 주소가 기억한 주소 목록 안"으로 바꿉니다. 하나라도 다르면 묻습니다.
- 주소는 사설 대역(10/8, 172.16/12, 192.168/16, 169.254/16, 100.64/10)과 127/8 만 받습니다(다른 대역이 필요한 프로젝트는 빌드 설정으로).
- 리슨 소켓은 Wi-Fi 주소에 바인드하고 `BindException` 을 잡아 문구로 보여 줍니다.

토큰 취급은 확인한 범위에서 괜찮습니다: 앱의 로그·HUD·기록 파일에 토큰을 쓰는 곳은 없고(`Log` 호출 9곳과 `Exporter` 확인), 저장은 앱 전용 `SharedPreferences`(`allowBackup=false`)입니다. 평문 저장이라는 점과, 딥링크 인텐트가 태스크의 기본 인텐트로 남는다는 점(m6)만 적어 둡니다.

## 7. 기기에서 확인하지 못한 부분: 설계와의 줄 단위 대조와 시험 계획

공통 준비(8장 4번): `WsClient` 의 `android.util.Base64` → `java.util.Base64`, `Session.openChannel` 의 "업그레이드 + 인증" 부분을 Android 클래스 없는 함수 `Handshake.run(ws, link, channel, cn, appInfo): Result`(성공 / 종료 상태 종류 / 재시도)로 분리. 그러면 아래 7.1~7.2 가 JVM 에서 `ServerSocket` 가짜 서버나 `node tools/replay.js --auth` 를 상대로 돕니다.

가상 기기에서(`04_device_lab.md` 가 READY 일 때): 에뮬레이터의 `10.0.2.2` 는 호스트의 루프백입니다. `replay.js` 를 `127.0.0.1` 에만 열어 두고 `seeplay-gvr://10.0.2.2:7311/c?…&via=lan` 으로 열면 **PC 를 LAN 에 열지 않고도 "루프백이 아닌 주소" 길**(Wi-Fi 망 묶기, 인증 필수, 병렬 걸기)을 탈 수 있습니다.

시험(JVM, 가짜 서버 또는 `replay.js --auth`):

1. 고정 `cn`(바이트 10..1f)과 서버 `sn`(20..2f), `sid=GVRTEST1` 형식 검사를 끈 상태에서 앱이 보낸 `auth` 메시지의 `mac` 이 `Mi9NohBm…`(video), `HvOPi01E…`(input)인지. → 핸드셰이크 전체가 설계 벡터와 맞는지의 유일한 직접 증거.
2. 서버가 틀린 `mac` 을 줌 → `FAILED_TOKEN`, 앱이 `auth` 메시지를 **보내지 않음**.
3. `sn` 이 21자, 응답 `v=2`, `proto=3` → 각각 `FAILED_TOKEN`, `FAILED_VERSION`.
4. 응답에 `X-GVR-Auth` 없음 + 루프백 → 연결, `auth = none(구버전 서버)`. 같은 응답 + 비루프백 주소(가짜 서버를 PC 의 다른 주소에 바인드하거나 원격 주소 판정 함수를 주입) → `FAILED_TOKEN`.
5. HTTP 401, 403(`unknown_server`, `bad_origin`, 코드 없음), 426(두 코드), 400, 503 → 기대 상태와 문구 표.
6. 요청이 `write` 1번인지: 가짜 서버가 첫 `read` 로 `\r\n\r\n` 까지 다 받는지(루프백에서는 한 덩어리로 옴).
7. 이번 리뷰가 Node 클라이언트로 `replay.js` 에 대해 확인한 8가지(1장)는 **시험 서버**의 검증입니다. 같은 표를 Kotlin 코드로 다시 돌려야 앱의 검증이 됩니다. Unity 쪽은 `tools/unity-host/hosttest.js` 가 같은 일을 합니다.

### 7.3 QR 스캐너 (설계 2.1, 4.1)

- 대조: CameraX + ZXing core, 인식은 기기 안(`Scanner.kt:37~43`), 읽은 글자열을 그대로 `LinkParser` 로(`MainActivity.kt:384~389`), 권한은 스캔에 들어갈 때만 요청(`:374`), 거부 문구(`:396`). 설계와 일치. 차이: 스캔 취소 뒤 재연결 없음(m7).
- 시험:
  1. JVM: ZXing 의 `QRCodeWriter` 로 설계 4.1 의 예(81자, 오류 정정 M)를 만들고 밝기 배열로 바꿔 `Scanner.decodeLuma` 에 넣음. 변형: 행 간격(`rowStride`) > 폭, 90도 회전, 흑백 반전, 여백 4모듈/1모듈, 모듈당 2픽셀(1280×720 에서 QR 이 화면의 1/4 일 때). 함수가 이미 Android 형식을 받지 않게 돼 있어 바로 쓸 수 있습니다.
  2. JVM: Unity 가 만든 QR PNG(6단계 산출물)를 같은 함수로 읽어 글자열이 QR 내용과 같은지. 앱의 인식기와 Unity 의 생성기를 직접 잇는 유일한 PC 쪽 확인입니다.
  3. 가상 기기: 에뮬레이터 카메라의 가상 장면에 QR 이미지를 걸 수 있으면 화면 흐름(권한 창 → 인식 → 연결)을 봅니다. 안 되면 소유자 목록.

### 7.4 딥링크와 확인 창 (설계 4.2)

- 대조: 스킴 필터, `?` 뒤 값, `via` 추론, 모르는 값 무시, `v≠1` → 업데이트 문구, 확인 창은 브라우저 링크이고 `sid` 가 다를 때 1번, 처음 설치는 묻지 않음, 스캐너와 adb 는 묻지 않음. **설계 문장과는 일치합니다.** 빈틈은 설계 수준의 것입니다(M5).
- 시험:
  1. JVM: 판정을 순수 함수 `LinkGate.decide(source, known, link): Use | Confirm | Reject` 로 떼고 표로 시험. 줄: 출처 3종(스캐너, 외부 링크, adb 입구) × 기억 없음 / 같은 서버 / `sid` 만 같고 토큰 다름 / `sid` 같고 주소 다름 / `sid` 다름. M5 의 3번이 `Confirm` 이어야 합니다.
  2. 가상 기기: `adb -s emulator-5554 shell am start -a android.intent.action.VIEW -c android.intent.category.BROWSABLE -d '<링크>' kr.co.seeplay.gvr` 로 브라우저 링크를 흉내 내고 `uiautomator dump` 로 창의 문구와 버튼을 읽음. 같은 링크에 `&legacy=1&hud=1` 을 붙여 **무시되는지**. `BROWSABLE` 없이 `MainActivity` 로 직접 보낸 `--es cmd forget` 이 (M5 를 고친 뒤) **거절되는지**.
  3. 가상 기기: 잘못된 링크(`seeplay-gvr://x`)가 재생 중인 세션을 끊지 않는지(m5), 프로세스를 죽이고 최근 앱에서 다시 열었을 때 옛 링크를 다시 쓰지 않는지(m6).

### 7.5 Wi-Fi 직접 연결과 소켓 묶기 (PRD F-32, 설계 5.1, 7.2)

- 대조: 후보 동시 걸기(첫 주소 먼저, 150ms 뒤 나머지, 각 3초), 이긴 소켓만 남김, 입력 채널은 같은 주소, LAN 주소는 Wi-Fi 망에 묶고 127.x 는 묶지 않음, Wi-Fi 망이 없으면 곧바로 실패. 설계와 일치. 차이: 망 고르기(M4), 콜백 대신 매번 조회, `via=usb` 면 첫 주소만 시도(`Session.kt:218`).
- 시험:
  1. JVM: `pickWifi(목록)` 순수 함수. 줄: Wi-Fi 만 / Wi-Fi + 모바일 / **VPN(전송 = VPN+WIFI) + Wi-Fi 에서 VPN 이 먼저** / Wi-Fi 없음 / 인터넷 없는 Wi-Fi(검증 안 됨).
  2. JVM: `Dialer` 를 떼어 `ServerSocket` 3개(바로 받음, 연결 거부, 응답 없는 주소)로 "먼저 닿는 쪽", 진 소켓이 닫히는지, 전부 실패 때의 예외 문구, 도중 `stop()` 에 소켓이 남지 않는지.
  3. 가상 기기: 위의 `10.0.2.2` 방법으로 `via=lan` 연결이 인증까지 되는지, 에뮬레이터의 Wi-Fi 를 끄면(`svc wifi disable`) "Wi-Fi 가 꺼져 있습니다" 가 나오는지, 다시 켜면 붙는지.
  4. 실제 Wi-Fi(전파 구간, 2.4/5GHz, VPN 을 켠 폰)는 가상 기기로 볼 수 없습니다. 소유자 목록.

### 7.6 그 밖에 넣을 단위 시험

- `WsClient`: 길이 125/126/65535/65536, 한 번에 1바이트씩 오는 흐름, 조각 2개 + 사이의 ping, 닫기 코드 유/무, 마스크된 서버 프레임, 16MB 초과, 125 초과 제어 프레임. 보내는 프레임의 마스크 풀기.
- `TouchMapper`: 좌표를 받는 순수 부분을 떼어 여백 자르기, 크기 미정(m2), 두 손가락 d/d/m/u/u 의 id 와 번호, 취소, 꺼질 때의 `c`.
- `Pacer`: 부록 A 의 방식으로 `tools/rec/` 기록 10개를 넣어 멈춘 갱신·건너뜀·지연의 상한을 회귀 기준으로.

## 부록 A. 표시 일정 오프라인 재현기

기록 파일의 `app.frames`(`[gen,id,flags,bytes,capMs,seq,recv,queued,decoded,due,release,target,rendered]`)와 `raf`(vsync 콜백 시각)만으로 `Decoder.onVsync` 를 다시 돌립니다. 이번 리뷰의 스크립트는 세션 임시 폴더에 있어 남지 않으므로(`tools/` 에는 쓸 권한이 없었습니다) 핵심을 여기 적습니다. 4단계 4번에서 `video.Pacer` 의 JVM 시험으로 옮기면 됩니다.

```js
// 입력: frames = [{id, cap, decoded, due}] (세대 하나, decoded > 0), raf = [vsync ms]
// 프레임은 decoded <= vsync + 0.8ms 이면 그 콜백에서 ready 에 있다고 봄(기록의 release − vsync 중앙값 0.8ms)
function simulate(frames, raf, rule) {
  let fi = 0, period = 16.667, lastV = 0, lastRelT = 0, lastRelDue = 0, phase = 0, vs = 16.7;
  const diffs = [], ready = [];
  for (const t of raf) {
    if (lastV) { const d = t - lastV; if (d > 1 && d < 100) { diffs.push(d); if (diffs.length > 15) diffs.shift();
      if (diffs.length >= 15) period = diffs.slice().sort((a, b) => a - b)[7]; vs += 0.1 * (d - vs); } }
    lastV = t;
    while (fi < frames.length && frames[fi].decoded <= t + 0.8) ready.push(frames[fi++]);
    let pick = null;
    if (rule === 'v3') {                                   // Decoder.kt:110~131 그대로
      const limit = t + period / 2;
      while (ready.length && ready[0].due <= limit) {
        const head = ready[0];
        if (lastRelT) { const want = head.due - lastRelDue, spacing = t - lastRelT;
          if (want >= 1 && want <= 50 && spacing < want - period / 2 && t - head.due < period * 1.5) break; }
        ready.shift();
        if (ready[0] && ready[0].due <= t - period / 2) { head.sim = -1; continue; }
        pick = head; break;
      }
    } else {                                               // 'page': GameViewRemotePage.html schedTake 와 같은 규칙
      let pi = -1; for (let i = 0; i < ready.length; i++) { if (ready[i].due + phase > t) break; pi = i; }
      if (pi >= 0) { for (let i = 0; i < pi; i++) ready.shift().sim = -1;
        pick = ready.shift(); const r = t - (pick.due + phase);
        if (r < vs) { phase += 0.1 * (r - vs / 2); if (phase > vs * 0.75) phase -= vs; else if (phase < -vs * 0.75) phase += vs; } }
    }
    if (pick) { pick.sim = t + 0.8; lastRelT = t; lastRelDue = pick.due; }
    while (ready.length > 4) ready.shift().sim = -1;       // holdLimit
  }
}
// 지표는 tools/app-report.js 와 같은 정의를 sim 열에 적용: 멈춘 갱신 = (sim 간격 − cap 간격) > 8ms (cap 간격 < 25ms)
```

검증(실제 기록 대 재현): `w2_tap1`(v3) 멈춘 갱신 10 → 9, 건너뜀 22 → 19, `넘긴 시각 − due` 중앙값 13.6 → 13.3ms. `w_tap1`(v2 규칙, 미루기 줄만 뺌) 50 → 65, 22 → 24. 방향과 크기가 맞으므로 규칙 비교에 쓸 수 있다고 봤습니다. 한계: 버퍼를 오래 쥐었을 때 디코더가 느려지는 효과와 콜백이 늦게 깨는 경우는 들어 있지 않습니다.
