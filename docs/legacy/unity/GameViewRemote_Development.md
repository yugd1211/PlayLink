# Game View Remote — 개발 문서

- 작성일: 2026-11-06
- 대상: CatJump, Unity 2022.3.62f2, Windows 에디터, 안드로이드 폰 Chrome
- 상태: 무선(adb 무선) + H.264(NVENC) 경로 추가(13장, 실기기 무선 확인). 1단계(입력 PoC) 완료, 2단계(MJPEG 스트림 + 폰 터치) 구현 완료. 폰 화면 찢어짐(부분 검은색) 문제 해결(11장, 실기기에서 사용자 확인). 프레임 끊김 원인 측정과 수정(12장, 하네스 확인, 실기기 확인 대기). 보완 작업(Game 뷰 가려짐 경고, 창 UX/adb, Wi-Fi 허용 옵션) 완료. 3단계(H.264)는 보류.
- 코드: `Assets/04_Scripts/Editor/GameViewRemote/`
- 사용 가이드: `Assets/04_Scripts/Editor/GameViewRemote/README.md`
- 2026-11-14: **QR 연결(안드로이드 앱)과 창의 새 흐름**을 넣었습니다(17장). 인증 없는 "Wi-Fi 접속 허용" 토글은 없앴습니다(17.5). 이 문서의 1~16장에서 그 토글을 말하는 곳은 그때의 기록이고, 지금 동작은 17장이 기준입니다.
- 근거 자료: `game-view-remote-plan.md`(계획/조사), `game-view-remote-phase1-result.md`, `game-view-remote-phase2-result.md`(실측 보고서)

## 1. 목표와 배경

- 에디터 Play 중 Game 뷰를 폰에 실시간으로 보여 주고, 폰 터치를 에디터에 실기기 터치처럼 넣습니다.
- Unity Remote 5를 대체합니다. Unity Remote 5는 프레임마다 JPEG/PNG를 축소해서 보냅니다(비디오 코덱 없음). 체감은 약 15fps이고, 입력과 영상이 같은 경로로 왕복합니다. 설정으로는 개선되지 않습니다.
- 제약:
  - 프로젝트가 2022.3이라 Unity 6 전용 기능은 쓸 수 없습니다.
  - **레거시 Input Manager만 씁니다**(`activeInputHandler: 0`). 게임 스크립트 22개가 `Input.touches`, `GetTouch`, `GetMouseButton` 등을 직접 읽습니다. 그래서 입력 주입은 UGUI 전용(`BaseInput` override)이 아니라 **레거시 `Input.touches` 자체를 채워야** 합니다.
  - 에디터 전용이어야 하고, 기존 게임 코드를 바꾸지 않아야 합니다.

### 1.1 핵심 발견: `Input.SimulateTouch`

- 엔진에 `internal static void UnityEngine.Input.SimulateTouch(Touch touch)`가 있습니다(`UnityEngine.InputLegacyModule`, `[Conditional("UNITY_EDITOR")]`). 내부적으로 `SimulateTouchInternal(Touch, long timestamp)` → 네이티브 `FreeFunction("SimulateTouch")`로 이어집니다.
- 리플렉션으로 부르면 **같은 프레임에** `Input.touchCount`와 `Input.touches`에 들어갑니다. 멀티터치도 됩니다. StandaloneInputModule(UGUI)도 이 터치를 처리합니다.
- 1단계에서 확인한 것: 엔진 수신, 게임플레이 점프(`GameManager.cs:1040 OnClickJump`), UI 버튼, 멀티터치 가드(`UIMgr.cs:7096`), 이중 점프 없음.

## 2. 전체 구조

```
[Unity Editor, Play 중]                                                   [폰 Chrome]
 PlayerLoop: EarlyUpdate.UpdateInputManager 직전 (RemoteStep, 메인 스레드)
   ① 끝난 리드백 확인(request.Update)
   ② Game 뷰 렌더 타깃(PlayModeView.m_TargetTexture) → GPU 상하 반전 Blit
      → AsyncGPUReadback 요청(최대 3개 겹침)
   ③ 입력 큐 → Input.SimulateTouch(리플렉션) + EventSystem 포커스 강제 ON
   ④ 1초 통계
 PlayerLoop: PostLateUpdate 맨 끝 (RemoteLateStep) — 저지연 리드백(기본 켬)이면 이번 프레임 리드백을 받음(끝난 것은 대기 없음)
 리드백 콜백(메인) → byte[] 복사 → [인코더 스레드] 프레임 검사(검정/크기, 안전장치) → 전체 픽셀 해시(같으면 건너뜀) → EncodeArrayToJPG
   → 헤더 28B + JPEG ─▶ 클라이언트별 "최신 1장" 슬롯 ─▶ [전송 스레드] ws /video ─▶ createImageBitmap → (rAF) canvas
                                                  ◀── "a"(수신 확인) ◀──
   EditorApplication.update: 게임 카메라가 0.7초 넘게 안 그리면 {t:"s", stale, msg} ─▶ 폰 화면 아래 경고
 [수신 스레드] ws /input ◀── {t:"d|m|u|c", id, x, y, s} (0~1, 그려진 이미지 기준) ◀── pointer 이벤트
                           ◀── {t:"p", ts} → {t:"P", ts} (RTT)
                           ◀── {t:"q", ...} 페이지 화면 검사 누적값(2초마다)
 TcpListener 127.0.0.1:7300 — GET / (페이지), /video, /input (RFC6455 직접 구현). 같은 Wi-Fi 의 앱은 앞단(GameViewRemoteHost, <QR 주소>:7300, 인증 필수)으로 들어옵니다(17장)
```

연결 경로:

- USB: `adb reverse tcp:7300 tcp:7300` → 폰에서 `http://localhost:7300/`. Start 때 기기가 1대면 자동으로 reverse합니다. 창의 "폰에서 열기"는 reverse + 폰 Chrome 열기까지 합니다.
- 같은 Wi-Fi(앱): 창의 Start → QR → 앱. 인증된 앱 연결만 받습니다(17장). 예전의 "Wi-Fi 접속 허용"(`0.0.0.0` 바인드, 인증 없음, 폰 Chrome 에서 `http://<PC IP>:7300/`)은 2026-11-14에 없앴습니다(17.5).
- Chrome 페이지의 무선 방법은 **무선 adb**입니다. 창의 "USB 폰을 무선으로 전환"(`adb tcpip 5555` → 폰 wlan0 IP 확인 → `adb connect IP:5555` → `adb reverse`) 또는 Android 11+ 무선 디버깅(`adb pair` → `adb connect`). PC → 폰 방향 adb 연결 위의 터널이라 방화벽 변경이 필요 없고, 폰은 USB와 같은 `http://localhost:7300/`을 엽니다. 마지막 주소를 `GVR_WirelessAddress`에 기억해 Start 때 기기가 없으면 다시 연결합니다.

### 2.1 스레드

| 스레드 | 하는 일 |
|---|---|
| 메인(PlayerLoop) | 캡처 요청, 리드백 확인, 입력 주입, 통계. **네트워크를 기다리지 않습니다.** |
| 수락 스레드 1개 | `TcpListener.AcceptTcpClient`, HTTP 요청 파싱, WebSocket 핸드셰이크 |
| 연결당 수신 스레드 | WebSocket 프레임 수신(마스킹 해제, 조각 메시지, ping/pong/close) |
| 영상 연결당 전송 스레드 | 최신 1장 슬롯에서 꺼내 전송, 수신 확인 대기 |
| 인코더 스레드 1개 | 프레임 검사 + 변경 감지 해시 + `ImageConversion.EncodeArrayToJPG` |
| adb 스레드(필요할 때) | `GameViewRemoteAdb`: 기기/권한/reverse 확인, 자동 reverse, 폰에서 열기. 명령은 하나씩 순서대로 |

## 4. 프로토콜

### 4.1 HTTP 경로

| 경로 | 내용 |
|---|---|
| `GET /`, `GET /index.html` | 폰 페이지 HTML |
| `GET /video` (WebSocket) | 서버 → 폰: 접속 직후 `{t:"hello", v}`(프로토콜 번호, 지금 2), 바이너리 프레임, 텍스트 상태 `{t:"s", stale, msg}`(화면이 멈춘 이유, 접속 직후에도 마지막 상태를 보냄). 폰 → 서버: `"a"`(수신 확인), `{t:"caps", h264}`, `{t:"key"}`(키프레임 요청) |
| `GET /input` (WebSocket) | 폰 → 서버: 포인터 JSON, ping. 서버 → 폰: pong |
| `GET /stats` | 진단 JSON: 창의 1초 통계(`snapshot`), 누적 카운터, 최근 약 34초의 Unity 프레임 기록(`frames`)과 인코딩 결정(`encodes`). 필드 순서는 `GameViewRemoteTrace.cs` 주석 |
| `GET /debug?pattern=1` / `0` | 테스트 패턴 켜기/끄기(창의 "테스트 패턴" 토글과 같음) |

프로토콜 번호(`GameViewRemoteCapture.PROTOCOL_VERSION` = 페이지의 `PROTOCOL_VERSION`)가 서로 다르면 페이지가 스스로 새로 고칩니다(서버만 새로 컴파일된 경우). 번호 1(헤더 24바이트)인 예전 페이지는 `hello`를 모르므로 한 번은 직접 새로 고쳐야 합니다.

### 4.2 영상 프레임 (바이너리, little-endian)

| 오프셋 | 타입 | 필드 | 설명 |
|---|---|---|---|
| 0 | u32 | frameId | 프레임 번호 |
| 4 | u16 | width | 픽셀 너비 |
| 6 | u16 | height | 픽셀 높이 |
| 8 | i32 | inputSeq | 이 화면에 반영된 마지막 입력 번호. 폰이 터치 → 반영 프레임 표시 지연을 직접 잽니다 |
| 12 | u32 | encodeUs | JPEG 인코딩 시간 |
| 16 | u32 | captureToEncodedUs | 캡처 요청 → 인코딩 완료 |
| 20 | u32 | flags | 1 = 이전 프레임과 같은 화면 재전송(JPEG), 2 = H.264, 4 = 키프레임, 8 = H.264 설정(avcC) |
| 24 | u32 | captureTime | 캡처 시각: 서버 시작 뒤 흐른 시간, 0.1ms 단위(프로토콜 2에서 추가). 폰 페이지가 이 시각표에 맞춰 표시합니다(12.8) |
| 28 | — | JPEG 또는 H.264 | JPEG 파일, 또는 AVCC(길이 4바이트 + NAL) 프레임 1장, 또는 avcC |

### 4.3 입력 메시지 (텍스트 JSON)

| `t` | 의미 | 필드 |
|---|---|---|
| `d` / `m` / `u` / `c` | pointerdown / move / up / cancel | `id`(pointerId), `x`, `y`(0~1, **그려진 이미지 영역 기준**, 레터박스 제외, 왼쪽 위 0), `s`(입력 번호) |
| `p` | ping | `ts` → 서버가 `{t:"P", ts}`로 답합니다(RTT) |
| `q` | 페이지 화면 검사 누적값(2초마다) | `fr` 그린 프레임, `bk` 검은 디코딩, `jb` 손상 JPEG, `sz` 크기 불일치, `de` 디코딩/그리기 실패, `cb` 화면 캔버스 검정, `cl` 컨텍스트 손실, `lb` 마지막 이상 frameId. 값이 바뀌면 서버 로그, 창의 `Client check` 줄 |

- 폰은 move를 애니메이션 프레임당 1번으로 합쳐 보냅니다.
- 서버는 x, y를 `Screen.width/height`로 바꾸고 y를 뒤집습니다(Unity 화면 좌표는 아래가 0).

### 4.4 역압(지연이 쌓이지 않게)

- 폰은 프레임을 받자마자 `"a"`를 보냅니다. 서버는 확인이 오기 전에는 다음 프레임을 보내지 않습니다(확인이 1초 동안 하나도 오지 않으면 그냥 보냄. 기한은 보낼 때와 확인이 올 때마다 미룸).
- WebSocket 메시지 1개(프레임 헤더 + 영상 헤더 + 내용)는 클라이언트별 버퍼에 모아 **소켓 쓰기 1번**으로 보냅니다. HTTP 응답도 헤더와 본문을 한 번에 씁니다. 나눠 쓰면 adb 터널에서 약 40ms 정체가 생깁니다(12.7).
- 그사이 새 프레임은 슬롯의 이전 프레임을 **덮어씁니다**. 인코딩 대기도 1장, 폰 디코딩 대기도 1장(최신 것만)입니다.
- 변경 감지: 픽셀 전체 FNV 해시가 같으면 보내지 않습니다. 같은 화면이어도 200ms마다 1번은 이전 JPEG를 다시 보냅니다(유휴 하한 5fps).
- 접속 직후에는 마지막 프레임을 바로 보냅니다(seed).

## 5. 캡처

- **`PlayModeView.m_TargetTexture`(private)를 리플렉션으로 읽습니다.** Game 뷰가 그려 둔 렌더 타깃입니다.
  - `ScreenCapture.CaptureScreenshotIntoRenderTexture`는 에디터 PlayerLoop 안에서 Game 뷰가 아니라 **에디터 창 백버퍼**(Game 뷰 툴바 포함)를 잡아서 쓰지 않습니다.
  - Game 뷰가 여러 개면 크기가 `Screen.width/height`와 같은 것을 고릅니다.
- D3D11(`SystemInfo.graphicsUVStartsAtTop`)에서는 위아래가 뒤집혀 나와서 GPU Blit(scale (1,-1))으로 뒤집습니다. GL 계열은 미확인입니다.
- `AsyncGPUReadback`으로 메인 스레드를 막지 않습니다. 리드백은 최대 3개까지 겹쳐 요청합니다(1개만 두면 17~21fps로 묶였음).
- 리드백 완료 확인 시점:
  - 그냥 두면 Unity가 "다음 프레임 끝"에야 완료를 확인해서 콜백이 2프레임(약 55ms) 늦게 옵니다. GPU 복사 자체는 3~5ms면 끝납니다.
  - **저지연 리드백(기본 켬)**: 같은 프레임 PostLateUpdate 끝에서 받습니다. 먼저 `request.Update()`로 확인하고, 아직 안 끝난 것만 `WaitForCompletion()`으로 기다립니다. 실측 대기 평균 1.1ms / 최대 2.2ms(60fps), fps 차이 없음.
    - 안전장치: 대기 평균(30회 이상)이 6ms를 넘으면 10초 동안 폴링 방식으로 돌아갔다가 다시 시도합니다(로그 `low-latency readback paused`, 창 Latency 줄). Scene 뷰를 Game 뷰 옆에 띄운 순간 평균 6.1ms가 나와 실제로 한 번 동작했습니다.
  - **끄면(폴링)**: 다음 프레임 시작(RemoteStep)에서 `request.Update()`를 직접 불러 1프레임으로 당깁니다. 메인 스레드 대기는 없습니다.
- 뒤집기 텍스처는 원본 렌더 타깃과 같은 `graphicsFormat`으로 만듭니다(색 공간 변환 없음). `Graphics.Blit`이 남기는 `RenderTexture.active`는 바로 원래대로 돌립니다(EarlyUpdate라 그대로 두면 이번 프레임의 다른 그리기가 영향받을 수 있음).
- **프레임 검사(인코더 스레드, 모든 프레임)**: 7픽셀 간격 표본에서 RGB 합 < 24인 비율이 0.97 이상이면 검은 프레임, 크기가 `Screen` 크기와 다르면 크기 불일치로 셉니다. 상태가 바뀔 때만 `[GVR] frame check:` 로그(frameId, 소스 텍스처 id, 재생성 여부, 직전 캡처 뒤 카메라 렌더 수, 에디터 포커스 포함).
- **안전장치**: 캡처 쪽 이상의 증거가 있는 프레임만 최대 300ms 보내지 않고 마지막 정상 프레임을 둡니다. 대상 = 크기 불일치, 또는 직전에 보낸 프레임은 정상인데 렌더 타깃이 새로 만들어졌거나 그 사이 게임 카메라가 그리지 않은 상태의 검은 프레임. 게임이 실제로 검게 페이드하는 프레임은 막지 않습니다. 실측에서 한 번도 동작하지 않았습니다(`held 0`).
- **화면 멈춤 감지**: 게임 카메라(`Camera.onPostRender`, `CameraType.Game`)가 0.7초 넘게 안 그리면 이유(Play 일시정지 / Game 뷰 탭 가려짐 / 그 밖: 창 최소화 등)를 창과 폰에 알립니다. Game 뷰 탭이 가려졌는지는 `m_Parent`(DockArea)의 `actualView`로 봅니다. 가려진 Game 뷰는 엔진이 그리지 않고, `PlayModeView.RenderView`를 밖에서 불러도 카메라가 그려지지 않았습니다(실측). 그래서 강제로 그리지 않고 경고 + "Game 뷰 보이기" 버튼으로 처리합니다.
- `ImageConversion.EncodeArrayToJPG`는 백그라운드 스레드에서 문제없이 동작합니다(수천 프레임 확인).
- `EditorPrefs`는 백그라운드 스레드에서 쓰면 예외가 납니다. 그래서 인코더가 읽는 값(JPEG 품질, fps 상한)은 정적 필드에 캐시합니다.

## 6. 입력

- 수신 스레드에서 JSON을 파싱해 `ConcurrentQueue`에 넣습니다. 메인 스레드는 **`EarlyUpdate.UpdateInputManager` 직전** PlayerLoop 단계에서 꺼내 `SimulateTouch`를 부릅니다. 이 위치라야 주입한 프레임과 게임 `Update()`가 터치를 보는 프레임이 같습니다(실행 순서와 무관).
- 페이즈 규칙:
  - 손가락 하나는 **프레임당 페이즈 전환을 1번만** 합니다. down+up이 같은 프레임에 와도 Began → 다음 프레임 Ended로 나눠서 탭을 잃지 않습니다.
  - 누르고 있는 손가락은 움직임이 없어도 **매 프레임 Stationary + delta 0**을 넣습니다. 넣지 않으면 엔진이 마지막 페이즈를 그대로 반복해서, Moved 뒤에는 멈춰 있어도 Moved와 이전 deltaPosition이 계속 보입니다.
  - 연결이 끊기면 그 연결의 손가락은 Canceled로 끝냅니다.
  - `deltaPosition`, `deltaTime`, `tapCount`(0.3초 · 40px 안의 연속 탭)를 채웁니다.
- pointerId → fingerId 매핑을 연결별로 관리합니다.
- **원격 입력 연결이 있는 동안:**
  - `Input.simulateMouseWithTouches = false`. 켜 두면 가짜 터치가 마우스로도 흉내 내집니다. 그러면 `GameManager.cs:1059~1079`의 에디터 전용 마우스 경로가 `gameSpeed != 1`이나 `gameOver`일 때 실기기에 없는 점프를 일으킬 수 있습니다. 연결이 끊기거나 Stop하거나 Play를 끝내면 원래 값으로 되돌립니다.
  - **EventSystem 포커스를 강제로 켭니다**(`EventSystem.m_HasFocus = true`, 리플렉션, 매 프레임). StandaloneInputModule은 앱 포커스가 없으면(`ShouldIgnoreEventsOnNoFocus`) UI 이벤트를 버립니다. 폰을 들고 조작하면 Unity가 OS 포커스를 잃는 일이 흔해서 필요합니다. 게임이 `Input`을 직접 읽는 경로는 원래부터 포커스와 무관하게 동작합니다.

## 7. 수명 관리

- 서버는 **Play 중에만** 돕니다. Play에 들어갈 때 도메인 리로드로 정적 상태가 사라지기 때문입니다.
- 닫는 시점: Stop, Play 종료(`ExitingPlayMode`), 도메인 리로드(`AssemblyReloadEvents.beforeAssemblyReload`), 에디터 종료(`EditorApplication.quitting`). 이때 포트를 닫고, PlayerLoop 단계를 빼고, 마우스 시뮬레이션 값을 복구합니다.
- PlayerLoop 단계를 뺄 때는 저장해 둔 루프로 되돌리지 않고 **우리 단계만** 뺍니다. 다른 도구가 바꾼 루프를 덮어쓰지 않기 위해서입니다.
- Play 중 재컴파일로 리로드되면 `SessionState`에 표시해 두었다가 리로드 뒤 다시 엽니다. 폰 페이지는 자동으로 다시 접속합니다.
- 자동 시작 옵션: `EnteredPlayMode`에서 Start합니다.

## 9. 설계 결정

| 결정 | 이유 |
|---|---|
| `HttpListener` 대신 `TcpListener` + 직접 구현한 HTTP/WebSocket | Mono `HttpListener`의 WebSocket 지원이 불완전하고, Windows에서 localhost 외 주소에 바인드하려면 관리자 권한(urlacl)이 필요합니다 |
| 기본 `127.0.0.1` 바인드, Wi-Fi는 옵션 | 인증이 없어서 기본은 PC 안에서만 받습니다. adb reverse는 PC 쪽에서 127.0.0.1로 들어오므로 USB는 그대로 됩니다 |
| MJPEG(프레임별 JPEG) 먼저 | 구현이 단순하고 외부 의존이 없습니다. USB에서는 전송이 병목이 아닙니다 |
| 영상/입력 WebSocket 분리 | 큰 영상 프레임이 입력을 막지 않게 합니다(serve-sim 구조 차용) |
| PlayerLoop 단계 삽입 | Editor 폴더 MonoBehaviour는 런타임에 붙일 수 없습니다("is an editor script" 오류) |
| Game 뷰 렌더 타깃 직접 읽기 | `ScreenCapture`는 에디터 창 백버퍼를 잡습니다 |
| 최신 1장 + 수신 확인 역압 | 지연이 큐에 쌓이는 것을 막습니다 |
| 폰 페이지를 TextAsset(.html)로 분리 | 수정하기 쉽고, C# 문자열 이스케이프가 필요 없습니다 |
| Android Chrome 전체 화면은 `click`에서 요청 | 터치 `pointerdown`은 사용자 활성화로 인정되지 않아 `requestFullscreen`이 거부됩니다 |
| 캔버스 `desynchronized` 사용 안 함, 그리기는 `requestAnimationFrame`에서 1번 | 앞 버퍼에 바로 그리면 실기기 패널에서 화면이 찢어집니다(11장) |
| 가려진 Game 뷰는 강제로 그리지 않고 경고 | `RenderView`를 밖에서 부르면 아무것도 그려지지 않고, 카메라를 직접 렌더하면 Screen Space Overlay UI가 빠집니다 |

## 11. 해결한 문제: 폰 화면 찢어짐(부분 검은색)

### 11.1 증상

- 실기기(Galaxy Z Flip5, 120Hz 패널) 폰 화면에서 **화면 전체가 아니라 일부 영역이 중간중간 검거나 이상하게** 보였습니다.
- **FPS Cap을 올릴수록 심해졌습니다.** 낮은 값에서는 거의 보이지 않았습니다.
- **Unity Game 뷰, 폰 스크린샷(`screencap`), 에뮬레이터에서는 한 번도 보이지 않았습니다.** 실제 폰 패널에서만 보였습니다.

### 11.2 원인

폰 페이지(`GameViewRemotePage.html`)의 그리기 방식 세 가지가 겹쳤습니다.

1. 캔버스를 `getContext('2d', { alpha: false, desynchronized: true })`로 만들었습니다.
2. 이미지 디코딩이 끝나자마자 바로 그렸습니다. 화면 갱신 주기(vsync, `requestAnimationFrame`)와 무관했습니다.
3. 그릴 때마다 `fillRect`로 캔버스 전체를 검게 칠한 뒤 `drawImage`를 했습니다.

`desynchronized`가 핵심입니다.

| | 보통 캔버스(이중 버퍼) | `desynchronized: true`(앞 버퍼) |
|---|---|---|
| 그리는 곳 | 보이지 않는 뒤 버퍼 | 패널이 지금 읽고 있는 화면 버퍼 |
| 패널에 나가는 시점 | 다 그린 뒤 vsync에 맞춰 통째로 교체 | 그리는 즉시(중간 상태 포함) |
| 장점 | 항상 완성된 그림만 보임 | 지연이 약 1프레임 짧음(펜 입력 앱용) |
| 단점 | 교체를 기다리는 만큼 늦음 | 패널이 읽는 도중 그림이 바뀌면 **찢어짐(tearing)** |

- 패널은 화면을 위에서 아래로 한 줄씩 읽어 나갑니다. 앞 버퍼에 그리는 도중에 패널이 그 영역을 읽으면 섞인 그림이 나갑니다. 위쪽은 이전 프레임, 아래쪽은 새 프레임이 되기도 하고, `fillRect` 직후라면 **그 영역이 검게** 나갑니다. 이것이 "부분부분 검게 보이는" 증상입니다.
- vsync와 상관없이 그리니 패널 읽기와 계속 어긋났습니다. FPS Cap을 올리면 그리는 횟수가 늘어 겹치는 일이 더 잦았습니다. 120Hz 패널은 읽는 빈도가 높아 더 잘 드러났습니다.
- **스크린샷에 안 보인 이유**: `screencap`은 운영체제 합성기가 만든 완성 화면을 찍습니다. 패널이 읽는 도중의 상태는 담기지 않습니다. 에뮬레이터는 PC GPU 경로라 앞 버퍼 모드가 적용되지 않거나 다르게 동작합니다.

### 11.3 전송 쪽은 정상이었음 (근거)

- 수정 전 코드로 FPS Cap 120 + 저지연 리드백 상태를 계측했습니다. **서버 18,051프레임에서 검은 프레임 0개**(리드백 버퍼 검사)였습니다. **폰 11,585프레임 디코딩에서 검은 디코딩 0개, 손상 JPEG 0개**였습니다.
- Unity를 재시작한 뒤 폰 화면 90초 녹화에서도 0개였습니다.
- 결론: 캡처, 인코딩, 전송, 디코딩은 정상이었습니다. **폰에서 화면에 표시하는 단계에서만** 생긴 문제입니다.

### 11.4 해결

| 변경 | 내용 |
|---|---|
| `desynchronized` 제거 | `getContext('2d', { alpha: false })`. 실기기에서 `getContextAttributes().desynchronized === false` 확인 |
| 전체 지우기 제거 | 레터박스 여백은 레이아웃(크기/회전)이 바뀔 때만 칠합니다. 이미지는 이전 이미지 위에 바로 그립니다 |
| vsync 맞춤 | 디코딩된 이미지는 대기 슬롯에 넣고, `requestAnimationFrame`에서 **최신 1장만** 그립니다. 그 사이 더 새 이미지가 오면 이전 대기 이미지는 `close()`하고 버립니다 |
| 비트맵 해제 순서 | 새 이미지를 그린 **뒤에** 이전 비트맵을 `close()`합니다 |
| 다시 그리기 | `visibilitychange`, `pageshow`, `contextrestored` 때 다시 그립니다. 숨겨진 동안은 디코딩하지 않고 최신 1장만 받아 둡니다 |
| 크기 맞춤 | 캔버스 CSS 크기를 `innerWidth/innerHeight`로 직접 맞춥니다(`100vh`는 주소창이 보일 때 달라져 이미지가 늘어나고 터치가 어긋남). `fullscreenchange`, `visualViewport` resize에도 다시 맞춥니다. 그리는 사각형은 장치 픽셀 정수로 맞춥니다 |
| 이상 프레임 건너뛰기 | 헤더보다 짧은 메시지, SOI/EOI 없는 JPEG, 디코딩 실패, 헤더와 크기가 다른 이미지는 그리지 않고 이전 이미지를 둡니다 |
| A/B 비교 | `?desync=1`이면 수정 전 그리기(desynchronized + 매 프레임 전체 검정)로 돌아갑니다. 실기기 눈 비교용입니다 |

- 확인: 실기기 FPS Cap 120에서 **사용자가 폰 화면으로 찢어짐이 사라진 것을 확인**했습니다(2026-11-06).
- 비용: 이론상 표시가 최대 1 vsync(120Hz 기준 약 8ms) 늦어질 수 있습니다. 전체 터치 → 화면 지연(80ms대)에 비하면 체감하기 어려운 수준입니다.

### 11.5 교훈

- **스트리밍 화면에 `desynchronized` 캔버스를 쓰지 않습니다.** 매 프레임 화면 전체가 바뀌는 영상에는 맞지 않습니다. 펜 획처럼 일부만 덧그리는 경우용입니다.
- 화면 표시 문제는 스크린샷이나 에뮬레이터로 검증할 수 없습니다. **실기기 패널을 눈으로 확인해야** 합니다.
- 서버와 클라이언트 양쪽에 프레임 검사 카운터를 두면 "데이터 문제인가, 표시 문제인가"를 빨리 가를 수 있습니다. 창의 `Frame check` / `Client check` 줄이 그 계측입니다.
- 페이지 픽셀 검사는 GPU 읽기라 표시를 늦출 수 있어서, 평소에는 30장에 1장만, 디버그 표시(`i`)가 켜져 있으면 10장에 1장 + 화면 캔버스(1초마다)를 봅니다(매 프레임 읽으면 끊김을 보려고 켠 표시가 끊김을 만들 수 있음). JPEG 표지·디코딩 실패·크기·컨텍스트 손실은 항상 모든 프레임을 셉니다.
- 외부 검토(웹 검색 + Codex/Claude 고성능 모델 독립 검토) 결과와 반영 내역은 `game-view-remote-phase2-result.md` 9장에 있습니다. 두 검토 모두 "desynchronized + 매 프레임 지우기"가 가장 유력하다고 봤고, 녹화로는 증명되지 않으므로 실기기 눈 확인(위 사용자 확인)과 `?desync=1` A/B를 근거로 둡니다.

## 12. 프레임 끊김 점검

### 12.1 증상

- 찢어짐을 고친 뒤 사용자 보고: 스트림이 **가끔 끊긴다**(프레임이 빠지거나 잠깐 멈칫). 폰을 PC에 미러링한 화면(Orca 에뮬레이터 뷰)에서도 보였습니다.

### 12.2 측정 방법

단계별로 "어디서 프레임 간격이 벌어지는가"를 보도록 계측을 넣었습니다(창 `Pacing` 두 줄, 1초 단위).

| 단계 | 값 | 뜻 |
|---|---|---|
| Unity | `unity frame max`, `hitches`, `GC` | 가장 긴 프레임 시간, 직전 평균의 2배 넘고 25ms 넘는 프레임 수, GC 횟수 |
| 캡처 | `capture N/s (every k frame)`, `readback-full` | 캡처 수와 간격(k프레임마다 1번), 리드백 3개가 차서 건너뛴 수 |
| 인코딩 | `encoder` | 인코더가 바빠 덮어써진 프레임 |
| 전송 | `send`, `ack avg/max`, `timeout`, `send gap max` | 전송 슬롯에서 덮어써진 프레임, 보내기 시작 → 수신 확인(전송 + 왕복 + 폰 수신 처리), 1초 확인 시간 초과, 가장 긴 전송 간격 |
| 폰 | `phone drops`, `phone decode/frame`, HUD `gap max`, `>50ms` | 폰 디코더가 바빠 버린 프레임(초당), 한 장당 디코딩 비용, 표시 간격 최대와 50ms 넘는 간격 수 |
| 메모리 | `new buffers` | 새로 만든 픽셀 버퍼(3.7MB) 수 |

브라우저 하네스(`control.js`)에 `/pacing`(최근 n장의 수신/표시 간격 분포, frameId 건너뜀 분포)과 `/cpu?rate=`(CDP CPU 스로틀링, 느린 폰 디코딩 흉내)를 더했습니다. **frameId 건너뜀**은 서버가 인코딩한 프레임이 폰 화면까지 못 간 경우라, 화면 내용이 한 장씩 건너뛰는 끊김(judder)을 바로 보여 줍니다.

### 12.3 원인

1. **전송이나 폰 디코딩이 Unity fps를 못 따라갈 때 프레임이 불규칙하게 버려졌습니다(주원인).**
   - USB adb 터널은 약 70Mbps입니다(2단계 실측). q80 프레임 250KB는 전송에 약 28ms가 걸려 60fps(16.7ms)를 못 따라갑니다. 그러면 전송 슬롯의 이전 프레임이 새 프레임에 덮어써집니다. 그런데 이 덮어쓰기가 1장, 2장으로 **불규칙**하게 일어나 화면 내용이 고르지 않게 건너뜁니다.
   - 폰 JPEG 디코딩(Z Flip5 13~19ms, 가끔 그 이상)도 16.7ms에 가까워 같은 일이 페이지 쪽에서 생겼습니다.
   - 재현(하네스, CPU 5배 스로틀 = 느린 폰): **frameId 건너뜀 58%**. 2장에 1장꼴로 불규칙하게 빠졌습니다.
2. **Unity 자체 GC 멈춤.** 이 프로젝트 에디터 힙이 1.2~1.3GB이고 GC가 매번 전체 수집이라 1번에 50~120ms 멈춥니다. 스트리밍과 무관하게 약 16초에 1번(0.06회/s) 생기고, **Unity Game 뷰에서도 똑같이 멈춥니다.** q80 · 60fps 스트리밍은 프레임마다 새 JPEG 배열(약 250KB)을 만들어 GC 빈도를 약 2배(0.11회/s)로 올립니다.
3. 부수 원인: 픽셀 버퍼(3.7MB)를 1개만 재사용해서, 리드백이 겹치면 새로 할당했습니다. 프레임마다 헤더 + JPEG를 새 배열로 한 번 더 복사했습니다. FPS Cap이 Unity fps보다 낮으면 시간 기준 거르기라 fps가 흔들릴 때 간격이 섞일 수 있었습니다.

### 12.4 해결

| 변경 | 내용 |
|---|---|
| **자동 프레임 간격**(기본 켬, 창 "자동 프레임 간격(끊김 방지)") | 1초마다 "못 따라간다"는 근거를 봅니다: 전송/폰에서 버려진 프레임이 10% 초과, 수신 확인 시간 1초 평균이 100ms 초과(계속 밀림), 폰 한 장당 디코딩 비용이 보내는 간격의 85% 초과. 근거가 **2초 이어지면** **N프레임마다 1번(최대 4)** 으로 고르게 보냅니다. 여유가 10초 이어지면 한 단계 줄이고, 줄였다가 15초 안에 다시 늘리게 되면 다음 대기 시간을 2배(최대 160초)로 늘립니다. 영상 클라이언트 접속 뒤 4초는 판정하지 않습니다. 예전의 "수신 확인 간격" 비용은 쓰지 않습니다(왕복이 프레임 간격보다 긴 무선에서 포화가 아닌데도 30fps로 내려갔음). 바뀔 때 `[GVR] auto pacing:` 로그 |
| FPS Cap 간격 | 시간 기준 대신 **N프레임마다 1번**(N = ceil(Unity fps / Cap))으로 고르게. Cap이 Unity fps보다 낮으면 창에 안내 |
| 폰 병렬 디코딩 | `createImageBitmap`을 최대 2개 동시에 돌립니다. 끝난 순서와 상관없이 **받은 순서대로** 넘겨, 늦게 끝난 이전 프레임이 버려지는 일이 없습니다 |
| 영상 워커(기본 켬) | 영상 수신 · 디코딩 · 표시를 워커에서 합니다. 터치 중 메인 스레드가 수신을 미루는 문제를 피합니다(12.9). `?worker=0`이면 메인 스레드 경로 |
| 폰 표시 일정(기본 켬) | 헤더의 캡처 시각에 맞춰 표시합니다(12.8). `?sched=0`이면 예전 방식: 화면 갱신(rAF)마다 도착 순서대로 1장, 최대 2장, 넘치면 가장 새 것 1장만 남김(`gvr.catchups`) |
| 폰 → 서버 보고 | `{t:"q"}`에 `dm`(한 장당 디코딩 비용) · `dp`(디코더가 바빠 버린 수)를 더해 자동 프레임 간격이 씁니다 |
| 픽셀 버퍼 풀 | 최대 6개 풀. 실측 새 버퍼 할당 **0개**(60초) |
| 복사 제거 | 헤더(지금 28B)와 JPEG를 WebSocket 메시지 하나로 이어 씁니다(프레임마다 250KB 복사 1번 제거) |

### 12.5 결과 (하네스, q80, FPS Cap 60, Unity 60fps)

| 조건 | frameId 건너뜀(불규칙하게 빠진 비율) | 수신 간격 p50 / p95 | 비고 |
|---|---|---|---|
| 수정 전, 정상 | 0% (단 p95 31.6ms: 상류에서 2프레임 간격 섞임) | 16.9 / 31.6ms | |
| 수정 후, 정상 | **0%** | 16.7 / **21.1ms** | 60fps 유지 |
| CPU 3배(느린 폰), 자동 간격 첫 버전 | 14% | 24 / 36.7ms | 병렬 디코딩이 순서 없이 끝나 이전 프레임이 버려짐 |
| CPU 3배, 최종 | **0.25%** | 32.5 / 36.3ms | 고른 30fps |
| CPU 5배, 자동 간격 끔 | **58%** | 28 / 33.5ms | 불규칙하게 건너뜀 = 끊김 |
| CPU 5배, 자동 간격 켬 | **0%** | 33.3 / 37.9ms | 고른 30fps |

- GC: q80 · 60fps 60초 스트리밍 GC 7회(0.11/s), 새 픽셀 버퍼 0개. 스트리밍 없을 때 0.06/s.
- **실기기 확인은 폰 연결이 끊겨 아직 못 했습니다.** 폰에서는 `?debug=1` HUD의 `gap max ... (>50ms N)`와 창의 `Pacing` 줄로 확인합니다.
- 폰 미러링(PC 쪽 화면 복제)은 자체적으로 프레임을 버릴 수 있습니다. 기준은 페이지 계측(HUD gap, frameId 건너뜀)입니다.

### 12.6 남은 일

- JPEG 배열을 프레임마다 새로 만드는 것(q80 · 60fps에서 약 15MB/s)을 참조 카운트가 있는 버퍼 풀로 바꾸면 스트리밍이 더하는 GC를 없앨 수 있습니다. 여러 전송 스레드와 같은 화면 재전송이 같은 배열을 공유하므로, 잘못 재사용하면 전송 중인 JPEG가 깨집니다. 그래서 이번에는 하지 않았습니다. 그 전까지는 JPEG Quality 60~70으로 줄이면 대역폭과 GC가 함께 줄어듭니다.
- Unity 자체 GC 멈춤(Game 뷰에서도 보임)은 도구 밖의 문제입니다(게임/에디터 할당, 힙 1.2GB).

### 12.7 USB + H.264에서 남아 있던 끊김: 소켓 쓰기 분할 (2026-11-13)

증상: Unity는 60fps로 고르게 캡처 · 인코딩하는데(프레임 최대 17ms, 히치 0, GC 0) 폰 표시는 45~58fps로 흔들리고 간격이 50~75ms까지 벌어졌습니다.

원인: `WriteFrame`이 WebSocket 메시지 1개를 소켓 쓰기 3번(프레임 헤더 4B, 영상 헤더 24B, 내용)으로 보냈습니다. `NoDelay`라 각각 따로 나가고, adb 서버가 앞의 몇 바이트만 먼저 넘기면 폰 쪽(adbd → Chrome)에서 나머지가 약 40ms 묶였습니다. 정체가 풀리면 2~3장이 한꺼번에 도착해 폰 표시 대기열이 일부를 버렸습니다. 폰 안쪽에서 묶이는 기전(Nagle + 지연 ACK로 추정)은 직접 확인하지 못했고, "나눠 쓰면 생기고 한 번에 쓰면 안 생긴다"는 것은 측정했습니다.

격리 측정(별도 포트, 같은 폰 · 같은 adb reverse, 12.5KB 메시지를 100ms마다, 폰이 다 받으면 답장, 각 60회 2번씩):

| 보내는 방식 | 왕복 p50 | 최대 | 35ms 이상 |
|---|---|---|---|
| 쓰기 3번(4 + 24 + 내용) | 44ms | 51~55ms | 62~63% |
| 쓰기 1번 | 6ms | 10~16ms | 0% |

해결:

- 메시지 1개를 클라이언트별 버퍼(`Connection.sendBuffer`, 다시 씀)에 모아 쓰기 1번으로 보냅니다(영상 · 텍스트 · pong · close 공통, `WriteMessage`). HTTP 응답도 한 번에 씁니다.
- 자동 프레임 간격은 늘리는 조건이 2초 이어질 때만 늘립니다. 고치기 전에는 정체가 섞인 1초 표본 하나로(버린 프레임 0) 30fps로 내려갔습니다.
- 전송 스레드는 한 장 보낸 직후에는 신호를 기다리지 않고 큐를 한 번 더 봅니다. 수신 확인 기한은 확인이 올 때마다 미룹니다.
- 폰 표시 대기열은 넘치면 최신 1장으로 한 번에 건너뜁니다. 디버그 표시 중 픽셀 검사는 10장에 1장입니다.
- 프로토콜(프레임 헤더, 메시지 형식)은 바뀌지 않았습니다.

실기기 결과(Z Flip5, USB adb reverse, H.264 720x1280 6Mbps, 같은 세션에서 고치기 전후, 10~12초 표본):

| 항목 | 전 | 후 |
|---|---|---|
| 폰 도착 간격 40ms 이상 | 52회/10초(9.0%) | 1회/10초(0.2%) |
| 3ms 안에 몰려 도착한 프레임 | 92장/10초 | 0장 |
| 수신 확인 평균 / 최대 | 15.9 / 44.8ms | 4.2 / 7.5ms |
| 그리지 않고 버린 프레임 | 11.0% | 0% |
| 폰 표시 fps(1초) | 45~58 | 54~59 |
| 표시 간격 최대(1초 창) | 50~75ms | 18~60ms(대부분 30~50ms) |
| 수신 → 표시 평균 | 24.8ms | 13.0ms |
| 자동 프레임 간격 | 2분 동안 30fps로 2번 내려감 | 매 프레임 유지(측정 구간) |

그 뒤 처리(12.8): 남아 있던 33~50ms 간격은 게임이 같은 화면을 그린 프레임이었고, 자동 프레임 간격 기준 · 표시 일정 · `decodeQueueSize` 감시 · 시간 기준 역압을 넣었습니다.

### 12.8 터치할 때만 끊기던 문제: 폰 120Hz 전환 + 도착 순서 표시 (2026-11-13)

> **정정(12.9)**: 이 절의 원인 설명은 일부만 맞았습니다. 120Hz 전환으로 간격이 섞이는 현상은 실제로 있고 표시 일정이 줄여 주지만, 소유자가 본 "탭하는 순간 끊김"의 주원인은 **손가락이 닿아 있는 동안 Chrome 메인 스레드가 영상 수신을 미루는 것**이었습니다. 이 절의 측정은 누르는 시간이 없는 주입 탭(`input tap`)이라 그 현상이 재현되지 않았습니다. 60Hz 고정에서도 끊긴다는 소유자 확인으로 드러났습니다.

증상: 손을 대지 않으면 고른데, 탭(한 번 누르기)만 해도 끊겨 보였습니다.

원인: 폰(Galaxy Z Flip5, 가변 주사율)은 전체 화면 페이지에서 평소 60Hz로 그리다가 **터치하면 120Hz로 올라갑니다**(rAF 실측 60회/초 → 113회/초, 탭 간격 1.5초 동안 계속 유지). 페이지는 프레임을 "디코딩이 끝난 순서대로 다음 화면 갱신에" 그렸는데, 도착 · 디코딩 시간의 흔들림(수 ms)이 60Hz에서는 16.7ms 칸에 묻히지만 120Hz에서는 8.3ms 칸이라 60fps 영상이 8 / 17 / 25ms 간격으로 섞여 그려졌습니다. 서버 · Unity 쪽 원인은 아니었습니다(아래 표: Unity 프레임 시간, 도착 간격은 터치 여부와 무관).

확인한 것(터치 1번당):

- 폰 페이지: `pointerdown`/`pointerup`에서 JSON 1개씩 전송, 움직임은 rAF당 포인터별 1개(드래그 실측 59~61개/초). 탭이 켜는 픽셀 읽기나 전체 화면 재요청은 없습니다.
- 링크: 터치는 입력 소켓, 영상과 수신 확인은 영상 소켓으로 따로 갑니다. 터치 중에도 도착 간격 40ms 이상은 0.0~0.2%로 같았습니다.
- 서버 · Unity: 주입(`InjectUpdate`)은 프레임당 0.03~0.06ms(첫 호출만 약 4ms), 받은 메시지는 전부 적용, 탭 전후 Unity 프레임 시간 최대 18~21ms로 차이 없음. Unity 프레임이 45~106ms로 튀는 일은 터치와 무관하게 10초에 1번쯤 있었습니다(에디터/게임 쪽).
- 게임이 탭에 반응하며(점프, 효과음 등) 에디터 프레임이 튀는지는 확인하지 못했습니다. 측정 때 게임이 멈춘 화면이어서 테스트 패턴으로 쟀습니다.

해결: **표시 일정**(페이지, 기본 켬, `?sched=0`으로 끔).

- 서버가 프레임 헤더에 캡처 시각을 넣습니다(프로토콜 2, 헤더 28바이트).
- 표시 예정 시각 = 캡처 시각 + base + delay. base는 최근 10초 중 가장 빨리 온 프레임의 "디코딩 완료 − 캡처"(두 기기 시계 차이 포함), delay는 최근 120장의 흔들림 95% 지점 + 2ms(처음 16.7ms, 범위 3~25ms)라 흔들림이 커지면 늘고 안정되면 줄어듭니다.
- 화면 갱신마다 예정 시각이 지난 프레임 중 가장 새 것 1장을 그리고 더 오래된 것은 닫습니다(H.264는 디코딩이 끝난 뒤라 버려도 뒤 프레임에 영향 없음).
- 예정 시각이 갱신 시각에 걸쳐 한 칸씩 흔들리지 않게 칸 가운데로 맞추는 보정(phase)을 두고, Unity fps와 폰 주사율 차이로 보정이 3/4칸을 넘으면 한 칸 넘깁니다(`gvr.sched.slips`).
- 주사율은 rAF 간격으로 재므로 프레임이 오는 동안에는 대기열이 비어도 rAF를 이어 갑니다(프레임이 끊기면 0.3초 뒤 멈춤).

결과(Z Flip5, USB adb reverse, H.264 720x1280 6Mbps, 전체 화면, 테스트 패턴 60fps, 각 9.5초, 표시 일정 끔 → 켬). 터치는 `adb shell input tap` / `input swipe`로 넣은 것이라 손가락과 똑같지는 않습니다.

| 항목 | 무터치 | 탭(1.5초마다) | 드래그(연속) |
|---|---|---|---|
| 폰 화면 갱신(rAF) | 60회/초 | 113회/초 | 114~115회/초 |
| 고르지 않은 표시 간격(9ms 미만 또는 25ms 초과) | 0.4% → 0.0% | **16.2% → 1.1%** | **15.9% → 0.6%** |
| 표시 간격 25ms 초과 / 40ms 초과 | 0.4% → 0.0% / 0 → 0 | 6.0% → 0.4% / 0 → 0 | 6.2% → 0.2% / 0 → 0 |
| 표시 간격 최대 | 33.7 → 21.8ms | 34.1 → 34.2ms | 33.7 → 34.7ms |
| 도착 간격 40ms 이상 | 0.2% → 0.2% | 0.0% → 0.2% | 0.0% → 0.2% |
| 표시 fps | 59.7 → 59.8 | 60.1 → 60.0 | 59.9 → 59.9 |
| 그리지 않고 버린 프레임 | 0.4% → 0.2% | 0.4% → 0.2% | 0.4% → 0.2% |
| 캡처 → 표시 평균(시계 차이 제외) | 35.7 → 28.3ms | 17.2 → 25.0ms | 15.5 → 25.2ms |
| 터치 → 표시 평균 | — | 54.6 → 61.9ms (10회) | 47.8 → 57.8ms (4회) |
| Unity 프레임 시간 최대 | 45 / 52ms | 22 / 20ms | 21 / 47ms |
| 터치 메시지(보냄 = 적용) | 0 | 10개 | 583 / 564개(약 60개/초) |

대가: 120Hz 상태에서는 예전 방식이 "오는 대로 바로" 그려 지연이 가장 짧았으므로, 고르게 그리는 대신 캡처 → 표시가 8~10ms, 터치 → 표시가 7~10ms 늘었습니다. 60Hz 상태(무터치)에서는 지연이 늘지 않았습니다.

무선 adb(같은 폰, 같은 조건, 끔 → 켬): 고르지 않은 간격 무터치 2.9% → 0.8%, 탭 28.8% → 3.8%. 캡처 → 표시 31.5 → 39.1ms / 19.9 → 32.4ms, 터치 → 표시 73.5 → 80.6ms. 무선은 전송이 100~290ms씩 밀리는 순간이 있어(도착 − 캡처 초과 40ms 이상 1.4~5.9%) 그때의 멈춤은 표시 일정으로 없어지지 않습니다.

함께 넣은 것:

- **같은 화면 건너뛰기 확인(12.7의 남은 33~50ms 간격)**: `GET /stats` 기록으로 보면 그 프레임들은 Game 뷰가 다시 그려졌는데(화면 카메라 렌더 있음) 그림이 같았습니다. 게임 화면이 실제로 같은 그림이었던 것이고(예: 8fps 스프라이트 화면에서 480장 중 415장), 캡처 누락 · 리드백 지연 · 중복 판정 오류 · FPS 제한 문제가 아닙니다. 매 프레임 그림이 바뀌는 테스트 패턴에서는 건너뛴 프레임 0, 60장/초가 모두 도착했습니다. 에디터 프레임 간격은 p50 16.7 / p90 17.3 / p99 20ms입니다(`targetFrameRate` 60, VSync 끔).
- **디코더 상태 감시**: `decode()` 전에 `decodeQueueSize`가 6을 넘으면(첫 출력 뒤부터) 디코더를 버리고 `{t:"key"}`를 보냅니다. 답이 없으면 1.5초마다 다시 요청합니다. 서버는 인코더를 다시 시작해 설정 + 키프레임을 보냅니다(실측 약 0.43초 공백). ffmpeg CLI로는 실행 중 임의 시점 IDR을 강제할 방법을 찾지 못해 재시작을 유지했습니다. 키프레임 요청이 와 있으면 같은 화면이어도 보냅니다.
- **H.264 역압을 시간 기준으로**: "확인 못 받은 4장"이 아니라 가장 오래된 미확인(또는 아직 못 보낸) 프레임의 나이가 150ms(`MAX_H264_BACKLOG_MS`)를 넘으면 더 보내지 않고 캡처 쪽이 인코딩 전에 건너뜁니다. MJPEG는 최신 1장 슬롯 + 2장 그대로입니다.
- **자동 프레임 간격 기준**(12.4 표). 페이지의 디코딩 비용 보고는 평균 대신 중앙값입니다(페이지를 막 연 직후의 몇 장 때문에 26.8ms로 보고돼 30fps로 내려간 적이 있음).
- **진단 도구**: `GET /stats`, 창의 "테스트 패턴(끊김 확인용)" 토글 / `GET /debug?pattern=1`(일정한 속도로 가로지르는 네모. 게임 화면이 멈춰 있어도 60fps로 보내지고 끊김이 눈에 보임), 폰 디버그 표시의 `sched … late … slip … vs`.
- 입력 연결이 새로 붙으면 `inputSeq`를 0으로 되돌립니다(페이지를 새로 연 뒤 터치 → 표시 시간이 실제보다 짧게 나오던 문제).

확인하지 못한 것:

- 실제 손가락 터치와 실제 게임 플레이(탭에 게임이 반응할 때의 에디터 프레임 시간).
- 시간 기준 역압은 PC의 스크립트 클라이언트로만 확인했습니다(확인을 1.5초 멈추면 약 150ms 분량 뒤 전송이 멈추고 72장을 인코딩 전에 건너뜀). 실제로 포화된 링크에서는 보지 못했습니다.
- `decodeQueueSize` 감시가 실제로 걸리는 상황(느린 폰, 소프트웨어 디코딩)은 만들지 못했습니다. 요청 → 재시작 → 복구 경로만 확인했습니다.
- 다른 폰. 120Hz 전환 조건은 기기와 설정에 따라 다릅니다.

선택지(이번 범위 밖, 예상 효과):

- 캡처 시점을 "다음 프레임 시작"에서 "Game 뷰 렌더 직후"로 옮기기: 프레임 제한 대기 시간(약 10ms로 추정, 미측정)만큼 지연이 줄어 표시 일정의 대가를 상쇄할 수 있습니다. Overlay UI가 빠질 위험이 있어 검증이 필요합니다.
- NVENC 네이티브 플러그인(ffmpeg 대체): 요청 즉시 IDR(0.43초 → 1프레임), 리드백과 파이프 복사 제거로 수 ms 단축. 작업량과 에디터 크래시 위험이 큽니다.
- WebRTC: 무선의 100ms 넘는 정체에 가장 효과적이지만 `adb reverse`(TCP)로는 못 쓰고 구조를 새로 짜야 합니다.

### 12.9 탭하는 순간 끊김의 실제 원인: 터치 중 메인 스레드 수신 지연 → 영상 워커 (2026-11-13)

**증상(소유자, 손가락)**: 에디터에서 마우스로 클릭하면 안 끊기는데 폰에서 탭하면 그 순간 끊깁니다. 폰을 60Hz 고정(표준)으로 바꿔도 끊깁니다.

**원인(측정)**: 손가락이 화면에 닿아 있는 동안(누른 시간 p50 62ms, p90 114ms) 폰 페이지의 영상 소켓 `onmessage`가 불리지 않습니다. PC는 그동안에도 16.7ms마다 캡처해 보내고 화면 갱신(rAF)도 정상인데, 프레임은 손을 떼는 순간(또는 손가락이 움직이기 시작할 때) 한꺼번에 전달됩니다. 그래서 탭마다 화면이 누른 시간만큼 멈췄다가 건너뜁니다. 수신 확인(`"a"`)도 같이 밀립니다.

- 실제 손가락 기록(무선, 60Hz, 메인 스레드 경로, 누른 시간 30ms 이상 58회): 누르는 동안 캡처된 196장 중 131장(67%)만 그 사이에 전달됐고, 63장은 손을 뗀 직후 12ms 안에 몰려 전달됐습니다. 약 60%의 누르기에서 전달이 0장이었고 전달 간격은 누른 시간 + 약 17ms(50~170ms)였습니다. 그 탭들에서 Unity 프레임은 정상이었습니다(터치를 넣은 프레임과 다음 두 프레임 최대 18.5 / 18.5 / 20.7ms, 80회 중 25ms 초과 0회, 주입 0.0~0.1ms).
- 주입으로 재현: `adb shell input swipe x y x y 120`(움직임 없이 120ms 누르기). 메인 스레드 경로에서 전달 간격 128~155ms, 화면 정지 117~136ms. 누르는 시간이 없는 `input tap`이나 움직임이 있는 swipe로는 재현되지 않습니다.
- 추정(확인 못 함): Chrome(Blink) 메인 스레드 스케줄러가 터치 시작 응답을 우선하느라 네트워크 수신 같은 작업 큐를 미루는 정책. 내부 동작은 소스에서 확인하지 않았고, "메인 스레드에서 받으면 생기고 워커에서 받으면 안 생긴다"는 것만 측정했습니다.

**수정: 영상 워커(기본 켬, `?worker=0`으로 끔)**. 영상 소켓 수신, H.264/MJPEG 디코딩, 표시 일정, 그리기를 워커에서 합니다(`gvrVideoWorker`, 캔버스는 `transferControlToOffscreen`). 메인 스레드는 터치 입력(입력 소켓), 배치 크기 전달, 통계 표시만 합니다. 워커를 못 쓰는 브라우저와 `?desync=1`은 예전 메인 스레드 경로를 씁니다. 검은/손상 프레임 픽셀 검사(11.5)는 메인 스레드 경로에만 있습니다.

결과(Z Flip5, 60Hz 고정, H.264 720x1280 6Mbps, 전체 화면, 테스트 패턴 60fps, 움직임 없는 120ms 누르기 5회, 각 9.5초):

## 13. 무선(adb 무선) + H.264

### 13.1 무선 연결

- 방법: PC가 폰에 adb로 무선 접속(PC → 폰)하고 그 위에 `adb reverse`를 겁니다. 폰은 USB와 똑같이 `http://localhost:7300/`을 엽니다. PC로 들어오는 연결이 없어서 **방화벽 변경 없이** 됩니다. scrcpy의 무선 방식과 같습니다.
- 창 "USB 폰을 무선으로 전환": `adb tcpip 5555` → 폰 `wlan0` IP 확인(`ip -f inet addr show wlan0`) → `adb connect IP:5555` → `adb reverse`. Android 11+ 무선 디버깅은 "페어링"(`adb pair`) → "연결". 마지막 주소를 `GVR_WirelessAddress`에 기억해 Start 때 기기가 없으면 다시 연결합니다. adb 명령은 10초 제한.
- 실측(이 PC/공유기, 폰 2.4GHz 802.11n, 링크 104/72Mbps, RSSI −46): **adb 무선 처리량 8.3Mbps**(20MB push 20.3초), USB 176Mbps. 영상 중 폰 `wlan0` 수신 10~15Mbps가 상한이었습니다. 왕복(입력 소켓 RTT) 7~22ms.

### 13.2 무선에서 MJPEG가 끊긴 이유

- MJPEG는 프레임마다 통째로 보냅니다. 720x1280 q10도 약 50~64KB라 30fps면 약 12~15Mbps → 무선 adb 터널을 넘습니다. 실측 100% q10: 18.8fps. 전송 해상도 50% + q40: 28fps(로비 화면 내용 속도와 같음, 360x640).
- 영상 전송이 수신 확인 1장씩(왕복마다 1장)이라 무선 왕복 지연(약 20ms)에 묶였습니다 → **동시에 2장(H.264는 4장)까지 보내도록**(파이프라인) 바꿨습니다. 자동 프레임 간격의 비용은 "링크가 바쁠 때 수신 확인 간격(= 한 장당 실제 전송 시간)"으로 봅니다(왕복 지연 자체는 처리량을 제한하지 않으므로 쓰지 않음).
- 폰 → PC 미러링(scrcpy, Orca 에뮬)이 부드러운 이유: 폰 하드웨어 인코더 H.264(기본 8Mbps, 무선은 2Mbps 정도 권장)라 데이터가 MJPEG의 수분의 1입니다.

### 13.3 H.264 경로

```
캡처(RGBA, GPU에서 행 순서를 ffmpeg용으로) → [인코더 스레드] stdin ─▶ ffmpeg h264_nvenc ─▶ stdout FLV
  → [H264 리더 스레드] FLV 태그(길이 앞에 있음) 1개 = 프레임 1장, 첫 태그 = avcC 설정 → 서버 순서 큐(버리지 않음) → ws /video
폰: 헤더 flags & 2 → 받은 순서대로 VideoDecoder.decode(EncodedVideoChunk) → VideoFrame → rAF 그리기 대기열(최대 2장)
```

- ffmpeg 인자: `-f rawvideo -pix_fmt rgba -s WxH -framerate 60 -i pipe:0 -c:v h264_nvenc -preset p1 -tune ull -zerolatency 1 -delay 0 -bf 0 -g 600 -rc cbr -b:v {kbps}k -maxrate {kbps}k -bufsize {kbps/30}k -profile:v high -flush_packets 1 -f flv pipe:1`. NVENC가 `rgba`를 바로 받아 CPU 색 변환이 없습니다.
- 실측 파이프(720x1280, 5Mbps): 입력 → FLV 태그 p50 3.0ms, p95 3.5ms, 시작 약 0.3초, 프레임 약 10KB.
- 선택 규칙: "H.264 사용"이 켜져 있고(기본), 영상 클라이언트가 **1개**이며 그 페이지가 `{t:"caps", h264:1}`(WebCodecs `isConfigSupported` + 보안 컨텍스트)를 보냈고, ffmpeg가 있으면 H.264. 아니면 MJPEG. 창 `Codec` 줄에 지금 형식과 이유.
- 키프레임: 새 클라이언트, 크기/비트레이트 변경, 페이지의 `{t:"key"}`(디코딩 오류) 때 인코더를 다시 시작 → 설정(avcC) + IDR이 바로 나옵니다. 페이지는 설정이 오면 디코더를 새로 만들고, 키프레임 전 델타는 버립니다.
- 역압: H.264는 앞 프레임에 기대므로 인코딩한 뒤에는 버리지 않습니다(서버 `ordered` 큐). 가장 오래된 미확인(또는 아직 못 보낸) 프레임의 나이가 150ms를 넘으면(예전: 4장) 다음 캡처는 **인코딩 전에** 건너뜁니다(전송 버림으로 세어 자동 프레임 간격이 봄, 12.8). 같은 화면은 보내지 않습니다(디코더가 마지막 화면을 유지).
- 행 순서: Unity `EncodeArrayToJPG`는 맨 아래 행부터, ffmpeg rawvideo는 맨 위 행부터. D3D11에서 JPEG일 때만 GPU에서 뒤집고 H.264일 때는 그대로 둡니다. 형식이 바뀌는 순간 방향이 다른 프레임은 인코더 스레드가 행을 바꿉니다(약 1ms). 처음 구현에서 H.264 화면이 위아래로 뒤집혀 찾았습니다.
- WebCodecs는 보안 컨텍스트에서만 됩니다: `http://localhost`(USB/무선 adb reverse) 가능, `http://<PC IP>`(Wi-Fi 직접 접속) 불가 → 그 경우 MJPEG.
- ffmpeg 버전: master/9.0은 NVENC API 13.1(드라이버 610 이상)을 요구해 이 PC(드라이버 591.66, API 13.0)에서 실패했습니다. **8.1에서 동작.** 실패하면 `[GVR] H.264 unavailable, using MJPEG: …` 로그와 창 표시 후 MJPEG.

### 13.4 결과 (무선 adb, 폰 Z Flip5, 2.4GHz)

| 설정 | 해상도 | 프레임 | 폰 표시 fps | 무선 사용량 | 폰 디코딩 | 터치 → 화면 |
|---|---|---|---|---|---|---|
| MJPEG 100% q10 | 720x1280 | 64KB | 18.8 | 10.6Mbps | 14.9ms | — |
| MJPEG 50% q40 | 360x640 | 50KB | 28(로비) | 12.1Mbps | 7.9ms | — |
| **H.264 6Mbps 100%** 로비 | 720x1280 | 12KB | **29.6**(화면 내용 속도) | **3.5Mbps** | 3.8~7.5ms | **평균 68ms**(15회) |
| **H.264 6Mbps 100%** 계속 점프 | 720x1280 | 12KB | **38.1** | **4.0Mbps** | 6.1ms | **평균 70ms**, p50 65, p90 96(45회) |

- 서버(H.264): 인코딩 2.9~5.7ms, 캡처 → 전송 6.3~10ms(MJPEG 약 14ms), 캡처 60/s 가능. 이상 프레임 0.
- 남은 끊김: 계속 점프 측정에서 frameId 건너뜀이 5.7%였습니다. **처음에 이를 "인코딩 전 건너뜀"으로 적었으나 틀렸습니다.** H.264의 frameId는 ffmpeg 출력 때 매기므로 인코딩 전 건너뜀은 frameId 건너뜀으로 나타나지 않습니다. 서버는 H.264 프레임을 버리지 않으니, 이 건너뜀은 폰 쪽(표시 대기열)에서 버려진 것으로 봅니다(프레임이 몰려 도착한 경우로 추정, 미확인). 실제 인코딩 전 건너뜀은 누적 39,160캡처 중 434건(1.1%)입니다. 또한 그 38.1fps 측정은 화면을 보지 않고 탭했으므로 게임 오버 같은 정지 구간이 섞였을 수 있습니다. 5GHz나 USB에서 60fps가 된다는 것은 예상이며 측정하지 않았습니다.
- H.264 ↔ MJPEG 전환(설정 토글), 서버 재시작, 페이지 새로 고침 뒤 H.264 자동 재개를 확인했습니다. 디코딩 오류 → 키프레임 요청 경로는 실제로 오류가 나지 않아 시험하지 못했습니다.

## 14. 알려진 문제

1. Wi-Fi **직접 접속**(`http://<PC IP>`)은 이 PC의 Windows 방화벽(공용 프로필 + `Unity 2022.3.62f2 Editor` 차단 규칙)에 막혀 있습니다. 무선은 **adb 무선 + adb reverse**(13장, 방화벽 무관)를 씁니다. 직접 접속은 보안 컨텍스트가 아니라 H.264(WebCodecs)도 안 되고 MJPEG만 됩니다.
2. 실기기 멀티터치는 `adb shell input`이 멀티터치를 지원하지 않아 직접 만져서만 확인할 수 있습니다(브라우저 하네스에서는 통과).
3. Play 중 도메인 리로드 뒤 서버는 다시 열리지만, 게임이 리로드를 견디지 못합니다.
4. Game 뷰 탭이 가려지면 엔진이 Game 뷰를 그리지 않아 폰 화면이 멈춥니다(검게 되지는 않음). 0.7초 안에 창과 폰에 이유를 표시하고 "Game 뷰 보이기" 버튼을 줍니다. 강제로 그리는 방법은 찾지 못했습니다(5장). Unity 창 최소화는 시험하지 않았습니다(같은 경고가 "그 밖" 이유로 뜰 것으로 예상).
5. 보안: Chrome 페이지가 붙는 서버는 `127.0.0.1`에만 열려 USB(adb reverse)나 무선 adb 로만 접속됩니다(인증 없음, 루프백 한정). 같은 Wi-Fi 에서 들어오는 연결은 QR 의 토큰으로 인증된 앱만 받습니다(17장). 인증 뒤의 영상과 터치는 평문입니다.
6. 1080p 이상에서는 인코더 스레드 1개 기준 프레임당 약 20~25ms로 예상합니다(미측정). 필요하면 인코더 스레드를 늘립니다.
7. 무선 adb + `adb reverse`, "폰에서 열기"는 실기기에서 확인했습니다(13장). USB 케이블을 뽑은 상태로는 시험하지 못했습니다(케이블은 꽂혀 있었고 영상은 Wi-Fi로 흐름을 폰 `wlan0` 수신량으로 확인). H.264 디코딩 오류 → 키프레임 요청 경로는 오류가 나지 않아 시험하지 못했습니다.
8. MJPEG(q80 · 60fps)는 프레임마다 JPEG 배열을 새로 만들어 에디터 GC 빈도를 약 2배로 올립니다(12.6). H.264는 프레임이 약 12KB라 이 문제가 거의 없습니다.
9. H.264는 영상 클라이언트가 1개일 때만 씁니다(여럿이면 MJPEG). NVIDIA(NVENC)에서만 시험했습니다(AMD/Intel은 ffmpeg 인자 변경 필요: `h264_amf`/`h264_qsv`).
10. 2.4GHz Wi-Fi에서는 지연이 튈 때 고른 30fps로 내려갑니다(13.4). 5GHz를 권장합니다.

### 17.3 QR (`GameViewRemoteQr.cs`, `ThirdParty/QrCodeGenerator/`)

- 내용(QR 형식 1): `http://<주 주소>:<포트>/c#v=1&s=<서버 표시 8자>&t=<토큰 22자>[&a=<다른 주소>,…(최대 3개)]`. 실제 문자열은 서버 쪽 `GameViewRemoteHost.BuildQrPayload()` 가 만들고, 창은 그것을 그대로 인코딩합니다. `GameViewRemoteQr.BuildPayload` 는 같은 형식을 만드는 순수 함수로, 자체 점검과 시험에 씁니다.
- 인코더: `manuelbl/QrCodeGenerator` **v2.0.6** 의 핵심 파일 7개를 소스로 넣었습니다(MIT, 네임스페이스만 `GameViewRemoteThirdParty.QrCodeGenerator` 로 바꿈, `NOTICE.md`). 인터넷과 외부 서비스를 쓰지 않습니다. Unity 2022.3(C# 9, .NET Standard 2.1)에서 경고 없이 컴파일됩니다.
- 인코딩: UTF-8 바이트, **바이트 모드**, 오류 정정 **M 이상**(같은 버전에 들어가면 인코더가 Q/H 로 올림), 버전은 내용 길이에 맞는 가장 작은 것, 마스크는 벌점이 가장 작은 것.

| 내용 | 바이트 | QR 버전(모듈) | 오류 정정 M 용량 |
|---|---|---|---|
| 주소 1개(`10.0.0.2`) | 62 | 4 (33×33) | 62 |
| 설계의 예(주 주소 + 다른 주소 1개) | 81 | 5 (37×37) | 84 |
| 가장 긴 경우(15자 주소 4개, 포트 5자리) | 120 | 7 (45×45) | 122 |

- 그리기: 흰 바탕, 검은 모듈, **둘레 여백 4모듈**, 모듈 하나 = 정수 픽셀(4 이상), `FilterMode.Point`, 텍스처 1픽셀 = 화면 1픽셀(`EditorGUIUtility.pixelsPerPoint` 로 나눠 배치). 한 변은 보통 300포인트 안쪽(버전 5에서 모듈당 6px = 270px), `[QR 크게]` 는 520포인트 안쪽.
- `Texture2D` 는 아래 줄이 먼저라 줄 순서를 뒤집어 넣습니다. 뒤집지 않으면 거울상이 되어 읽히지 않습니다(자체 점검이 확인).
- `[QR 이미지 저장]`: 창이 그리는 그 텍스처를 `Temp/GameViewRemote/qr.png` 로 저장합니다.
- 자체 점검: 메뉴 `Tools > Game View Remote > QR Self Test`. 규격 예제의 리드-솔로몬 값, 버전 1~10 의 바이트 용량 경계, 설계 예제의 버전, 위치 찾기/타이밍 무늬와 형식 정보(오류 정정, 마스크, BCH)를 인코더와 무관한 코드로 다시 읽기, 여백과 정수 픽셀, 텍스처 방향, 내용 만들기와 토큰 가리기를 확인합니다.

### 17.4 창과 서버 쪽 사이

창(`GameViewRemoteHostGUI.cs`, `GameViewRemoteWindow.cs`)은 서버 쪽 클래스(`GameViewRemoteHost`, `GameViewRemoteFirewall`, `GameViewRemoteAppAdb`, `GameViewRemoteSeats.Viewer`)를 **직접 부릅니다.** 처음에는 두 작업자가 같은 폴더를 동시에 고치느라 이름으로 찾아 부르는 어댑터(`GameViewRemoteHostLink`)를 두었고, 통합 단계에서 없앴습니다. 멤버 이름을 바꾸면 이제 컴파일 오류로 드러납니다.

### 17.5 없앤 것: "Wi-Fi 접속 허용" 토글

- 무엇: 창의 토글(`GVR_AllowLan`), 그 아래의 Wi-Fi URL 목록, 방화벽 `netsh` 안내. 서버는 이제 항상 `127.0.0.1` 에만 엽니다.
- 왜: 인증 없이 `0.0.0.0` 에 여는 길이라 같은 네트워크의 누구나 화면을 보고 조작할 수 있었습니다(설계 리뷰 M1, 조정자 결정 브리프 3.3의 1번).
- 대신: 같은 Wi-Fi 는 QR + 앱(인증 있음). Chrome 페이지를 무선으로 쓰려면 무선 adb(13장).
- 잃는 것: 폰 Chrome 에서 PC 주소로 페이지를 직접 여는 방법. 그 경로는 MJPEG 만 됐고 이 PC 에서는 방화벽에 막혀 쓰이지 않았습니다(14장 1번).

### 17.6 Chrome 페이지의 변경

- `[여기서 보기]` 버튼 하나를 더했습니다. 서버가 `{"t":"s","stale":true,"code":"standby","msg":…}` 를 보내면(다른 기기가 영상을 받는 중) 화면 가운데에 버튼이 나오고, 누르면 영상 소켓으로 `{"t":"take"}` 를 보냅니다(워커 경로에서는 메인 → 워커 `postMessage({t:'take'})`). `stale:false` 가 오거나 연결이 끊기면 사라집니다.
- 그 밖의 동작(주소, 프레임 형식, `caps`/`a`/`key`, 입력, 표시 일정, 워커)은 바꾸지 않았습니다. 앱이 붙지 않으면 `code` 가 `standby` 인 메시지는 오지 않으므로 페이지는 예전과 같습니다.
