# 02. PRD 리뷰 (2단계, 독립 리뷰)

- 작성: 2026-11-13 밤 (2단계 워커). 이 단계에서 쓴 파일은 이 문서 하나입니다. 다른 파일, 폰, Unity, 방화벽은 건드리지 않았습니다.
- 대상: `docs/01_research.md`(이하 "조사"), `docs/02_PRD.md`(이하 "PRD").
- 기준: `docs/00_BRIEF.md` 2장(소유자 요구사항), 3장(질문), 6장(문서 규칙), `docs/00_current_system_and_history.md`(이하 "00 문서").

## 0. 결론

**조건부로 설계에 넘길 수 있습니다.** 방향(폰이 PC로 거는 TCP, `http://` QR 하나, 앱에서 AVCC 변환, 프로토콜 2 유지, UDP는 측정 뒤 판단)은 근거가 있고 브리프와 맞습니다. 조사 문서는 확인한 것과 못 한 것을 잘 나눠 적었습니다.

다만 아래 **차단 2건**은 PRD를 고친 뒤에 설계를 시작해야 합니다. 둘 다 PRD 문장 수정으로 끝나고 새 조사가 필요하지 않습니다.

| # | 차단 | 한 줄 |
|---|---|---|
| B1 | 합격 조건이 요점을 증명하지 않음 | 지금 조건대로면 실제 Unity 서버에 무선으로 한 번도 붙지 않고, 실제 게임에서 탭 한 번 안 해 보고도 합격합니다 |

## 2. 차단

### B1. 합격 조건이 "탭하는 동안 부드러운가"를 증명하지 않는다

근거:

- PRD 5.1 합격 조건 1은 "수치가 있어야 함(충족 여부와 무관)"이고, 조건 3의 목록에 NF-1~NF-9가 없습니다. 무선 부드러움은 어떤 값이 나와도 합격입니다. 브리프 요구사항 11은 "합격 기준은 무선이어야"입니다.
- 측정 서버가 "시험 서버 또는 허락된 시간의 실제 서버"입니다(5.1 표). 재생 서버만으로 조건 1을 채울 수 있습니다. 그런데 재생 서버는 입력을 받아 `inputSeq`를 돌려주지 못하므로 NF-6(터치 → 표시)을 잴 수 없고, Unity가 탭에 반응하는 구간이 아예 없습니다.
- 측정 영상이 테스트 패턴뿐입니다(PRD 4.1). 00 문서 3.4.4의 후보 3(게임이 탭에 반응하는 프레임)은 테스트 패턴에서 나타나지 않습니다. 00 문서 8장 3번이 권한 "그 순간의 Unity 프레임 시간 확인"은 PRD 4.2에서 "충족되지 않으면 본다"는 조건부로만 남았습니다.
- 같은 지표(고르지 않은 표시 간격, `adb shell input tap`, 테스트 패턴)는 Chrome 페이지에서 이미 1.1%로 좋게 나왔는데 소유자 눈에는 끊겼습니다(00 문서 3.4.3, 3.4.4). 이 지표만 다시 재면 같은 결과를 얻고 같은 질문이 남습니다.
- NF-4의 기준 0.5%p는 10초 구간(약 600장)에서 3장 차이입니다. 10초 × 3회로는 Chrome의 1.1%p와 구분되지 않습니다.
- 비교 대상이 00 문서의 옛 수치입니다. 그 수치는 `drawImage` 호출 시각으로 잰 것이고(00 문서 3.4.4), 앱은 시스템이 알려 준 표시 시각으로 잽니다(F-92). 같은 것을 재지 않습니다.

고칠 것:

1. PRD 5.1 합격 조건을 아래로 바꿉니다.
   - 조건 1: **실제 Unity 서버**에 **무선 LAN 직접**(중계를 거쳤으면 그렇게 표시)으로 붙어 NF-1~NF-9를 잽니다. 재생 서버 수치는 앱 단독 기준선으로 따로 적고 합격 근거로 쓰지 않습니다.
   - 조건 2: 결과를 셋 중 하나로 판정합니다. (가) NF-2~NF-5 충족 → 합격. (나) 미충족이고 같은 구간의 서버 `/stats` 프레임 시간이나 `transportStride`에 원인이 보임 → "Unity 쪽"으로 판정, 증거 첨부. (다) 미충족이고 도착 간격에 원인이 보임 → "링크"로 판정, 4.6절로. 셋 어디에도 안 들어가면 미합격입니다.
2. PRD 4.1에 측정 구간을 추가합니다: **실제 게임 화면에서 탭**(게임이 반응하는 화면). 앱의 프레임별 기록(F-93)과 서버 `/stats`의 `frames`를 캡처 시각으로 맞춰 탭 전후 200ms의 Unity 프레임 시간과 앱 표시 간격을 나란히 냅니다.
3. NF-3, NF-4의 정의를 "탭 전후 ±200ms 창 안의 고르지 않은 간격 비율 대 그 밖"으로 바꾸고, 구간을 60초 이상(탭 40회 이상)으로 늘립니다.
4. PRD 4.1의 "비교 대상"을 "같은 날, 같은 경로, 같은 구간으로 다시 잰 Chrome 페이지 수치"로 바꿉니다. 지표 정의가 다르다는 것(그리기 호출 시각 대 표시 시각)을 표에 적습니다.
5. F-93에 추가: 소유자가 손가락으로 탭하는 구간을 워커 없이 남길 수 있게 HUD에 [기록 시작/끝] 하나를 둡니다. 실제 손가락 수치를 얻는 길이 이것뿐입니다.
6. PRD 4.2 표의 USB 열에도 "잠정"을 붙입니다. 앱으로 잰 USB 수치도 아직 없습니다.

### B2. "나중에 붙은 쪽이 영상"은 Chrome 페이지와 서로 뺏는다

근거: `GameViewRemotePage.html:335, 754, 927`. 페이지는 소켓이 닫히면 0.7초 뒤 다시 붙습니다. F-39 권장안대로 먼저 쪽을 끊으면 페이지가 0.7초 뒤 "나중에 붙은 쪽"이 되어 앱을 밀어내고, 앱은 F-40으로 다시 붙어 페이지를 밀어냅니다. 끊지 않고 대기 상태로 두더라도 페이지를 새로 고치면 같은 일이 생깁니다. PRD 2.6의 "다른 기기가 연결했습니다"와 F-40(스스로 다시 시도)도 서로 충돌합니다.

고칠 것:

- F-39를 "영상을 받는 클라이언트는 1개이고, 자리를 내준 쪽은 **연결을 유지한 채** 대기 상태 문구만 받는다(끊지 않는다). 우선순위는 인증된 앱 > 루프백 페이지. 같은 종류끼리는 사람이 누른 쪽"으로 바꿉니다.
- F-40에 "서버가 '자리 내줌'을 알린 경우에는 자동으로 다시 뺏지 않고 [여기서 보기] 버튼을 낸다"를 추가합니다.
- 자리를 내준 쪽의 입력 소켓도 받지 않아야 합니다(00 문서 1.5.6: 입력 번호는 입력 연결이 0 → 1일 때만 초기화. 두 입력 연결이 있으면 F-95의 터치 → 표시가 틀립니다).
- 이 규칙은 `SingleH264Client`와 페이지 양쪽을 고치는 일이라 다른 워커의 파일을 건드립니다(조정자 결정 C3).

## 3. 중대

### M1. 평문 트래픽 규칙이 빠졌다 (실기기에서 연결 자체가 안 될 수 있음)

- 근거: 대상 SDK 36이면 평문이 기본 차단입니다("cleartext support is disabled by default"). `HttpURLConnection`, OkHttp, `DownloadManager` 같은 상위 스택은 `ws://`와 `http://`를 거절합니다. `Socket`을 직접 쓰면 해당하지 않습니다. 조사와 PRD에 이 내용이 없고, D11은 WebSocket 구현을 정하지 않았습니다. F-25의 [업데이트](APK 받기)도 같은 규칙에 걸립니다.
- 고칠 것: F-50 옆에 요구사항 추가. "앱은 사설 주소로 평문 연결을 한다. 매니페스트에서 평문을 허용하고(주소가 임의의 사설 IP라 도메인별 설정으로는 나열할 수 없음), 영상/입력 WebSocket은 `Socket` 위에 직접 구현한다." 직접 구현은 "메시지 1개 = 쓰기 1번"(F-54)과 M3의 망 지정에도 필요합니다. 라이브러리를 쓴다면 헤더와 내용을 한 번에 쓰는지 확인하는 항목을 설계에 넣습니다.

### M2. QR 설치 흐름(흐름 B)이 실기기에서 한 번도 확인되지 않았다

- 근거: 조사 3.1, 4.1, 4.3, 10장 1·3·4번. 삼성 인터넷의 `intent://` + 대체 주소, 평문 사설 주소에서의 APK 내려받기 경고, 자동 차단 상태가 모두 미확인입니다. PRD 2.3의 탭 수는 예상입니다(PRD도 그렇게 적었습니다). 나도 문서로 확인하지 못했습니다. 이 흐름은 요구사항 3의 절반입니다.
- 고칠 것: PRD 5.1에 "5단계 첫 작업(앱 코드를 쓰기 전)"을 추가합니다.
  1. `node.exe`로 정적 서버를 LAN 포트에 띄워 폰 셸의 `nc`로 닿는지 확인합니다(양성 대조. 조사 1.3은 막힌 포트만 시험했습니다. 이것이 실패하면 방화벽이 아니라 공유기가 원인입니다).
  2. 빈 APK(조사 1.4에서 만든 것)와 착륙 페이지 초안을 그 서버에 두고, adb로 그 주소를 삼성 인터넷과 Chrome에 열어 내려받기와 설치 화면을 끝까지 기록합니다.
  3. `intent://…;S.browser_fallback_url=…;end` 버튼이 앱이 있을 때와 없을 때 어떻게 되는지 두 브라우저에서 기록합니다.
- 결과가 "막힘"이면 QR 설치의 기본 흐름을 바꿔야 하므로 Unity 쪽(6단계) 전에 알아야 합니다. 브라우저 화면을 adb로 누르는 것은 조정자 결정 C2입니다.

### M3. 인터넷이 없는 Wi-Fi, 모바일 데이터, VPN (NF-43이 지금 요구사항으로는 보장되지 않음)

- 근거(리뷰어 지식, 문서 미확인): Wi-Fi에 인터넷이 없으면 Android는 모바일 데이터를 기본 망으로 씁니다. 망을 지정하지 않은 소켓은 기본 망으로 나가므로 `192.168.x.x`에 닿지 않습니다. 폰에 VPN이 켜져 있어도 같습니다. 사내 폐쇄망이 바로 이 경우입니다.
- 고칠 것: F-32에 "연결 소켓은 Wi-Fi 망에 묶는다(`ConnectivityManager`로 Wi-Fi 망을 얻어 `Network.bindSocket`)"를 추가합니다. NF-43에는 "기본 카메라 → 브라우저 경로는 브라우저가 망을 고르므로 보장하지 않는다. 앱 안 스캐너 경로만 보장"이라고 적습니다. 5단계에서 실기기로 확인할 항목으로 올립니다. 폰 설정을 바꿀 수 없으므로 소유자 확인 목록에 넣습니다.

### M4. 처음 설치는 "QR 한 번"이 아니다 (요구사항 4가 조용히 약해짐)

- 근거: PRD 2.3 4단계는 설치 뒤 QR을 한 번 더 찍거나 브라우저로 돌아가게 합니다. 이를 없애는 F-27은 "권장"입니다. 관리자 권한이 없는 PC에서는 QR 경로 자체가 없습니다(PRD 2.2 끝줄).
- 고칠 것: PRD 0장(소유자가 정해야 하는 것)에 두 줄을 올립니다. "처음 설치하는 폰은 QR 2번(또는 QR 1번 + 브라우저로 돌아가 버튼 1번)", "관리자 동의를 못 하는 PC에서는 QR 연결이 안 되고 USB만 됨". F-27은 가장 단순한 형태(착륙 페이지를 닫지 않고 "설치가 끝나면 이 버튼"을 크게 보여 줌)를 필수로 올립니다. 이것은 F-20에 문구 한 줄입니다.

### M5. Play 밖에서 서버를 열면 스크립트를 저장할 때마다 서버가 죽는다

- 근거: `GameViewRemote.cs:487`은 Play 중일 때만 리로드 뒤 다시 열도록 표시를 남깁니다. Play 밖에서는 스크립트를 저장할 때마다 도메인 리로드가 일어나 리스너가 닫히고 다시 열리지 않습니다. F-01은 Play 밖에서도 열라고만 하고 이 경우를 말하지 않습니다. 에디터를 다시 켠 뒤도 같습니다. 그러면 PRD 2.4의 "앱 아이콘 1번(QR 없음)"은 사용자가 Start를 다시 눌렀을 때만 성립합니다.
- 고칠 것: F-01에 추가. "Start 상태는 도메인 리로드를 넘어 유지된다(리로드 뒤 같은 포트, 같은 토큰으로 다시 연다). 에디터를 다시 켰을 때 자동으로 열지는 설정으로 둔다." NF-41에 "Play 밖에서 스크립트 재컴파일 5회"를 추가합니다.

### M6. 인증 절차가 반사 공격에 열려 있고, 인증 뒤 연결은 가로챌 수 있다

- 근거: F-34는 양쪽이 **같은 토큰**으로 서로 증명하고, F-38은 절차가 방향과 무관하게 같다고 합니다. 이 조합은 반사 공격의 전형입니다. 공격자가 서버에서 받은 임의 값을 두 번째 연결에서 서버에게 되물으면 서버가 정답을 만들어 줍니다. 또 인증 뒤의 TCP는 평문이라 같은 망에서 연결을 가로채 터치를 넣을 수 있습니다. NF-63은 "엿봄"만 적었습니다.
- 고칠 것: F-34에 "증명 값은 양쪽 임의 값(각 128비트 이상)과 역할 문자열(서버/클라이언트), 채널(`video`/`input`)을 모두 묶어 계산한다. 영상과 입력 소켓 각각 인증한다. 시험 벡터를 설계 문서에 둔다"를 추가합니다. NF-63에 "인증 뒤 연결 가로채기와 터치 주입은 막지 않는다"를 추가합니다.

### M7. 루프백 예외(F-36)가 구멍 두 개를 남긴다

- 근거 1: PC의 브라우저에서 연 아무 웹 페이지나 `ws://127.0.0.1:7300/input`에 붙을 수 있습니다. WebSocket은 교차 출처 제한이 없고 서버는 `Origin`을 보지 않습니다(`GameViewRemoteServer.cs:360~361`). 지금도 있는 구멍이지만 F-01로 서버가 Play 밖에서도 떠 있게 되어 노출 시간이 늘어납니다. 조사 6장은 `Origin` 검사를 적었는데 PRD에는 요구사항이 없습니다.
- 근거 2: LAN 연결을 루프백으로 넘기는 것(D17의 `node.exe` 중계)을 거치면 토큰 없이 들어옵니다.
- 고칠 것: 요구사항 추가. "`Origin` 헤더가 있는 WebSocket 요청은 자기 페이지의 출처(`http://localhost:포트`, `http://127.0.0.1:포트`)일 때만 받는다." D17에 "중계는 시험 포트로만, 측정하는 동안만 띄우고 끝나면 내린다. 중계가 떠 있는 동안 그 포트는 인증이 없다"를 적습니다.

### M8. LAN에 열리는 HTTP 표면이 정해져 있지 않다

- 근거: 지금 `/`, `/stats`, `/debug`가 인증 없이 응답합니다. NF-60은 "영상, 입력, 통계"만 말합니다. `/debug?pattern=1`은 화면을 테스트 패턴으로 바꿉니다. 연결마다 스레드를 하나 쓰므로(00 문서 1.4) 인증 전 연결을 쌓아 에디터를 느리게 할 수 있습니다. 바인드 정책(`0.0.0.0`을 기본으로 켤지)도 PRD에 없습니다.
- 고칠 것: 요구사항 추가.
  - 루프백이 아닌 연결에 열리는 경로는 착륙 페이지, APK, 인증된 `/video`·`/input`뿐이다. `/`, `/stats`, `/debug`는 루프백 전용이다.
  - 인증 전 연결은 3초 안에 인증하지 못하면 닫고, 동시에 8개까지만 받는다.
  - 바인드는 QR에 넣은 주소와 루프백에만 한다(`0.0.0.0` 아님). VPN과 가상 어댑터로는 열리지 않는다.
  - NF-60의 시험 목록에 `/debug`와 `/`를 넣는다.

### M9. 토큰이 QR 주소의 쿼리에 실린다

- 근거: 조사 3.3의 예 `http://…/c?v=1&s=…&t=…`. 토큰이 평문 GET에 실려 가고 브라우저 방문 기록에 남습니다. 토큰은 오래 갑니다(D3). QR은 에디터 창에 계속 떠 있어 화면 공유나 스크린샷으로도 새 나갑니다. PRD NF-63은 "설계에서 줄임"으로 미뤘습니다.
- 고칠 것: F-03에 "토큰은 주소의 `#` 뒤에 둔다(서버로 전송되지 않음). 착륙 페이지의 스크립트가 버튼의 `intent://` 주소를 만든다"를 넣습니다. F-02에 "기기가 연결된 동안에는 QR을 접어 두고 [QR 보기]로 편다"를 권장으로 추가합니다. 스크립트가 만든 `intent://` 링크가 삼성 인터넷에서 동작하는지는 M2의 3번에서 같이 확인합니다.

### M10. 워커가 시험할 수 없는 것이 합격 조건에 들어 있다

- 근거: NF-41의 "Wi-Fi 끊김 3회"는 폰 설정을 바꿔야 합니다(브리프 4장 금지). F-83(커버 화면)은 폰을 접어야 합니다. NF-9와 NF-40은 소유자의 폰 화면을 30분 켜 둡니다. 60Hz 고정 비교도 폰 설정입니다.
- 고칠 것: NF-41의 Wi-Fi 항목을 "서버 쪽에서 소켓을 끊거나 중계를 내려서 3회"로 바꾸고, 실제 Wi-Fi 끊김은 소유자 확인 목록으로 옮깁니다. 30분 시험은 조정자 결정 C4로 올립니다.

### M11. 관리자 없는 경로(B)가 "권장 실험"으로 밀려 있다

- 근거: 브리프 3장은 방화벽을 "관리자 권한 없이 어떻게 넘는가, 가능한 방법과 한계를 실제로 이 PC에서 확인"하라고 합니다. 조사 2.4는 방향 뒤집기(B)를 "될 가능성이 높지만 확인한 부분이 없는" 것으로 남겼고 PRD F-41은 권장입니다. 반면 F-38(방향과 무관한 절차)은 필수입니다. 확인되지 않은 방식 때문에 프로토콜을 일반화하면서 그 방식의 성립 여부는 미루는 셈입니다.
- B는 측정에도 쓸모가 있습니다. 앱이 듣고 PC의 시험 서버가 폰으로 걸면 방화벽도 중계도 없이 진짜 LAN 직접 수치가 나옵니다. R3의 대비책이 `node.exe` 중계 하나뿐인데, 중계는 띄워 본 적이 없습니다(조사 2.5).
- 고칠 것: F-41을 필수로 올리고 범위를 줄입니다. "앱이 TCP 포트를 열고, PC가 adb로 읽은 폰 `wlan0` 주소로 건다. 폰 주소 자동 발견(DNS-SD, 브로드캐스트)은 시험하지 않는다." F-38은 필수에서 빼고 설계 원칙으로 둡니다. R3의 대응에 이 경로를 두 번째 수단으로 적습니다.

### M12. 인증을 더하면 "프로토콜 2 그대로"(F-50)가 아니다

- 근거: F-34와 F-37은 새 메시지가 필요합니다. 5단계의 앱은 Unity 쪽(6단계)보다 먼저 만들어지고, 그때 붙을 수 있는 것은 워커가 직접 만든 시험 서버뿐입니다. 앱의 인증은 자기가 만든 상대하고만 맞춰 보게 됩니다. 도구 폴더는 지금도 바뀌고 있습니다(1장 표).
- 고칠 것: F-50을 "프레임 형식과 `hello`/`caps`/`a`/`key`는 프로토콜 2 그대로. 루프백이 아닌 연결은 그 앞에 인증 단계를 둔다. 인증 단계의 버전은 따로 센다"로 고칩니다. PRD 5.1에 "5단계의 시험 서버는 설계 문서의 인증 절차와 시험 벡터를 그대로 구현한다. 6단계의 Unity 구현도 같은 벡터로 확인한다"를 추가합니다.

### M13. 시험용 녹화 스트림을 어떻게 얻는지가 없다

- 근거: D17의 재생 서버는 "녹화한 프로토콜 2 스트림"이 필요합니다. 녹화하려면 실제 서버(포트 7300)에 영상 클라이언트로 붙어야 하고, 그 순간 다른 워커의 Chrome 세션이 MJPEG로 떨어집니다(`SingleH264Client`). 브리프 4장이 금지한 일입니다.
- 고칠 것: D17을 "ffmpeg를 서버와 같은 인자(00 문서 1.2)로 직접 돌려 테스트 영상을 FLV로 뽑고, 시험 서버가 28바이트 헤더를 붙여 보낸다. 실제 서버 녹화는 조정자가 허락한 시간에만"으로 고칩니다. 이 PC의 NVENC는 한 번에 여는 세션 수에 한도가 있을 수 있으므로 다른 워커의 인코더와 겹치는지 먼저 확인하라는 문장을 넣습니다(한도 값은 확인하지 않았습니다).

## 5. 범위에 대한 의견

- **과한 것**: F-38(방향 무관 절차, 필수), F-33의 여러 PC, F-11의 기기 이름과 앱 버전. 위 M11, m7, m8대로 내립니다.

## 8. 이 단계에서 한 것

- 읽기: 브리프, 00 문서, 조사, PRD, catjump의 `GameViewRemote.cs`·`GameViewRemoteServer.cs`·`GameViewRemotePage.html` 일부.
- PC 읽기 전용: 방화벽 규칙과 프로필(COM `FwPolicy2`), 네트워크 프로필, `node` 경로, 도구 폴더 파일 목록.
- 외부 열람: Chrome intent 문서, Android 평문 설정 문서 2개, 로컬 네트워크 권한 문서, `ConnectivityManager` 문서, Chrome 내려받기 관련 3개(본문 못 얻음). 요청에 소유자, 회사, 프로젝트 이름과 내부 주소를 넣지 않았습니다.
- 하지 않은 것: 폰 명령, 포트 열기, 방화벽 변경, Unity 조작, 포트 7300 접속, 이 문서 외의 파일 쓰기.
