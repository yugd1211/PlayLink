# 02. PRD — Game View Remote 안드로이드 앱 시제품

- 작성: 2026-11-13 23:20경 (1단계 워커). 근거는 `docs/01_research.md`(이하 "조사")와 `docs/00_current_system_and_history.md`(이하 "00 문서")에 있습니다. 절 번호로 가리킵니다.

- 열린 결정은 권장안으로 진행합니다. 소유자가 정해야만 하는 것은 바로 아래에 모았습니다.
- **3단계 개정(2026-11-13 밤)**: `docs/02_PRD_review.md` 의 지적과 브리프 3.1절(조정자 결정 C1~C5, 탭 끊김 원인 확인)을 반영했습니다. 지적별 수용/기각은 맨 끝 [9장](#9-prd-리뷰-반영-기록-3단계)에 있습니다. 구체적인 형식과 절차는 `docs/03_design.md` 가 정합니다.

## 0. 소유자가 정해야 하는 것

기다리지 않고 진행할 수 있게 각 항목에 "그동안 이렇게 진행"을 붙였습니다.

| # | 정할 것 | 왜 소유자만 할 수 있나 | 권장 | 그동안 이렇게 진행 |
|---|---|---|---|---|
| O1 | **이 PC의 Windows 방화벽에 허용 규칙을 한 번 넣는 것**(UAC "예" 1번) | UAC 동의 창은 사람이 눌러야 하고, 시스템 설정 변경입니다. 이 PC는 지금 폰 → Unity.exe 접속이 막혀 있습니다(조사 1.3, 직접 시도해 시간 초과) | 허용. 범위는 "이 Unity.exe, TCP, 도구 포트, 같은 서브넷에서만" | 조정자 결정 C1: 지금은 요청하지 않습니다. 6단계에서 도구에 "방화벽 허용" 버튼을 만들고 **누르지는 않습니다.** 그 전까지 LAN 직접 측정은 ① 이미 허용된 `node.exe` 중계(조사 2.5) ② 앱이 듣고 PC가 거는 방식(F-41)으로 합니다. 버튼을 실제로 눌러 확인하는 것은 소유자 몫으로 최종 보고에 남깁니다 |
| O7 | **처음 설치하는 폰은 "QR 한 번"이 아닙니다** | 요구사항 4("QR 한 번 찍으면 바로 연결")가 처음 설치 때는 그대로 성립하지 않습니다. 브라우저는 설치가 끝난 것을 알 수 없습니다 | 받아들임: 처음 한 번만 "QR 1번 + 설치 뒤 같은 페이지의 [앱으로 열기] 1번"(또는 QR 2번). 그 뒤로는 QR 0~1번 | 착륙 페이지를 닫지 않고 "설치가 끝나면 이 버튼"을 크게 보여 주는 것(F-27)을 필수로 올려 진행 |
| O8 | **관리자 동의를 못 하는 PC에서는 폰이 PC로 거는 QR 연결이 안 됩니다** | 방화벽 규칙은 관리자만 바꿀 수 있습니다(조사 2.3) | 그런 PC는 USB(흐름 F)로 쓰고, "앱이 듣고 PC가 거는 방식"이 F-41 실험에서 성립하면 다음 범위에서 제품 기능으로 | F-41 을 필수 실험으로 진행하고 결과를 보고 |
| O2 | **5GHz 에서의 측정**(무선 품질에서 가장 큰 변수. 2.4GHz 의 정체는 Wi-Fi 구간 자체에서 생기고 앱으로는 100ms 넘는 정체를 못 없앱니다, 4.7절) | 폰은 지금 2.4GHz 에 붙어 있고(조사 1.1) 워커는 폰 설정을 바꿀 수 없습니다. 공유기에 5GHz 가 있는지도 모릅니다 | 5GHz SSID 가 있으면 폰을 옮겨 준 뒤 측정 요청 | 2.4GHz 로만 재고, 합격 기준의 5GHz 칸은 "미측정"으로 둡니다 |
| O3 | **QR을 실제 카메라로 찍는 시험**(요구사항 10에서 이미 소유자 몫) | 사람 손이 필요 | 최종 보고의 확인 목록대로 | 워커는 QR 이미지를 프로그램으로 다시 읽고, 같은 주소를 adb 로 열어 확인합니다 |
| O4 | **이 폰의 삼성 "자동 차단" 상태** | 설정 키로 판별하지 못했습니다(조사 1.1). 켜져 있으면 QR 설치가 막힙니다 | 확인만 | 워커의 설치는 adb 로 하므로 영향 없음. QR 설치 시험 때 막히면 이 항목이 원인 후보 |
| O5 | 앱 식별자와 이름 | 한 번 배포하면 바꾸기 어렵습니다(식별자가 바뀌면 다른 앱) | 이름 `Game View Remote`, 식별자 `kr.co.seeplay.gvr` | 권장값으로 진행. 사내 배포 전까지는 바꿀 수 있습니다 |
| O6 | 사내 배포 범위와 서명 키 관리(누가, 몇 대) | 2027년 개발자 확인 제도(조사 4.1)와 키 보관에 영향 | 시제품은 프로젝트에 넣은 전용 디버그 키 | 시제품 범위 밖. 다음 범위에서 다시 묻습니다 |

## 1. 목표와 비목표

### 1.1 목표

| # | 목표 | 소유자 요구사항 |
|---|---|---|
| G1 | 안드로이드 네이티브 앱이 Unity 에디터의 Game 뷰를 받아 표시하고 터치를 되돌린다 | 1 |
| G2 | **무선(같은 Wi-Fi, LAN 직접)이 기본 경로**다. 합격 기준과 측정은 무선에서 한다. USB 는 기준선이자 대체 수단 | 11 |
| G3 | Unity 도구에서 Start 를 누르면 서버가 열리고 QR 이 나온다. 그 QR 하나로 **설치도 연결도** 한다 | 3, 5 |
| G4 | 주소와 포트를 사람이 입력하는 곳이 없다 | 4 |
| G5 | 손가락이 화면에 닿아 있는 동안에도 앱이 영상을 계속 받아 표시하는지를 **수치로 답한다.** 탭 끊김의 원인은 확인됐습니다(브리프 3.1: 누르고 있는 60~150ms 동안 Chrome 페이지 메인 스레드가 프레임을 받지 못하고 떼는 순간 몰아서 받음). 웹 페이지는 Web Worker 경로로 고쳤으므로 앱의 존재 이유는 ① QR 로 쉬운 설치와 연결 ② 무선(LAN 직접) 품질 쪽으로 옮겨졌고, 탭 구간은 **워커 경로가 적용된 새 웹 페이지와 같은 조건으로 비교**하는 합격 조건으로 남습니다 | 브리프 3.1, 00 문서 4장 |
| G6 | 나중에 문제가 생겼을 때 어디가 원인인지 가를 수 있는 계측을 처음부터 넣는다 | 8, 00 문서 5장 |
| G7 | **다른 Unity 프로젝트에서도 쓸 수 있는 형태**로 만든다: 게임 코드 의존 없음, 프로젝트별 설정 분리(이 프로젝트나 이 PC에 묶인 값을 코드에 적지 않음), Unity 쪽을 나중에 패키지로 떼어낼 수 있는 경계. 앱 하나로 여러 프로젝트에 붙는다 | 12 |
| G8 | **기능을 붙이기 쉬운 구조**로 만든다: 프로토콜의 버전·기능 협상, 옛 클라이언트를 깨지 않고 메시지와 채널을 늘릴 수 있는 규칙, 앱의 모듈 경계. 어떤 기능을 붙일지는 정해지지 않았으므로 **구체 기능은 만들지 않고 붙일 자리만 만든다** | 12 |

소유자 결정(요구사항 12): Chrome 페이지가 잘 동작하는 것을 확인한 뒤에도 앱은 그대로 진행합니다. 이유는 "다른 곳에서 쓰기 좋게, 기능을 더 붙일 수 있을 것 같아서"입니다. 그래서 앱의 가치는 탭 끊김(페이지에서 이미 고쳐짐)이 아니라 G2 ~ G4(무선 직접, QR 설치와 연결)와 G7, G8 에 있습니다.

## 2. 사용자와 사용 흐름

### 2.1 사용자

| 사용자 | 설명 | 필요한 것 |
|---|---|---|
| **기획자/아티스트/QA**(주 대상) | Unity 는 쓰지만 네트워크, adb, 개발자 옵션은 모름 | QR 한 번. 실패하면 무엇을 하라는 한 문장 |
| 개발자 | 도구를 설치하고 문제를 진단 | 진단 HUD, 통계, USB 대체 경로 |
| PC 관리자(같은 사람일 수 있음) | 처음 한 번 방화벽 허용 | 버튼 1번 + UAC 1번 |

### 2.2 흐름 A: PC 첫 준비 (PC마다, Unity 버전마다 한 번)

1. Unity 에서 `Tools > Game View Remote > Window` 를 엽니다.
2. [Start] 를 누릅니다. 창이 "이 PC는 폰에서 들어오는 연결이 막혀 있습니다"를 보여 주고 [방화벽 허용] 버튼을 냅니다(막혀 있을 때만).
3. [방화벽 허용] → Windows 의 UAC 창에서 [예]. 창의 경고가 사라지고 QR 이 나옵니다.

- 사람이 하는 일: 클릭 2번 + UAC 1번. 명령 입력 없음.
- 관리자 비밀번호를 모르는 계정이면 3번이 막힙니다 → 흐름 F(USB) 또는 다음 범위의 "PC가 폰으로 거는 방식".

### 2.3 흐름 B: 폰에 처음 설치 (QR)

1. 폰 기본 카메라로 Unity 창의 QR 을 비추고 뜨는 주소를 누릅니다.
2. 브라우저에 착륙 페이지가 열립니다. [앱 설치] 를 누릅니다.
3. 브라우저와 Android 가 묻는 것에 답합니다: 내려받기 경고 → 열기 → (처음이면) 이 출처 허용 → 설치 → Play 프로텍트 확인 → 열기.
4. 설치가 끝나면 브라우저에 그대로 남아 있는 착륙 페이지의 큰 버튼 [설치가 끝났으면 여기를 눌러 연결]을 누릅니다(F-27, 필수). 연결됩니다. 브라우저 탭을 닫았다면 앱의 스캐너로 같은 QR 을 한 번 더 비춥니다.

- 즉 처음 설치하는 폰은 "QR 1번 + 버튼 1번"(또는 QR 2번)입니다. "QR 한 번"은 설치가 끝난 폰에서만 성립합니다(0장 O7).
- 탭 수: 직접 설치를 처음 해 보는 폰에서 약 10~11번, 소유자 폰의 지금 상태에서 약 8~9번(조사 4.3. **예상이며 실제 화면으로 끝까지 확인하지 않았습니다.** 5단계 첫 작업에서 실기기로 기록합니다, 5.1절).
- 이 탭들은 Android 가 요구하는 것이고, 줄이는 방법은 USB 설치 외에는 찾지 못했습니다. 삼성 자동 차단이 켜진 폰은 먼저 그것을 꺼야 합니다.

### 2.4 흐름 C: 평소 연결

| 경우 | 사람이 하는 일 |
|---|---|
| 그 PC에 연결한 적이 있음 | Unity [Start] → 폰에서 앱 아이콘 1번. **QR 없음**(자동 재접속) |
| 처음 보는 PC | Unity [Start] → 앱 아이콘 → 앱의 스캐너로 QR 비춤(처음 한 번 카메라 권한 허용) |
| 앱이 깔려 있는지 모름 | 기본 카메라로 QR → 착륙 페이지 [앱으로 열기] |

- Start 는 Play 전에 눌러도 됩니다. 앱은 연결된 뒤 "Play 를 기다리는 중"을 보여 주다가 Play 가 시작되면 영상을 띄웁니다.

### 2.5 흐름 D: 재접속

| 상황 | 동작 |
|---|---|
| Play 종료 → 다시 Play, 스크립트 재컴파일 | 앱이 스스로 다시 붙음. 사람은 아무것도 안 함 |
| 앱이 뒤로 갔다 돌아옴, 화면 꺼졌다 켜짐 | 돌아오면 스스로 다시 붙고 화면이 3초 안에 나옴 |
| Wi-Fi 가 잠깐 끊김 | 화면에 "다시 연결 중", 스스로 재시도 |
| PC 주소가 바뀜 | 같은 망에서 서버를 찾아 다시 붙음(권장 F-12). 못 찾으면 "QR 을 다시 찍으세요" |
| 토큰을 새로 발급함 | 기억한 서버가 거절 → "QR 을 다시 찍으세요" |

### 2.6 흐름 E: 실패할 때

원칙: 앱과 도구 창은 **원인과 다음 행동을 한 문장씩** 보여 줍니다. 오류 코드만 보여 주지 않습니다.

| 상황 | 폰에 보이는 것 | Unity 창에 보이는 것 |
|---|---|---|
| QR 의 주소에 닿지 않음 | "PC에 연결할 수 없습니다. 폰과 PC가 같은 Wi-Fi 인지 확인하세요." + 시도한 주소 | 방화벽이 막고 있으면 경고와 [방화벽 허용] |
| 토큰이 틀림(옛 QR) | "이 QR 은 더 이상 쓸 수 없습니다. Unity 창의 QR 을 다시 찍으세요." | — |
| 프로토콜/인증 버전이 다름(필수) | "앱과 Unity 도구의 버전이 맞지 않습니다." + 어느 쪽을 올려야 하는지 | 접속을 거절한 이유 |
| 앱 버전이 도구에 든 APK 보다 낮음(권장, F-25) | "새 버전이 있습니다." + [업데이트] | 접속한 앱 버전 |
| 서버가 H.264 를 못 냄(ffmpeg 없음 등) | "PC가 H.264 를 보낼 수 없습니다." (시제품은 MJPEG 를 표시하지 않음) | 지금처럼 `MJPEG (이유)` |
| 다른 클라이언트가 영상을 보는 중(자리 내줌) | "다른 기기가 보고 있습니다." + [여기서 보기]. 연결은 유지하고 **스스로 다시 뺏지 않습니다** | 지금 보는 쪽과 대기 중인 쪽 |
| Game 뷰가 가려짐, 일시정지 | 서버가 보내는 상태 문구 그대로 | 지금과 같음 |
| USB 대체로 붙음 | HUD 에 "경로: USB(adb)" | "영상 경로: USB" |

### 2.7 흐름 F: USB 대체

1. 폰을 USB 로 연결(USB 디버깅 켜짐).
2. Unity 창 [USB 로 앱 설치] → adb 가 설치(폰에서 탭 0번).
3. Unity 창 [USB 로 연결] → adb reverse 를 걸고 앱을 연결 정보와 함께 실행.

- 방화벽 허용이 필요 없습니다. 워커의 설치와 시험(요구사항 9)도 이 경로를 씁니다.

## 3. 기능 요구사항

우선순위: **필수** = 시제품 합격에 필요, **권장** = 시제품에 넣되 시간이 모자라면 미룸, **나중** = 다음 범위.

### 4.2 부드러움과 지연 (잠정)

"고르지 않은 표시 간격" = 연속 표시 간격이 9ms 미만 또는 25ms 초과인 비율(00 문서 6.3 과 같은 정의). 앱에서는 시스템이 알려 준 표시 시각으로 계산합니다.

NF-3, NF-4, NF-10 의 "탭 창" = 각 탭의 down 시각 − 200ms 부터 up 시각 + 200ms 까지. "누름 구간" = down 부터 up 까지.

| # | 지표 | USB 기준선(잠정) | **무선 2.4GHz**(잠정) | 무선 5GHz | 참고(옛 Chrome 페이지, 주입 탭은 누르는 시간 없음) |
|---|---|---|---|---|---|
| NF-1 | 표시 fps(60fps 입력) | 59 이상 | 58 이상 | 미측정 | USB 59.7~60.1 |
| NF-2 | 고르지 않은 표시 간격, 무터치 | 0.5% 이하 | 1% 이하 | 미측정 | USB 0.0%, 무선 adb 0.8% |
| NF-3 | 고르지 않은 표시 간격, **탭 창 안** | 1% 이하 | 2% 이하 | 미측정 | USB 1.1%, 무선 adb 3.8%(구간 전체 기준) |
| NF-4 | **탭 창 안과 탭 창 밖의 차이** | 1%p 이하 | 1.5%p 이하 | 미측정 | USB 1.1%p, 무선 adb 3.0%p(구간 전체 기준) |
| NF-10 | **누름 구간에 영상이 멈춘 탭의 비율**: 누름 구간과 그 직후 50ms 안에 표시 간격 50ms 초과가 있거나, 손을 뗀 직후 6ms 안에 3장 이상이 몰려 도착한 탭 / 전체 탭. 같은 시각의 서버 쪽 공백(캡처 간격 50ms 초과)으로 설명되는 탭은 뺀다 | 5% 이하 | 10% 이하 | 미측정 | 진단 워커: 실제 손가락 탭 87회 중 약 60%(고치기 전 페이지) |
| NF-5 | 표시 간격 50ms 초과(정체) | 10초에 0회 | **기준 아님, 기록 항목**: 같은 시각의 도착 정체로 설명되지 않는 것이 10초에 0회(앱이 만든 정체가 없어야 함). 링크 정체로 생긴 것은 횟수와 길이를 지터 버퍼 설정별로 기록(4.7절) | 미측정 | 링크만 잰 값: Wi-Fi 직접에서 도착 간격 40ms 이상이 20초에 23~25회, 최대 46~470ms |
| NF-6 | 터치 → 표시 평균 / p90 | 66ms / 90ms 이하(= 새 웹 페이지 이하) | 72ms / 100ms 이하(지터 버퍼 "균형" 설정에서. 버퍼를 키운 설정은 따로 적음) | 미측정 | 옛: USB 61.9ms, 무선 adb 80.6ms. **새 페이지(워커)**: USB 66.0ms, 무선 adb 71.7ms, 50ms 버퍼를 넣으면 107ms |
| NF-7 | 캡처 → 표시 평균 | 30ms 이하 | 40ms 이하 | 미측정 | USB 25~28ms, 무선 adb 32~39ms |
| NF-8 | 받았는데 표시하지 않은 프레임 | 1% 이하 | 3% 이하 | 미측정 | 무선 adb 탭 8.9% |
| NF-9 | 지연 누적 | 30분 재생 뒤 캡처 → 표시 평균이 처음 1분 대비 +10ms 이내 | 같음 | 미측정 | — |

- **앱이 맞추거나 넘어야 할 기준선은 워커 경로가 적용된 새 웹 페이지입니다**(진단 워커 보고 3, 표준 60Hz 고정, 120ms 제자리 누름 5회, 9.5초): USB 탭에서 멈춘 갱신 0.1/초, 건너뛴 프레임 0/초, 화면 정지 최대 50ms, 표시 59.6fps, 터치 → 표시 66.0ms. 무선 adb 탭에서 0.1/초, 0/초, 50ms, 59.3fps, 71.7ms. 앱도 같은 정의(멈춘 갱신 = 표시 간격이 원본 간격보다 8ms 넘게 긴 것, 건너뛴 프레임 = 받았는데 표시하지 않은 것, 화면 정지 최대)로 같이 냅니다. 가변 120Hz 모드의 페이지 수치는 없습니다(폰이 표준 60Hz 였음).
- 위 무선 값은 **근거가 무선 adb 터널 수치와 링크만 잰 값뿐인 잠정값**이고, USB 값도 앱으로 잰 적이 없는 잠정값입니다. 5단계의 첫 측정 뒤 이 표를 고칩니다. LAN 직접이 터널보다 나쁘게 나오면 기준을 낮추는 것이 아니라 원인(2.4GHz 혼잡, TCP 정체)을 문서에 적고 4.6절의 UDP 판단으로 넘깁니다.
- NF-4 의 1%p 는 60초(약 3600장, 탭 창 약 1000장)에서 10장 차이입니다. 구간이 짧으면 구분되지 않으므로 4.1절의 60초 이상을 지킵니다.
- NF-4 와 NF-10 이 탭에 대한 질문의 답입니다. 충족되지 않으면 그 순간의 서버 `/stats`(Unity 프레임 시간, `transportStride`, 00 문서 6.2)와 앱의 도착 간격을 같이 봐서 Unity 쪽인지, 링크인지, 앱인지 가릅니다(5.1절 합격 조건 2).
- 수치가 좋아도 눈으로 본 것과 다를 수 있습니다(00 문서 L2). 소유자의 눈 확인이 최종 판정에 들어갑니다.

### 4.6 UDP 로 넘어갈지의 판단 기준 (다음 범위의 입구)

전제(4.7절): 지금까지 잰 2.4GHz 정체는 Wi-Fi 구간 자체에서 생겼습니다. 정체가 무선 MAC 계층(재전송, 절전, 채널 점유)에서 패킷을 붙잡는 것이면 UDP 로 바꿔도 그 패킷은 똑같이 늦게 옵니다. UDP 가 줄일 수 있는 것은 TCP 가 덧붙이는 부분(손실 뒤 재전송 대기, 뒤 프레임이 줄줄이 밀리는 것)뿐입니다. 그래서 아래는 "정체가 있다"가 아니라 "TCP 가 정체를 키우고 있다"는 증거를 조건으로 합니다.

5단계의 LAN 직접 TCP 측정에서 아래 중 하나라도 해당하면 다음 범위에서 UDP 경로를 설계합니다. 해당하지 않으면 TCP 를 유지합니다.

- 표시 간격 50ms 초과(정체)가 5GHz 에서도 10초에 1회를 넘는다.
- 2.4GHz 에서 도착 지연 40ms 이상인 프레임이 2%를 넘고, 그 원인이 TCP 재전송으로 보인다(같은 구간에 Unity/인코더 쪽 지연이 없음). 재는 법: 측정 전후 PC의 `netstat -s -p tcp` 재전송 수 차이와 앱의 도착 지연 기록을 같이 적는다(같은 PC의 다른 트래픽도 섞이므로 강한 증거는 아님).
- 지터 버퍼 목표 지연이 2프레임을 계속 넘는다.

### 4.7 2.4GHz 무선에서 앱이 고칠 수 있는 것과 없는 것 (진단 워커 보고 3 반영)

같은 폰, 같은 공유기(2.4GHz 802.11n 채널 1, RSSI −48)에서 게임 없이 링크만 잰 값입니다(12.5KB 를 16.7ms 마다, 20초씩 4회, 폰 Chrome 이 받음).

| 경로 | 지연 흔들림 p50 / p99 / 최대 | 40ms 이상 늦은 비율 | 도착 간격 40ms 이상(20초당) |
|---|---|---|---|
| adb reverse, USB | 1.7 / 4.4~9.2 / 17~25ms | 0% | 0~1회 |
| adb reverse, 무선 adb | 3.3~3.8 / 34~236 / 61~417ms | 0.3~3.3% | 9~11회 |
| **Wi-Fi 직접(PC IP)** | 2.1~2.4 / 35~312 / 46~470ms | 0.3~3.3% | 23~25회 |

- **정체는 adb 터널이 아니라 Wi-Fi 구간 자체에서 생깁니다. LAN 직접 연결은 평소 2~3ms 빠를 뿐 정체는 같거나 더 많았습니다.** "LAN 직접이면 무선 정체가 해결된다"는 가정은 틀렸고, 이 문서와 설계는 그 가정을 쓰지 않습니다.
- 이 값은 Chrome 이 받은 것입니다. 네이티브 앱 + Wi-Fi 저지연 잠금 + 소켓 설정에서 같은 값이 나오는지는 **아직 모릅니다**(5단계에서 같은 방식으로 다시 잼).

**앱이 2.4GHz 에서 할 수 있는 것**

| 항목 | 내용 | 근거 수준 |
|---|---|---|
| LAN 직접에서 H.264 | 웹 페이지는 `http://<PC IP>` 가 보안 컨텍스트가 아니라 WebCodecs 를 못 써서 **MJPEG 로 떨어집니다**(무선 대역을 넘음, 00 문서 3.6.1). 앱은 LAN 직접에서 H.264 를 씁니다. 케이블도 adb 도 없는 무선에서 H.264 를 쓰는 길은 앱뿐입니다 | 보고 3 + 코드. 5단계에서 실기기 확인 |
| 지터 버퍼로 짧은 정체 가리기 | 표시를 N ms 늦추면 N ms 이하의 정체는 보이지 않습니다. 대가는 터치 → 표시가 그만큼 늘어나는 것(웹 페이지 50ms 버퍼: 멈춘 갱신 0.7 → 0.0/초, 터치 → 표시 66 → 107ms). 앱은 이 맞바꿈을 설정(지연 우선 / 균형 / 부드러움 우선)으로 내놓고 설정별 수치를 냅니다 | 보고 3(페이지) |
| Wi-Fi 저지연 잠금 | 폰 Wi-Fi 의 절전이 수신을 묶는 것이 정체의 일부라면 `WIFI_MODE_FULL_LOW_LATENCY` 잠금이 줄일 수 있습니다. 브라우저는 못 하고 앱만 할 수 있습니다. **가설이고 재지 않았습니다.** 켬/끔 비교를 5단계 무선 측정에 넣습니다(F-61 필수로 올림) | 가설 |
| 정체 뒤 회복 | 몰려 온 프레임을 전부 디코딩하고 최신 1장만 표시해 지연이 쌓이지 않게 합니다(F-56). 서버는 150ms 넘게 밀리면 인코딩 전에 건너뜁니다(이미 있음) | 코드 |
| 비트레이트 | 6Mbps 와 3Mbps 를 비교해 정체가 보내는 양에 따라 달라지는지 봅니다 | 미측정 |

**앱이 고칠 수 없는 것**

- 100ms 를 넘는 Wi-Fi 정체(최대 470ms 까지 측정됨). 지터 버퍼로 가리려면 터치 지연이 그만큼 늘어나 조작용으로 쓸 수 없습니다. 그 순간 화면은 멈췄다가 건너뜁니다.
- 2.4GHz 채널의 혼잡 자체. **5GHz 가 가장 효과가 클 것으로 예상되지만 측정하지 않았습니다**(O2: 소유자가 폰을 5GHz 로 옮겨 줘야 잴 수 있음).
- UDP 로 바꿔도 무선 MAC 계층이 붙잡은 패킷은 빨리 오지 않습니다(4.6절).

**방화벽에 대한 두 보고의 대조**: 진단 워커의 링크 시험이 방화벽에 막히지 않은 것은 `node.exe` 가 `0.0.0.0:7312` 에서 들었기 때문입니다(`measure/linktest.js`. `node.exe` 는 이 PC에서 공용 프로필 인바운드가 이미 허용됨, 조사 1.3). **Unity.exe 가 직접 받는 것은 여전히 막혀 있습니다**(조사 1.3: 폰 → Unity.exe 포트 시간 초과, 리뷰가 규칙을 다시 읽어 확인). 둘 다 맞습니다. 이 결과는 조사 2.5 의 "`node.exe` 중계로 LAN 직접을 잴 수 있다"가 실제로 된다는 확인이기도 합니다.

### 5.1 시제품 (이 프로젝트에서 만들고 연결된 폰으로 시험)

**안드로이드 앱(5단계)**

- 연결: 딥링크/인텐트/앱 안 스캐너 입구(F-30, F-31), 병렬 시도(F-32), 서버 기억과 자동 재접속(F-33, F-40), 인증(F-34, F-37, F-38)
- 영상: F-50 ~ F-60, 입력: F-70 ~ F-73, 화면: F-80 ~ F-82, 진단: F-90 ~ F-93, F-95
- 빌드와 서명: F-22, F-23, F-26, F-103
- 실험: F-41(앱이 듣고 PC가 거는 방식), F-64(평문과 직접 구현 WebSocket)
- 시험용 서버: Unity 를 고치기 전이므로 **프로토콜 2 스트림을 보내는 재생 서버와 TCP 중계**를 다른 포트에 둡니다(조사 2.5, 7.4). 재생 서버의 스트림은 ffmpeg 를 실제 서버와 같은 인자(00 문서 1.2)로 직접 돌려 만들고, 시험 서버가 28바이트 헤더를 붙여 보냅니다(실제 서버를 녹화하려고 다른 워커의 세션에 붙지 않음. NVENC 동시 세션 한도와 겹칠 수 있으므로 띄우기 전에 다른 워커의 인코더가 도는지 확인). 시험 서버는 설계 문서의 **인증 절차와 시험 벡터를 그대로 구현**하고, 6단계의 Unity 구현도 같은 벡터로 확인합니다. 중계는 시험 포트로만, 측정하는 동안만 띄우고 끝나면 내립니다(떠 있는 동안 그 포트는 인증이 없음).
- **5단계 첫 작업(앱 코드를 쓰기 전)**: ① `node.exe` 정적 서버를 LAN 포트에 띄워 폰 셸의 `nc` 로 닿는지 확인(양성 대조. 실패하면 방화벽이 아니라 공유기가 원인) ② 빈 APK 와 착륙 페이지 초안을 그 서버에 두고 adb 로 그 주소를 삼성 인터넷과 Chrome 에 열어 내려받기와 설치 화면을 기록(조정자 결정 C2: 폰의 보안 설정을 바꾸는 화면은 누르지 않고 그 화면이 나오는 데까지만) ③ `intent://…;S.browser_fallback_url=…;end` 버튼이 앱이 있을 때와 없을 때 두 브라우저에서 어떻게 되는지 기록. 결과가 "막힘"이면 QR 설치의 기본 흐름을 바꿔야 하므로 6단계 전에 보고합니다.

**Unity 도구(6단계, 조정자가 시작을 정함)**

- F-01 ~ F-04, F-06 ~ F-09, F-11, F-20, F-21, F-24, F-27, F-34 ~ F-37, F-39, F-43, F-44, F-100, F-101
- 공존 규칙(F-39)과 Play 밖 서버(F-01)는 다른 워커가 고치는 기존 파일을 바꾸므로 조정자가 정한 시점(진단 워커가 끝난 뒤, C3)에 합니다.

**워커가 확인할 수 없어 소유자에게 남기는 것**

- 카메라로 QR 찍기(O3), UAC 동의와 그 뒤의 실제 방화벽 통과(O1), 5GHz(O2), 실제 손가락으로 탭했을 때 눈에 끊겨 보이는지(HUD [기록 시작/끝]으로 수치도 같이), QR 설치에서 폰의 보안 설정을 바꾸는 화면부터 끝까지(그 화면이 나오는 데까지는 워커가 하고 기록, C2), 인터넷 없는 Wi-Fi 와 폰 VPN(NF-43), 실제 Wi-Fi 끊김, 폰을 60Hz 고정으로 바꾼 상태의 비교, 접은 상태의 커버 화면.
- 30분 연속 시험(NF-9, NF-40)은 워커가 돌립니다(조정자 결정 C4). 소유자가 폰을 쓰고 있는 것으로 보이면 미루고 보고에 적습니다.

**시제품 합격 조건**

1. **실제 Unity 서버**에 **무선 LAN 직접**(2.4GHz. 중계나 "PC가 거는 방식"을 거쳤으면 그렇게 표시)으로 붙어 4.1절 조건으로 NF-1 ~ NF-10 을 쟀다. 같은 날 같은 경로로 워커 경로 Chrome 페이지도 재서 나란히 놓았다(Chrome 페이지는 LAN 직접에서 H.264 를 못 쓰므로 페이지 쪽 무선 수치는 무선 adb 터널 것이고, 그렇게 표시한다. USB 는 양쪽 같은 경로). 재생 서버 수치는 합격 근거가 아니다.
2. 결과를 셋 중 하나로 판정했다. (가) NF-2 ~ NF-5, NF-10 충족 → 합격. (나) 미충족이고 같은 구간의 서버 `/stats` 프레임 시간이나 `transportStride` 에 원인이 보임 → "Unity 쪽"으로 판정하고 증거를 첨부(합격으로 치되 넘길 문제로 기록). (다) 미충족이고 도착 간격에 원인이 보임 → "링크"로 판정하고 4.6절로(합격으로 치되 UDP 판단을 기록). 셋 어디에도 들어가지 않으면(도착은 고른데 앱 표시가 고르지 않음) **미합격**이다.
3. NF-20 ~ NF-23, NF-25, NF-27, NF-40, NF-41, NF-45, NF-60 을 충족한다.
4. QR 이 올바른 내용으로 생성되고, 그 주소와 딥링크가 adb 로 동작한다.
5. F-41 실험의 결과(성립 여부와 수치)가 문서에 있다.
6. 소유자 확인 목록이 최종 보고에 있다.

- B1 의 "비교 대상을 같은 날 같은 경로로": 무선에서는 **같은 경로가 될 수 없습니다.** Chrome 페이지는 `http://<PC IP>` 에서 WebCodecs 를 못 써서(00 문서 L12) LAN 직접으로는 H.264 를 받지 못합니다. 그래서 무선 비교는 "앱 = LAN 직접, 페이지 = 무선 adb 터널"이고 그렇게 표시합니다. USB 는 양쪽이 같은 경로입니다(합격 조건 1).
